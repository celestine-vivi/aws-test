Lambda: 制限、concurrency、layer、VPC、event source

概要

Lambda はイベントが発生したときに関数（function）を実行します。利用者はコードを渡して memory を選ぶだけで、サーバー、OS、スケールは AWS が担当します。料金は リクエスト数 と GB-second（割り当て memory × 実行時間、1 ms 単位で切り上げ）で決まります。リクエストがなければ費用はかかりません。Always free: 毎月 100万リクエストと 400,000 GB-s。

  • 利用できる runtime: Python、Node.js、Java、.NET、Ruby、Go（provided 形式）、custom runtime、または AWS の base image をもとにした container image（最大 10 GB）。
  • 1 回の呼び出しは 1 つの execution environment（Firecracker の micro VM）で処理されます。環境はしばらくウォームな状態で保持され、次の呼び出しで再利用されるため、handler の外で初期化した変数（DB 接続、SDK client）は残ります。
  • Execution role: Lambda が他のサービスを呼ぶときに assume する IAM role です（CloudWatch Logs への書き込み、DynamoDB の読み取りなど）。逆に、誰が Lambda を呼べるかは function の resource-based policy で決まります（S3、API Gateway、他アカウントはここに追加します）。

Concurrency と cold start
  • Cold start: 最初の呼び出し（または環境を追加で作るとき）は、コードの読み込み、runtime の初期化、init 部分の実行に追加の時間がかかります。Java、.NET が最も遅く、Python、Node.js は速いです。VPC 内の関数は、デプロイ時に ENI が作成済みになる（Hyperplane ENI）ため、現在は以前ほど cold start が長くありません。
  • Reserved concurrency: その関数専用に一定数の枠を確保し、同時にその関数の 上限 にもなります。費用はかかりません。0 に設定すると関数を緊急停止できます。downstream を守りたいとき（DB の接続上限が 50 → reserved 50）に使います。
  • Provisioned concurrency: 初期化済みの環境を N 個待機させるので cold start がなくなります。呼び出しがなくても時間単位で課金されます。スケジュールまたは Application Auto Scaling でスケールします。問題文に consistent low latency、eliminate cold start → provisioned。
  • SnapStart（名前を知っていれば十分）: init 後の環境のスナップショットを取り、呼び出し時に復元することで cold start を最大 10 分の 1 に短縮します。当初は Java のみでしたが、Python と .NET にも拡大されています（AWSドキュメントで要確認）。provisioned concurrency との違いは、SnapStart は環境を常時起動しておかない点です。
  • スケール: Lambda は function ごとに 10 秒あたり約 1,000 の速度で新しい環境を追加します（AWSドキュメントで要確認）。downstream が耐えられない場合は、reserved concurrency で制限するか、SQS をバッファとして挟みます。

VPC 内の Lambda
  • デフォルトでは Lambda は利用者の VPC の外で動き、Internet に出られ、public な AWS サービスも呼べますが、private な RDS / ElastiCache には アクセスできません。
  • VPC に接続する: subnet と Security Group を選ぶと、Lambda はその subnet に ENI を作成します。以後、関数のネットワークは subnet 内の 1 台のマシンと同じになります。Internet に出るには private subnet + NAT Gateway が必要です（Lambda には public IP がないため public subnet に置いても効果はありません）。Internet を経由せずに S3、DynamoDB を呼ぶ → VPC endpoint。
  • ENI を作成するため、Execution role に AWSLambdaVPCAccessExecutionRole が必要です。
  • 問題文に Lambda cannot connect to RDS in private subnet → Lambda を VPC に入れ、RDS の Security Group で Lambda の SG からの通信を許可します。多数の Lambda が DB 接続を開きすぎる場合は RDS Proxy を追加します。
Layer、URL、Edge
  • Layer: ライブラリ、custom runtime、設定ファイルを含む zip で、複数の function に付けられます。package のサイズを減らし依存関係を共有できますが、合計は 250 MB に含まれます。
  • Function URL: function に直接付く HTTPS endpoint で、認証は AWS_IAM か NONE。シンプルな webhook には十分ですが、API Gateway のような throttling、usage plan、キャッシュはありません。
  • Lambda@Edge: CloudFront の Edge location で実行され、Node.js か Python で書き、us-east-1 からデプロイし、4 つのイベント（viewer request / response、origin request / response）にフックします。A/B テスト、ヘッダーの変更、国別の origin 選択、トークン認証に使います。CloudFront Functions（JavaScript、1 ms 未満で実行、viewer request / response のみ、より安価、ネットワーク呼び出し不可）との比較: URL の書き換えやヘッダー追加など軽い処理 → CloudFront Functions。他サービスの呼び出しや時間のかかる処理 → Lambda@Edge。
  • Alias と version: 不変の version を publish し、alias（prod、dev）が version を指します。alias で比率を指定して負荷を分け、canary を行えます。

確認クイズ

1. 画像を処理する Lambda が memory 512 MB で 20 秒かかっています。開発者はコードを変えずに速くしたいと考えています。どうしますか。

memory を増やします。 Lambda の CPU は memory に比例し、約 1,769 MB で 1 vCPU 分になります。timeout を延ばしても長く実行できるだけで速くはなりません。「layer を追加する」を選ぶ人もいますが、layer はライブラリをパッケージする手段にすぎません。

2. ファイルがアップロードされると S3 から Lambda が呼ばれます。外部サービスの利用上限に達して関数がときどき失敗しますが、イベントを一つも失いたくありません。least operational overhead な方法は？

function に on-failure destination（または DLQ）として SQS キューを設定します。 S3 は Lambda を asynchronous で呼ぶため、Lambda は 2 回 retry した後、失敗したイベントを destination に送り、後で再処理できます。エラーを DynamoDB に書き出すコードを自作しても可能ですが手間がかかります。S3 は自動で retry しません。

3. private subnet に置いた Lambda が、Security Group で outbound を許可しているのに Internet 上の public API を呼べません。なぜですか。

NAT Gateway（private subnet の 0.0.0.0/0 ルート）がないためです。 VPC 内の Lambda には public IP がないため、Internet Gateway のある public subnet に置いても外に出られません。「Lambda を public subnet に移す」は典型的なひっかけです。

4. アカウントに 20 個の Lambda があります。夜間バッチの関数がときどき concurrency をほぼ使い切り、顧客向け API の関数が 429 になります。最も安く直す方法は？

バッチ関数（例: 200）と / または API 関数に reserved concurrency を設定します。 Reserved は専用枠であると同時に上限でもあり、費用はかかりません。Provisioned concurrency も API 関数の助けにはなりますが、時間単位の費用がかかり、バッチ関数が残りを使い切るのを防げません。

API Gateway: REST と HTTP API、throttling、キャッシュ、authorizer

概要

API Gateway は API のためのマネージドな「玄関口」です。HTTPS リクエストを受け、認証、レート制限、キャッシュ、変換を行い、バックエンド（Lambda、HTTP endpoint、AWS サービス）を呼び出します。API は 3 種類あります。REST API（最も機能が多い）、HTTP API（軽量で安価、新規アプリの大半はこれで十分）、WebSocket API（長時間の双方向接続）です。

  • 設定は 3 層です: API → resource / route と method → バックエンドへの integration。stage（dev、prod）にデプロイすると stage ごとに URL があり、stage variable で stage ごとに別の Lambda alias を指せます。
  • Integration timeout は最大 29 秒（Regional の REST API は引き上げ申請可能、AWSドキュメントで要確認）。超えるとクライアントは 504 を受け取ります。Payload は最大 10 MB。
  • よく出るエラーコード: 429 throttle された、502 バックエンドの応答形式が不正（Lambda proxy が statusCode を返さない）、504 バックエンドが 29 秒を超えた、403 authorizer が拒否した、または API key がない。

Endpoint type（REST API）
  • Edge-optimized（デフォルト）: AWS が管理する CloudFront ネットワークを経由し、世界中のクライアントに向いています。
  • Regional: クライアントが同じ Region にいる場合、または自前の CloudFront を前段に置いてキャッシュや WAF を制御したい場合。
  • Private: interface VPC endpoint（execute-api）経由で VPC 内からのみ呼べます。aws:SourceVpce を制限する resource policy と組み合わせます。問題文に API must not be reachable from the Internet → Private。
Throttling とキャッシュ
  • Region ごとのアカウント上限: 10,000 リクエスト/秒、burst 5,000（AWSドキュメントで要確認）。超えると 429。さらに stage 単位、method 単位、または usage plan + API key（rate、burst、月間 quota）で顧客単位の制限をかけられます。
  • キャッシュ（REST）: stage 単位で有効化し、TTL はデフォルト 300 秒（0〜3,600）、容量 0.5〜237 GB、時間単位で課金されます。execute-api:InvalidateCache 権限を持つクライアントは Cache-Control: max-age=0 ヘッダーでキャッシュを無視できます。変更の少ないデータで Lambda / DB の負荷とレイテンシーを下げます。
  • バックエンドが過負荷 → throttling に加えて、integration を SQS に変えることも検討します（API Gateway がキューに直接書き込み、Lambda が後で処理）。

Integration: API Gateway が背後で何を呼ぶか
  • Lambda proxy: リクエスト全体（header、path、query、body）をそのまま event に変換し、Lambda は statusCode、headers、body を持つオブジェクトを返す必要があります。最も簡単で、ラボでも使います。
  • Lambda non-proxy（custom、REST）: VTL の mapping template でリクエスト / レスポンスを変換し、Lambda は HTTP を意識しなくて済みます。
  • HTTP: 任意の HTTP endpoint（public な EC2、オンプレミス、ALB）へ転送します。VPC 内の private なバックエンド → VPC Link 経由。
  • AWS service: Lambda を使わずに AWS サービスの API を直接呼びます。SQS、Kinesis、DynamoDB への書き込み、Step Functions の開始など。問題文に without writing code、directly to SQS → この integration。
  • Mock: 固定のレスポンスを返します。CORS の preflight や、バックエンドがまだない段階のテストに使います。

CORS: ブラウザが別ドメインの API を呼ぶには Access-Control-Allow-Origin ヘッダーが必要です。HTTP API は設定で有効化できます。REST API の proxy integration では Lambda 自身がこのヘッダーを返し、OPTIONS method は Mock で作ります。ブラウザでは CORS エラーなのに curl では動く場合、CORS の設定忘れのサインです。

WebSocket API、stage、canary
  • WebSocket API: チャット、リアルタイムダッシュボード、ゲーム向けの長時間の双方向接続です。route は $connect、$disconnect、$default と、message の内容による独自 route。バックエンドは connectionId（通常 DynamoDB に保存）を使い、@connections callback URL でクライアントに送り返します。
  • Stage: REST API は変更のたびに stage へ デプロイ し直す必要があり、デプロイ忘れはよくあるミスです。stage variable を Lambda alias に対応付けると、同じ API で dev / prod を別々に指せます。
  • Canary release（REST）: 同じ stage の新しいデプロイメントにトラフィックの一部を振り分け、メトリクスを見て promote または rollback します。
  • モニタリング: CloudWatch メトリクス 4XXError、5XXError、Latency、IntegrationLatency、Count。access log と execution log。X-Ray によるエンドツーエンドのトレース。

SQS と SNS: キューと pub/sub

概要

SQS（Simple Queue Service） はキューです。producer が message を送り、consumer が 取りに行き（poll）、処理してから 削除 します。各 message は 1 つの consumer が処理します。decouple と バッファ のために使います。フロントエンドは注文を素早く受け付け、バックエンドは自分のペースで処理し、downstream が落ちても message は残って待ちます。SNS（Simple Notification Service） は pub/sub です。publisher が topic に送ると、SNS はすべての subscriber へ即座に プッシュ（push）し、保存はしません。1 つのイベントを複数の宛先に fan-out するために使います。

EventBridge: event bus、rule、スケジュール

概要

EventBridge は serverless の event bus です。イベント（JSON）が bus に流れ込み、rule が event pattern で照合して target に送ります。CloudWatch Events の拡張版（同じ API、同じ default bus）で、custom bus、partner bus、schema registry、archive と replay が加わっています。多数の AWS サービス、自社アプリケーション、外部 SaaS の間で イベントを内容に応じてルーティング したいときに EventBridge を選びます。

  • Default bus: AWS サービスのイベントを受け取ります（EC2 の状態変化、CloudTrail または S3 Event Notifications 経由の S3、CodePipeline、Health、GuardDuty の finding など）。Custom bus: 自社アプリケーションが PutEvents するためのもの。Partner bus: Zendesk、Datadog、Auth0、Stripe などの SaaS がイベントを直接アカウントに送ります。
  • Rule: 1 つの bus に複数の rule を置け、各 rule の target は最大 5 個。Target: Lambda、SQS、SNS、Step Functions、Kinesis Data Streams、Firehose、ECS task、Batch、CodeBuild、SSM Run Command、API Gateway、API Destination（認証付きの外部 HTTP endpoint）、別の bus（cross-account、cross-Region）。
  • Event pattern はフィールドで絞り込みます: source、detail-type、detail.state。prefix、numeric、exists、anything-but が使えます。Input transformer で target に送る前に payload を整形します。
  • 配信は at-least-once、最大 24 時間 retry し、配信できなかったイベント用に target ごとの DLQ（SQS）があります。

スケジュールと EventBridge Scheduler
  • Scheduled rule（旧来の方法）: rate(5 minutes) や cron(0 2 * * ? *) で rule を実行して target を呼びます。default bus のみ、時刻は UTC。
  • EventBridge Scheduler（独立した新しいサービス）: 1 回限り または繰り返しのスケジュール、time zone の指定、flexible time window、API 経由で 270 以上のサービスを呼べ、スケジュール数の上限もはるかに高く（数百万）、実行後に自動削除できます。AWS は新しいスケジュールにはすべて Scheduler を推奨しています。問題文に run a task at a specific time、schedule in local time zone、one-time schedule → Scheduler。
  • EC2 上の cron の置き換え: eliminate the EC2 instance that only runs cron jobs → EventBridge Scheduler + Lambda。
Archive、replay、schema、Pipes
  • Archive: pattern に一致するイベントを N 日間または無期限に保存します。Replay: 指定期間のイベントを bus に再送し、バグ修正後の再処理や新しい consumer への投入に使います。SNS と SQS にはこの機能はありません。
  • Schema registry: イベントの構造を保存します。schema discovery が bus 上のイベントから自動で推定し、code binding（Java、Python、TypeScript）を生成するので、開発者は型を使えます。

  • Cross-account: アカウント B の bus の resource policy で、アカウント A（または aws:PrincipalOrgID で Organization 全体）に PutEvents を許可し、アカウント A は B の bus を target とする rule を作ります。複数アカウント向けの「central event bus」パターンです。

19. ECS Fargate 上の service は動いていますが、DynamoDB への書き込みはすべて AccessDenied になります。コンテナのイメージ pull とログ出力は正常です。どこを直しますか。

20. ある会社では 40 個のマイクロサービスが 24 時間 365 日、CPU 70% で安定して動いており、Compute Savings Plans も購入済みです。コンテナのコストを下げたい場合、ECS on EC2 と Fargate のどちらですか。

ECS on EC2（大きなインスタンスに多数の task を詰めて高密度を活かし、EC2 の Reserved があればさらに安い）。Fargate は変動する負荷や、ホストを管理したくないチームに向いています。安定して密な負荷では通常 EC2 のほうが安くなります。（Compute Savings Plans は両方に適用されるので、決め手にはなりません。）

21. Kubernetes の経験がないチームが、load balancer の背後でコンテナの Web API を動かし、リクエスト量に応じて自動スケールさせたいと考えています。least operational overhead で選ぶなら？

AWS App Runner（選択肢に App Runner がなければ ECS Fargate + ALB）。App Runner はビルド、HTTPS、LB、スケールを自動で行います。EKS は不要な Kubernetes の複雑さを持ち込みます。

22. オンプレミスの Java アプリケーションが JMS プロトコルで ActiveMQ を使っており、2 週間以内にコードを変えずに AWS へ移す必要があります。何を選びますか。

Amazon MQ（ActiveMQ エンジン）。 SQS / SNS ではコードを AWS の API に変更する必要があります。問題文が new application の場合に SQS / SNS を選びます。

Lab 1. CRUD API: API Gateway HTTP API + Lambda（Python）+ DynamoDB

  1. partition key id の on-demand の DynamoDB テーブルを作成します:

  2. Lambda の execution role を作成します。ファイル trust.json:

    { "Version": "2012-10-17", "Statement": [{ "Effect": "Allow",
  "Principal": { "Service": "lambda.amazonaws.com" }, "Action": "sts:AssumeRole" }] }

    ファイル ddb-policy.json（このテーブルのみ。Lambda 版の task role にあたります）:

    { "Version": "2012-10-17", "Statement": [{ "Effect": "Allow",
  "Action": ["dynamodb:GetItem","dynamodb:PutItem","dynamodb:DeleteItem","dynamodb:Scan"],
  "Resource": "arn:aws:dynamodb:ap-northeast-1:<account-id>:table/saa-items" }] }

  3. lambda_function.py を書きます。関数は HTTP API の event（payload v2）を受け取り、method と path で分岐し、statusCode と body を持つオブジェクトを返します（Lambda proxy integration）:

    import json, os, boto3
table = boto3.resource("dynamodb").Table(os.environ["TABLE"])

def lambda_handler(event, context):
    method = event["requestContext"]["http"]["method"]
    path = event.get("rawPath", "/")
    parts = [p for p in path.split("/") if p]      # ["items"] または ["items","1"]
    item_id = parts[1] if len(parts) > 1 else None
    try:
        if method == "GET" and item_id:
            r = table.get_item(Key={"id": item_id})
            body, code = r.get("Item", {}), 200 if "Item" in r else 404
        elif method == "GET":
            body, code = table.scan(Limit=50).get("Items", []), 200
        elif method == "PUT":
            data = json.loads(event.get("body") or "{}")
            table.put_item(Item=data)
            body, code = {"ok": True, "id": data.get("id")}, 200
        elif method == "DELETE" and item_id:
            table.delete_item(Key={"id": item_id})
            body, code = {"deleted": item_id}, 200
        else:
            body, code = {"error": "unsupported route"}, 400
    except Exception as e:
        body, code = {"error": str(e)}, 500
    return {"statusCode": code, "headers": {"content-type": "application/json"},
            "body": json.dumps(body, default=str)}

    注意: DynamoDB の数値は Decimal 型で返るため、json.dumps がエラーにならないよう default=str を指定しています。

  4. パッケージして function を作成します（Python 3.12、memory 256 MB、timeout 10 秒）。「role cannot be assumed」エラーが出たら、IAM role の反映を数秒待ちます:

    Compress-Archive -Path .\lambda_function.py -DestinationPath .\function.zip -Force
aws lambda create-function --function-name saa-items-api --runtime python3.12 `
  --handler lambda_function.lambda_handler --zip-file fileb://function.zip `
  --role arn:aws:iam::<account-id>:role/saa-items-lambda-role `
  --memory-size 256 --timeout 10 --environment "Variables={TABLE=saa-items}"

    API を通さず直接テストします（synchronous の RequestResponse 呼び出し）:

    aws apigatewayv2 create-api --name saa-items-http --protocol-type HTTP `

curl.exe -s "$API/items"

curl.exe -s -i "$API/items/1"     # 期待値: HTTP 404

Lab 2. SNS から 2 つの SQS キューへの fan-out、DLQ、filter policy

  1. topic と 3 つのキュー（受信用 2 つ、DLQ 1 つ）を作成します:

    aws sns create-topic --name saa-orders
aws sqs create-queue --queue-name saa-orders-email
aws sqs create-queue --queue-name saa-orders-analytics
aws sqs create-queue --queue-name saa-orders-dlq
# URL と ARN を取得して控えておく
aws sqs get-queue-attributes --queue-url <url-analytics> --attribute-names QueueArn

  2. analytics キューに maxReceiveCount = 3 の DLQ を設定し、実験を速くするため visibility timeout を 5 秒に下げます。ファイル redrive.json（RedrivePolicy の値はネストした JSON 文字列なのでエスケープが必要）:

    {
  "VisibilityTimeout": "5",
  "RedrivePolicy": "{\"deadLetterTargetArn\":\"arn:aws:sqs:ap-northeast-1:<account-id>:saa-orders-dlq\",\"maxReceiveCount\":\"3\"}"
}
    aws sqs set-queue-attributes --queue-url <url-analytics> --attributes file://redrive.json

  3. SNS が 2 つのキューに送れるよう許可します（キューの access policy。最も忘れやすい手順）。ファイル qpolicy-email.json、analytics も同様に作ります:

    {
  "Policy": "{\"Version\":\"2012-10-17\",\"Statement\":[{\"Effect\":\"Allow\",\"Principal\":{\"Service\":\"sns.amazonaws.com\"},\"Action\":\"sqs:SendMessage\",\"Resource\":\"arn:aws:sqs:ap-northeast-1:<account-id>:saa-orders-email\",\"Condition\":{\"ArnEquals\":{\"aws:SourceArn\":\"arn:aws:sns:ap-northeast-1:<account-id>:saa-orders\"}}}]}"
}
    aws sqs set-queue-attributes --queue-url <url-email> --attributes file://qpolicy-email.json
aws sqs set-queue-attributes --queue-url <url-analytics> --attributes file://qpolicy-analytics.json

  4. 2 つのキューを topic に subscribe し、キュー内の message が元の body になるよう raw message delivery を有効にします:

    aws sns subscribe --topic-arn arn:aws:sns:ap-northeast-1:<account-id>:saa-orders `
  --protocol sqs --notification-endpoint arn:aws:sqs:ap-northeast-1:<account-id>:saa-orders-email `
  --attributes RawMessageDelivery=true --return-subscription-arn
aws sns subscribe --topic-arn arn:aws:sns:ap-northeast-1:<account-id>:saa-orders `
  --protocol sqs --notification-endpoint arn:aws:sqs:ap-northeast-1:<account-id>:saa-orders-analytics `
  --attributes RawMessageDelivery=true --return-subscription-arn

  5. attribute type=normal の message を publish し、10 秒の long polling で両方のキューから受信します:

    aws sns publish --topic-arn arn:aws:sns:ap-northeast-1:<account-id>:saa-orders `
  --message '{\"orderId\":101,\"total\":40}' `
  --message-attributes '{\"type\":{\"DataType\":\"String\",\"StringValue\":\"normal\"}}'
aws sqs receive-message --queue-url <url-email> --wait-time-seconds 10
aws sqs receive-message --queue-url <url-analytics> --wait-time-seconds 10

    両方のキューに message があれば、それが fan-out です。キューが空なら、手順 3 の access policy を見直します（Console → SNS → Subscriptions → Status 列が Confirmed になっている必要があります）。

  6. email の subscription に、type=vip だけを受け取る filter policy を追加します:

    aws sns set-subscription-attributes --subscription-arn <arn-sub-email> `
  --attribute-name FilterPolicy --attribute-value '{\"type\":[\"vip\"]}'

    さらに 2 件の message を publish します。type=vip（orderId 102）と type=normal（orderId 103）です。受信し直すと、email キューには 102 だけ、analytics キューには 102 と 103 の両方があります。読んだ message は aws sqs delete-message --receipt-handle か Console → Purge で削除します。

  7. DLQ の実験: 新しい message を publish し、analytics キューで receive-message を delete せずに、5 秒以上の間隔をあけて 4 回続けて 実行します。1〜3 回目は message が見え、4 回目は空です。DLQ を確認します:

    aws sqs get-queue-attributes --queue-url <url-dlq> --attribute-names ApproximateNumberOfMessages

    maxReceiveCount = 3 を超えて受信されたため、message は DLQ に移っています。Console → SQS → saa-orders-dlq → Start DLQ redrive で元のキューに戻せます。これが試験でいう「redrive」です。

  8. Console で振り返ります: SNS topic → Subscriptions タブで filter policy を確認。SQS キュー → Monitoring で NumberOfMessagesSent、ApproximateAgeOfOldestMessage（consumer の停止を警告するのによく使うメトリクス）を確認します。

SQS と SNS は毎月 100万リクエストが無料なので、このラボは 0 USD です。キューと topic は放置しても費用はかかりませんが、アカウントをきれいに保つため Lab 5 で削除します。

資料を見ずに自分で説明できるようにする 2 つの問い

1. SQS、SNS、EventBridge、Kinesis はそれぞれいつ使うか？

回答の骨組みのヒント（隠してから自分で言ってみる）:

  • SQS: キュー、consumer が pull、各 message は 1 つ の consumer が処理して削除。decouple と バッファ（Web 層 → キュー → worker）に使う。Standard: 無制限、at-least-once。FIFO: 順序 + exactly-once、300/3,000 msg/s。visibility timeout、DLQ、long polling を覚えておく。
  • SNS: pub/sub、複数 の subscriber へ即座に push、保存しない。fan-out（SNS → 複数の SQS）と 人 への送信（email、SMS、push）に使う。絞り込みは filter policy。
  • EventBridge: event bus、rule が 内容でルーティング。ソースは AWS サービス、SaaS partner、自社アプリ。スケジュール、archive / replay、schema registry がある。複数サービス間の event-driven な統合とスケジュール実行に使う。
  • Kinesis: MB/s 規模の リアルタイムストリーミング、データは shard に 24 時間〜365 日保持、複数の consumer が同じデータを読む、replay、partition key ごとの順序。S3 / Redshift / OpenSearch にほぼリアルタイムで流し込むだけなら Firehose。
  • それぞれ例を 1 つ挙げられること: 注文を SQS に入れて worker が処理。注文の通知を SNS で在庫 + 請求 + email に送る。EC2 の terminate で EventBridge がチケットを作る。clickstream を Kinesis で 1 分単位に分析。

2. ECS on EC2 と Fargate の違いは？

回答の骨組みのヒント:

  • どちらも同じ ECS（cluster、task definition、service）で、違いは ホストを誰が管理するか。EC2 は利用者（instance type、AMI、OS パッチ、ECS agent、ASG）。Fargate は AWS で、利用者は task の vCPU / memory を宣言するだけ。
  • 課金: EC2 は稼働中のインスタンス単位（空き容量にも払う、RI / Spot が使える）。Fargate は task ごとの vCPU と memory で秒単位。
  • EC2 を選ぶ場面: GPU、安定した負荷を高密度にして安くする、ホスト / docker daemon へのアクセスが必要、bridge / host の network mode、既存の RI。Fargate を選ぶ場面: serverless、least operational overhead、変動する負荷、小さな service が多い、task ごとに独自 ENI で分離（awsvpc 必須）。
  • スケール: EC2 は 2 層（task とインスタンス、capacity provider の managed scaling が必要）。Fargate は task の 1 層のみ。
  • 説明できること: どちらの launch type でも、task role（アプリケーション）と task execution role（ECR からの pull、ログ出力）は別物。
