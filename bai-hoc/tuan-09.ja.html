Disaster recovery: RPO、RTO と4つの戦略

概要
  • RPO (Recovery Point Objective): どれだけのデータ損失を許容するかを、直近の backup 時点までさかのぼる時間で表したものです。例: 毎晩午前2時に snapshot を取り、14時に障害が起きた → 12時間分のデータを失う、RPO = 12時間。RPO 1時間にしたければ毎時 backup、RPO 数秒にしたければ継続的な replicate が必要です。
  • RTO (Recovery Time Objective): 障害発生から再稼働までにどれだけの停止を許容するかです。例: AMI から EC2 を再構築し、snapshot から RDS を restore するのに3時間 → RTO = 3時間。RTO 数分にしたければ、DR サイトのインフラをあらかじめ稼働させておく必要があります。
  • この2つの数字は業務側が決め、アーキテクトは両方を満たす最も安い戦略を選びます。RPO と RTO が小さいほど高くなります。これが DR の設問のロジックのすべてです。
  • High Availability との区別: HA（Multi-AZ）は1つの AZ の障害に対応し、自動で、1つの Region 内で完結します。DR は Region 全体の喪失に対応し、通常は別の Region を使い、人がボタンを押す必要があることもあります。

確認クイズ

4. 社内アプリケーションが東京の EC2 と RDS MySQL で稼働しています。Region 障害時、業務側は最大24時間の停止と最大12時間分のデータ損失を許容しており、most cost-effective が求められています。何を選びますか。

Backup and restore: AWS Backup で RDS snapshot と AMI を12時間ごとに取得して大阪へコピーし、必要時に restore して CloudFormation で構築します。「より安全だから」と pilot light を選びがちですが、業務が求めていないのに replica を常時稼働させる費用がかかります。

5. EC サイトは、主 Region が落ちても数分以内に注文受付を継続でき、データ損失は数秒以内、常時コストはできる限り低くしたいと考えています。何を選びますか。

Warm standby: DR Region で縮小版を稼働（小さい min の ASG、Aurora Global Database または RDS replica）、Route 53 failover、障害時に scale out します。pilot light は RTO が数十分（起動して instance の立ち上がりを待つ必要がある）なので誤りです。Multi-site は要件を満たしますが、設問は最低コストと言っています。

6. 自社データセンターに物理サーバーが200台ある企業が、RPO 数秒、RTO 数分で AWS に復旧できるようにしたいと考えています。200台の EC2 を常時稼働させる費用は払いたくありません。何を選びますか。

AWS Elastic Disaster Recovery: agent が安価な staging area（小さい EC2 + EBS）へ継続的に replicate し、drill や障害時にだけ本番 instance を launch します。Application Migration Service も同じ技術を使いますが、目的は完全移行（cutover）であり、長期の replicate や failback は想定していません。

7. 2つの Region の active-active 構成で、ユーザーが自分のいる Region に書き込めるようにするサービスを2つ選んでください。(A) DynamoDB Global Tables、(B) RDS Multi-AZ、(C) Route 53 latency routing と health check、(D) S3 One Zone-IA。

A と C。 RDS Multi-AZ は1つの Region 内だけです（HA であって DR ではない）。S3 One Zone-IA は1つの AZ にあるので要件と正反対です。選択肢に Aurora Global Database があればそれでもよいのですが、書き込みは primary だけ（write forwarding を除く）なので、設問が「両方で書き込む」と強調しているときは DynamoDB Global Tables が最も確実です。

8. ある企業が、データセンターの Windows と Linux のサーバー300台を3か月で EC2 に移行したいと考えています。アプリケーションは修正不可で、app ごとの downtime は15分以内です。何を使いますか。

9. migration の前に、CIO はすべての on-premises サーバーの一覧、実際に使われている CPU と RAM、サーバー間の依存関係図を minimal effort で得たいと考えています。何を選びますか。

10. 設問: on-premises の 20 TB の Oracle Database を Amazon Aurora PostgreSQL に移行する必要があり、切り替えまで移行元は書き込みを受け続けなければなりません。サービスを2つ選んでください。

AWS Schema Conversion Tool と AWS DMS（full load + CDC）。 SCT が schema と PL/SQL code を変換し、DMS がデータを移行してから変更を継続的に取り込みます。20 TB なら Direct Connect や VPN で問題なく、DMS の CDC にはネットワーク接続が必要なので Snowball は不要です。巨大なデータを offline で移す指定があれば DMS と Snowball Edge を組み合わせますが、その場合も SCT は必要です。

11. ある企業が 50 TB の JSON ログを S3 に保存し、Athena で特定の日付を指定して1日数回 query しています。Athena の請求額が大きく増えました。without changing the query tool でコストを下げる方法を2つ選んでください。

JSON を Parquet（圧縮）に変換し、日付で partition する（Glue job を使う）。そのうえで partition に対する WHERE 付きで query します。Redshift への移行を選びがちですが、設問はツールを変えないと言っています。Athena 向けの Reserved 購入というものは存在しません。

12. データチームは S3 上のデータに対して毎晩6時間の Spark job を実行する必要があり、most cost-effective にしつつ、instance が回収されても中間データを失いたくありません。何を選びますか。

core node を On-Demand、task node を Spot にした EMR で、データは S3 上で読み書き（EMRFS）し、job 後に cluster を停止します（transient cluster）。cluster 全体を Spot にするのはひっかけです。core node は HDFS を持っており、失うと job が壊れます。

13. S3 上の data lake が Athena と QuickSight を通じて5つの部門に使われています。要件: 各部門は一部の列だけ見られる、集中管理、least operational overhead。何を選びますか。

Lake Formation で bucket を登録し、Glue Data Catalog のテーブルに対して列単位で権限を付与します。部門ごとに bucket と bucket policy を分けると、データが重複するうえに列単位で制限できません。

標準的な 3-tier アーキテクチャと設問の読み方

概要

SAA の問題の半分以上は、同じアーキテクチャのバリエーションを描いています。web tier（ALB）、app tier（private subnet の Auto Scaling group 内の EC2）、data tier（RDS Multi-AZ、ElastiCache、S3）を Route 53、CloudFront、WAF で外側から包み、SQS でつなぐ構成です。この「標準」の構成図を身につけておけば、各問題は どのコンポーネントが欠けているか、どこに「2」が足りないか、どこで余分なお金を払っているか を探すだけになります。

イメージ: 2つの AZ にまたがる標準的な 3-tier アーキテクチャ

すべての層に「2」があります。2つの AZ、種類ごとに2つの subnet、ALB は自動で2つの AZ に node を持ち、ASG は instance を2つの AZ に分散し、RDS には standby、ElastiCache には replica、NAT Gateway は2つ。CloudFront、Route 53、S3、SQS、CloudWatch だけは、それ自体で HA を備えた Regional または Global のサービスです。

確認クイズ

17. 構成図: 2つの AZ に ALB、2つの private subnet に ASG min 2、AZ 1a に NAT Gateway が1つ、RDS Multi-AZ。AZ 1a が落ちたとき、どんな現象が起き、どう直しますか。

AZ 1c の instance は ALB から traffic を受け続けるが、唯一の NAT が 1a にあるため Internet への接続（外部 API の呼び出し、package のダウンロード）を失う。 修正: 1c に NAT Gateway を追加し、1c の private subnet の route table を 1c の NAT に向ける。「ALB を追加する」を選ぶ人が多いが、ALB はすでに HA です。

18. アプリケーションは設定ファイルに書いた RDS の private IP で database に接続しています。RDS Multi-AZ の failover の後、RDS は稼働しているのに app が接続できません。なぜですか。

failover によって DNS endpoint が別の IP を持つ standby に切り替わったが、app は古い IP を使っている。 RDS の DNS endpoint を使い、app 内の DNS キャッシュの TTL を短くして直します。これは確認ポイント2の「hard-coded IP」のひっかけです。

19. アーキテクチャでは m5.large の On-Demand instance 20台が1年中 24/7 で安定稼働し、それに加えて SQS から画像を処理する worker instance が30台あります。信頼性を下げずに most cost-effective にする方法を2つ選んでください。

ベースの20台には Compute Savings Plans（または Reserved）、SQS を読む30台の worker には Spot。 web 層を Spot にすると回収されて availability が下がるので誤りです。worker の負荷は変動するので、worker に Reserved を使うのは無駄です。

20. 設問の構成図は1つの AZ にある web app です。public な EC2 が1台、同じ public subnet に RDS Single-AZ。最小限の変更で highly available and secure にすることが求められています。必要な作業を挙げてください。

2つ目の AZ に public と private の subnet を追加、ALB を public に置く、EC2 を private subnet の ASG min 2 に入れる、RDS を private subnet に移して Multi-AZ を有効化、RDS の Security Group は EC2 の SG からのみ受け付ける。 よくある誤答: 「read replica を作る」（HA ではない）や「Elastic IP を使う」（instance は1台のまま）。

    import * as cdk from 'aws-cdk-lib';
import * as ec2 from 'aws-cdk-lib/aws-ec2';
import * as elbv2 from 'aws-cdk-lib/aws-elasticloadbalancingv2';
import * as autoscaling from 'aws-cdk-lib/aws-autoscaling';
import * as rds from 'aws-cdk-lib/aws-rds';
import * as s3 from 'aws-cdk-lib/aws-s3';
import * as cloudwatch from 'aws-cdk-lib/aws-cloudwatch';

export class Saa3TierStack extends cdk.Stack {
  constructor(scope: cdk.App, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    // 1. VPC: 2 AZ、3層の subnet。natGateways: 1 は意図的な SPOF で、Lab 4 で直す。
    const vpc = new ec2.Vpc(this, 'Vpc', {
      maxAzs: 2, natGateways: 1,
      subnetConfiguration: [
        { name: 'public', subnetType: ec2.SubnetType.PUBLIC, cidrMask: 24 },
        { name: 'app', subnetType: ec2.SubnetType.PRIVATE_WITH_EGRESS, cidrMask: 24 },
        { name: 'db', subnetType: ec2.SubnetType.PRIVATE_ISOLATED, cidrMask: 24 },
      ],
    });

    // 2. App tier: private subnet の ASG、user data で web server をインストール
    const userData = ec2.UserData.forLinux();
    userData.addCommands(
      'dnf install -y httpd',
      'echo "<h1>SAA 3-tier: $(hostname -f)</h1>" > /var/www/html/index.html',
      'systemctl enable --now httpd');
    const asg = new autoscaling.AutoScalingGroup(this, 'Asg', {
      vpc, vpcSubnets: { subnetType: ec2.SubnetType.PRIVATE_WITH_EGRESS },
      instanceType: ec2.InstanceType.of(ec2.InstanceClass.T3, ec2.InstanceSize.MICRO),
      machineImage: ec2.MachineImage.latestAmazonLinux2023(),
      minCapacity: 2, maxCapacity: 4, userData,
    });
    asg.scaleOnCpuUtilization('Cpu', { targetUtilizationPercent: 60 });

    // 3. Web tier: public subnet の internet-facing ALB（自動で 2 AZ に分散）
    const alb = new elbv2.ApplicationLoadBalancer(this, 'Alb', { vpc, internetFacing: true });
    const listener = alb.addListener('Http', { port: 80 });
    listener.addTargets('Web', { port: 80, targets: [asg], healthCheck: { path: '/' } });

    // 4. Data tier: 最小構成の RDS MySQL Multi-AZ、isolated subnet、削除時に snapshot を残さない
    const db = new rds.DatabaseInstance(this, 'Db', {
      engine: rds.DatabaseInstanceEngine.mysql({ version: rds.MysqlEngineVersion.VER_8_0 }),
      instanceType: ec2.InstanceType.of(ec2.InstanceClass.T3, ec2.InstanceSize.MICRO),
      vpc, vpcSubnets: { subnetType: ec2.SubnetType.PRIVATE_ISOLATED },
      multiAz: true, allocatedStorage: 20,
      removalPolicy: cdk.RemovalPolicy.DESTROY, deleteAutomatedBackups: true,
    });
    db.connections.allowDefaultPortFrom(asg);   // DB の SG は ASG の SG からのみ受け付ける

    // 5. S3: bucket に object が残っていても cdk destroy が止まらないよう autoDeleteObjects
    const bucket = new s3.Bucket(this, 'Assets', {
      removalPolicy: cdk.RemovalPolicy.DESTROY, autoDeleteObjects: true,
    });
    bucket.grantRead(asg);

    // 6. CloudWatch alarm: ALB の 5xx が2分連続で5回を超えたら
    new cloudwatch.Alarm(this, 'Alb5xx', {
      metric: alb.metrics.httpCodeElb(elbv2.HttpCodeElb.ELB_5XX_COUNT,
        { period: cdk.Duration.minutes(1) }),
      threshold: 5, evaluationPeriods: 2,
    });

    new cdk.CfnOutput(this, 'AlbDns', { value: alb.loadBalancerDnsName });
  }
}

確認ポイント

資料を見ずに自分で説明できなければならない2つの問い

1. 4つの DR 戦略と対応するコストを説明する

回答の骨組みのヒント（隠してから自分で話してみる）:

  • RPO（どれだけデータを失うか）と RTO（どれだけ停止するか）の定義から始める。2つの数字は業務側が決める。
  • Backup and restore: DR Region には backup だけ。RPO と RTO は時間単位、最も安い。サービス: AWS Backup、S3 CRR、AMI copy、CloudFormation。
  • Pilot light: DB は replicate 済み、compute は停止。RPO 分、RTO 数十分、コストは低い。サービス: RDS cross-Region replica、Elastic Disaster Recovery。
  • Warm standby: 縮小版が稼働していて処理できる。RPO 秒、RTO 分、コストは中程度。サービス: Aurora Global Database、小さい ASG、Route 53 failover。
  • Multi-site active-active: 2つの Region が同時に処理。RPO と RTO はほぼ 0、最も高い。サービス: DynamoDB Global Tables、Route 53 latency または weighted と health check。
  • 選択ルールで締めくくる: 設問の RPO と RTO の両方を満たす中で最も安い戦略を選ぶ。

2. アーキテクチャを見て single point of failure を指摘する

回答の骨組みのヒント:

  • 外側から内側へ読む: DNS → CDN/WAF → load balancer → compute → cache → DB → storage → queue。
  • 各層で「2はあるか」と問う: 2つの AZ、2台の instance（ASG min 2）、2つの NAT Gateway、RDS Multi-AZ、replica を持つ cache、各 AZ の EFS mount target。
  • 典型的な5つの SPOF を挙げられる: NAT が1つ、AZ が1つ、instance が1台、RDS Single-AZ、hard-coded IP。さらに instance 上の session と、サービス間の同期呼び出し。
  • 各 SPOF について、直し方とその代償をすぐに言う: AZ ごとの NAT（時間料金が増える）、Multi-AZ（RDS が2倍）、ASG min 2（instance が1台増える）。
  • 設問が「survive Region failure」を問うときは、HA（Multi-AZ、自動）と DR（Multi-Region、RPO/RTO に基づく）を区別する。
