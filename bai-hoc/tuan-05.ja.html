Elastic Load Balancing: ALB、NLB、Gateway Load Balancer

概要

Load balancerは唯一の入口（DNS name）としてrequestを受け取り、複数AZにある複数のtarget（EC2、IP、Lambda、container）へ振り分けます。1台のinstanceの障害を隠し、private IPを隠し、TLS証明書を取り付ける場所でもあります。ELBはmanagedサービスで、AWSがload balancerのnodeを自動でscaleします。利用者は種類、listener、target group、health checkを選ぶだけです。

  • Application Load Balancer (ALB): layer 7、HTTP/HTTPS、gRPC、WebSocketを理解します。host（api.example.com）、path（/images/*）、query string、HTTP header、method、source IPでroutingします。Target groupはEC2、IP、ECS task、またはLambda functionにできます。Cognito User PoolまたはOIDC（Google、Okta）によるlistener上のauthenticationをサポートし、requestがappに届く前に認証できます。ALBはX-Forwarded-For headerを付与するので、appはclientの本当のIPを知ることができます。security groupを持ちます。
  • Network Load Balancer (NLB): layer 4、TCP/UDP/TLS、毎秒数百万requestを非常に低い遅延で処理します（約100 ms、ALBは約400 ms、要確認）。各AZに1つの静的IPを持ち、自分のElastic IPを割り当てられます。static IPを持つ唯一の種類です。targetがinstanceの場合、clientのsource IPを保持します。PrivateLink（endpoint service）の入口でもあります。NLBのtargetにALBを置けば、静的IPとlayer 7 routingの両方が得られます。2023年以降はNLBもsecurity groupを持ちます（要確認）。
  • Gateway Load Balancer (GWLB): layer 3、GENEVEプロトコルのport 6081を使って全パケットをサードパーティapplianceの群（Palo Alto、Fortinetなどのfirewall、IDS/IPS、deep packet inspection）に通してから戻します。「bump in the wire」として配置し、appからは透過的です。別VPCのGateway Load Balancer endpointと組み合わせて使います。
  • Classic Load Balancer (CLB): 旧世代で、layer 4と7の機能は簡素、target groupは1つ、host/path routingはありません。試験では見分けられれば十分です。選択肢にCLBがあればほぼ常に誤答なので、ALBかNLBを選びます。

1. ある会社のappはALBの背後のEC2で動いています。取引先は自社firewallでappのIPをwhitelistしたいのですが、ALBのIPは変わります。least operational overheadな解決策は?

前段にElastic IP付きのNLBを置き、ALBをNLBのtargetにする。 ALBのpath routingを保ったまま静的IPが得られます。ALBを完全にNLBへ置き換えるとlayer 7のruleを失います。Global Accelerator も2つの静的IPを提供し、設問がグローバルユーザーと言うなら正解ですが、「取引先のwhitelist」ならNLB + EIPで十分で安価です。

2. ALBの背後にあるEC2のSecurity Groupは、most secureにするためどのinbound ruleを持つべきですか?

port 80（または443）をsource = ALBのSecurity Groupで許可する。 0.0.0.0/0を開けるのは誤りで、VPN経由でprivate IPを知る者なら誰でも直接アクセスできてしまいます。public subnetのCIDRを使うのもSG idほど厳密ではなく、そのsubnet内の全マシンが通ってしまいます。

3. NLBにAZ 1aのtargetが2つ、AZ 1cのtargetが6つあり、cross-zoneは無効です。ユーザーから一部のrequestが遅いと苦情があります。原因と対処は?

各NLB nodeは自分のAZのtargetにしか送らないため、1aの2つのtargetがtrafficの50%を負担しています。cross-zone load balancingを有効にする（AZ間data transfer料金を受け入れる）か、instance数を均等にします。ALBではcross-zoneがdefault有効なのでこの問題は起きません。

4. 会社は各VPCを出入りする全trafficをEC2上で動くPalo Altoのfirewallに通し、集中管理し、アプリケーションには透過的にしたいと考えています。どのサービスを選びますか?

各VPCにGateway Load Balancer endpointを置いたGateway Load Balancer。 NLBでも負荷分散はできますが、パケットを正しい場所へ戻すGENEVEがなく、routeの変更が複雑になります。AWS Network FirewallはAWSのmanaged firewallで、サードパーティapplianceは動かしません。

EC2 Auto Scaling

概要

Auto Scaling Group（ASG）はEC2の台数を常にminとmaxの間に保ち、desiredに向けて調整します。故障したinstanceを自動で置き換え（self-healing）、選択したAZにinstanceを均等に配置し、scaling policyに従って台数を増減します。ASG自体は無料で、EC2の料金のみ支払います。ASGがinstanceを作るには機械の設計書が必要で、それがlaunch templateです。

  • Launch templateとlaunch configuration: launch configurationは旧型で不変、変更のたびに新規作成が必要、mixed instance typeとSpotの組み合わせを非対応、2023年からconsoleでの新規作成は停止しています（要確認）。Launch templateはversionを持ち、複数instance type、1つのASG内でのSpot + On-Demandの混在、T2/T3 Unlimited、placement group、dedicated hostをサポートします。試験では常にlaunch templateを選びます。
  • min / desired / max: 例えば2 / 2 / 10。desiredはASGが維持しようとする台数で、scaling policyが[min, max]の範囲内でdesiredを変更します。1つのAZの障害に耐えるには2 AZでmin 2にします。
  • Health check: defaultはEC2 type（instance status check）。ASGがELBの背後にある場合はELB typeも有効にして、OSは生きているがappが固まったinstanceも置き換えるようにします。unhealthyなinstanceはterminateして新規作成され、修理はされません。
  • AZ rebalance: あるAZのinstanceが多い場合（別のAZが一時的に故障したなど）、ASGは少ないAZで先にinstanceを作ってから多いAZでterminateするため、一時的にdesiredを最大10%超えることがあります。
  • scale in時のdefault termination policy: instanceが最も多いAZ → 最も古いlaunch templateを使うinstance → 次の課金時刻に最も近いinstance の順で選びます。OldestInstance、NewestInstanceに変更したり、長いjobを処理中のinstanceにscale-in protectionを付けたりできます。

Route 53: DNS、routing policy、health check

概要

Route 53はAWSのmanaged DNSで、globalサービス、SLA 100%です。3つの役割があります: domain登録（registrar）、DNS queryに応答するrecordを保持するhosted zone、endpointの障害時に応答を切り替えるhealth check。名前の「53」はDNSのport番号です。

  • Public hosted zone: Internetに応答します（example.com）。Private hosted zone: 関連付けたVPC内からのqueryにのみ応答します（db.internal）。VPCでenableDnsHostnamesとenableDnsSupportを有効にする必要があります。hosted zoneは1つにつき月額約0.50 USD（要確認）。
  • Record type: A（名前 → IPv4）、AAAA（名前 → IPv6）、CNAME（名前 → 別の名前、example.comのようなapexでは使えない）、NS（zoneのname server、Route 53は4つ割り当て）、SOA（zone情報）、MX、TXT（domain検証、SPF）、SRV、PTR。
  • Alias record: Route 53独自の拡張で、名前をAWS resource（ALB、NLB、CloudFront、API Gateway、S3 website endpoint、Elastic Beanstalk、Global Accelerator、同じzone内の別record）へ向けます。利点: apex domainで使える、queryが無料、resourceのIPが変わっても自動で追従、Evaluate target healthを有効にできる。欠点: EC2のDNS nameやAWS外のDNSには向けられない、TTLを設定できない（resourceのTTLを使う）。
  • TTL: resolverが応答をcacheする時間。TTLが長い（24時間）とquery料金は減りますがIP変更に時間がかかり、TTLが短い（60秒）と変更は速いですが料金は増えます。移行前には数日前からTTLを下げ、それからrecordを変更します。
  • Domain registration: Route 53でdomainを購入でき、hosted zoneが自動で作られます。GoDaddyで購入したdomainでも、registrar側のNSをhosted zoneの4つのNSに変更すればRoute 53をDNSとして使えます。逆にRoute 53で購入したdomainのNSを別のDNSへ向けることもできます。

CloudFront: Edge locationのCDN

概要

CloudFrontはAWSのCDNです。distributionはd123.cloudfront.net形式のDNS nameを持ち、ユーザーに近いEdge location（600か所以上、要確認）でrequestを受け、cacheにあればそこから返し、なければoriginから取得してcacheします。利点: 遅延の削減、originの負荷とdata transfer費用の削減、Shield Standardによるlayer 3/4のDDoS防御、layer 7向けのWAF取り付け。globalサービスで、設定はus-east-1で行います。

  • Origin: S3 bucket（最も一般的。S3 static website endpointも使えるが、その場合はcustom originとして扱う）、ALB、public IPを持つEC2、API Gateway、MediaStore、任意のHTTP server（custom origin、on-premisesも含む）。1つのdistributionに複数のoriginを持て、cache behaviorのpath patternでoriginを選びます（/api/* → ALB、/* → S3）。
  • Origin group: primaryとsecondaryのorigin。primaryが500/502/503/504、または403/404（任意）を返すと、CloudFrontが自動でsecondaryへ切り替えます。2つのRegionにある2つのbucket間のorigin failoverに使います（S3 Cross-Region Replicationと組み合わせる）。
  • Cache behavior: 1つのpath patternに対する規則です。どのorigin、viewer protocol（HTTP → HTTPSへredirect）、許可するmethod（GET/HEADかPUT/POSTも含むか）、cache policy、origin request policy、signed URLが必要か、どのfunctionを紐付けるか。
  • TTL: originがCache-Control: max-ageを送ればCloudFrontはそれに従います（cache policyのmin/max TTLの範囲内）。headerがなければdefault TTL（24時間）を使います。すぐにcacheを破棄したい場合: invalidation（/images/*、月1000 pathを超えると課金）か、versionを含むファイル名に変更（app.v2.js、推奨される方法）。

  • Cache policyはcache keyを決めます: URLに加えてどのheader、cookie、query stringを含めるか。cache keyの要素が多いほどcache hitは減ります。静的コンテンツにはmanaged policy CachingOptimized、動的APIにはCachingDisabledを使います。

  • Response headers policy: CORSやsecurity header（HSTS、CSP）をEdgeで付与します。

  • Lambda@Edge: Regional Edge Cacheで動くLambda（Node.js、Python）で、最大5秒（viewer）または30秒（origin）、viewer request、origin request、origin response、viewer responseの4つのポイントがあります。他サービスの呼び出しやbodyの読み取りが可能です。us-east-1で作成してからreplicateされます。
  • 選び方: 軽い処理、高頻度 → CloudFront Functions。network呼び出し、bodyの操作、origin request/responseが必要 → Lambda@Edge。

  • S3 / EC2からCloudFrontへのdata transferは無料です。CloudFrontからユーザーへは課金されますが、S3からInternetへ直接出すより安価です。cacheが不要でも、egress料金の削減とDDoS対策のためだけにS3の前にCloudFrontを置く価値があります。
  • HTTP/2、HTTP/3（QUIC）、IPv6、WebSocket、gRPCをサポートします。動的コンテンツ（API）にもTTL 0で使い、EdgeからoriginまでのAWS backboneネットワークを活用できます。

Global AcceleratorとCloudFrontの比較

概要

AWS Global Accelerator（GA）はアプリケーションに、全Edge locationから広告される2つの静的anycast IPアドレスを割り当てます。ユーザーは最寄りのEdgeに接続し、その後trafficはAWSのbackboneネットワーク（公衆Internetを経由しない）を通ってRegionのendpoint（ALB、NLB、EC2、Elastic IP）へ届きます。GAはcacheせず、HTTPも理解せず、TCP/UDPパケットをより速く安定して運ぶだけです。

  • Accelerator → listener（port、TCP/UDP） → Regionごとのendpoint group（Regionの比率調整や無効化のためのtraffic dial 0〜100%） → weight付きのendpoint。health checkは常時行われ、endpointが故障すると約30秒未満〜1分で切り替わり、clientのDNS TTLに依存しません（秒数は要確認）。
  • IPが変わらないので、顧客は一度whitelistすれば済みます。自分のIPを持ち込むこと（BYOIP）もできます。2つのIPは独立した2つのnetwork zoneに属し、片方が落ちてもclientはもう片方を使います。
  • Client IP preservation: ALBとEC2のendpointでは、GAはclientの本当のIPを保持します。NLBでは設定次第です（要確認）。
  • Shield Standardと統合されています。料金: 時間あたりの固定料金 + 通過したGBあたりの料金で、静的コンテンツではCloudFrontより高くなります。
  • 向いている用途: gaming（UDP）、VoIP、IoT（TCP上のMQTT）、動的コンテンツのAPI、複数Region間のdeterministic failoverが必要なアプリケーション、HTTP以外のアプリケーション。

Route 53 latency / failoverとの比較
  • Route 53はDNSに応答するだけです。clientやISPがTTLに従って応答をcacheするので、実際のfailoverには数分かかることがあります。GAはネットワーク層で切り替えるので、client側は何もする必要がありません。
  • Route 53 latency routingははるかに安価で、通常のwebには十分です。GAが費用に見合うのは、設問がminimize failover time、static IP、UDPを強調するときです。
  • 設問がDNS caching causes slow failoverと言う → Global Accelerator。

17. UDPを使うモバイルgameで、serverはTokyoとFrankfurtのNLBの背後にあります。プレイヤーから遅延と、片方のRegionのメンテナンス時のカクつきについて苦情があります。解決策は?

18. Global AcceleratorではなくCloudFrontを使う理由を2つ選んでください: (A) 画像と動画をcacheしたい、(B) 静的IPが必要、(C) 有料コンテンツにsigned URLが必要、(D) UDPが必要。

AとC。 Cacheとsigned URL/cookieはCloudFrontの機能です。BとDはGlobal Acceleratorを選ぶ理由です。

19. 2つのRegionにあるHTTPSアプリケーションで、各RegionにALBが1つあります。要件: clientは1つの固定アドレスを使い、片方のRegionが落ちたら1分未満でもう片方へ切り替える。何を選びますか?

2つのendpoint groupを持ち、それぞれがそのRegionのALBを指すGlobal Accelerator。 Route 53 failoverは名前としての固定アドレスを提供しますが、切り替え時間はTTLとresolverのcacheに依存し、通常1分を超えます。origin group付きのCloudFrontもfailoverしますが、静的IPがありません。

Lab 2. stress-ngで負荷試験、ASGのscale outとscale inを観察

  1. Session Managerでinstanceに入ります（EC2 → instanceを選択 → Connect → Session Manager。Lab 1のSSM roleが必要、bastionやport 22の開放は不要）。CPU 100%の負荷を10分間かけます:

    sudo stress-ng --cpu 2 --timeout 600s &
top    # CPUがほぼ100%になる、qで終了

    stress-ngが未インストールの場合（user dataのエラー）: sudo dnf install -y stress-ng。

  2. 2台目のinstanceでも同様に行い、ASGの平均CPUが50%を超えるようにします（target trackingはgroup全体の平均で計算するので、1台100%で1台0%なら50%にしかなりません）。

  3. CloudWatchを確認します: CloudWatch → AlarmsにTargetTracking-saa-web-asg-AlarmHigh-...とAlarmLow-...という名前の自動作成されたalarmが2つあります。AlarmHighは50%超のdatapointが3つ連続（各datapoint 1分）してはじめてIn alarmになります。CLIで追うこともできます:

    aws cloudwatch get-metric-statistics --namespace AWS/EC2 --metric-name CPUUtilization --dimensions Name=AutoScalingGroupName,Value=saa-web-asg --start-time (Get-Date).AddMinutes(-15).ToUniversalTime().ToString("yyyy-MM-ddTHH:mm:ssZ") --end-time (Get-Date).ToUniversalTime().ToString("yyyy-MM-ddTHH:mm:ssZ") --period 60 --statistics Average --query "Datapoints[].[Timestamp,Average]" --output table

  4. 約3〜5分後、ASGのActivityタブに「Launching a new EC2 instance ... in response to alarm AlarmHigh」が表示されます。Desiredが2から3または4に増えます。新しいinstanceがPending → InServiceと進み、120秒のwarm-up中はmetricに含まれないことを観察します。

    aws autoscaling describe-scaling-activities --auto-scaling-group-name saa-web-asg --max-items 5 --query "Activities[].[StartTime,StatusCode,Cause]" --output table

  5. stress-ngが600秒で終わるとCPUはほぼ0に戻ります。性急なscale inを避けるため、AlarmLowは閾値を下回るdatapointが15個連続（約15分）する必要があります。その後ASGはdefault termination policy（instanceの多いAZを優先）に従ってinstanceをterminateし、desired 2に戻します。ActivityとInstance managementを再確認します。

  6. ノートに記録します: 負荷開始から新しいinstanceがhealthyになるまでの時間（通常4〜7分）、負荷終了からscale inまでの時間（約15分）。これが試験でscale out fast, scale in slowと言われる理由であり、warm poolやpredictive scalingが存在する理由です。

scale outが見られない場合: ASGのmaxがdesiredより大きいか、平均CPUが本当に50%を超えているか（2台ともstressを実行）、alarmがIn alarm状態になっているかを確認します。Target trackingは3分のalarmを使うので即座には反応しません。

Lab 3. health check付きRoute 53 failover

このlabには2つの方法があります。方法AはRoute 53で管理しているdomainが必要です（Route 53で.comを購入すると年額約13 USD、または既存domainのNSをRoute 53へ向ける）。方法Bはdomain不要で、health checkを作って状態の変化を観察するだけです。仕組みの理解には十分ですが、DNSの切り替えは見られません。domainがなければ方法Bを行い、checklistにその旨を明記します。

  1. 2つのpublicなendpointを用意します: primaryはLab 1のALBのDNS name。secondaryはstatic website hostingを有効にしたS3 bucketで、「Site under maintenance」と書いたindex.htmlを置きます（方法Aではbucket名をrecord名と同じにする必要があります。例: www.example.com。方法Bでは任意の名前）。bucketはBlock Public Accessを無効にし、public なs3:GetObjectを許可するbucket policyを設定します。publicが許される数少ない例外です。

  2. primary用のhealth checkを作成します: Route 53 → Health checks → Create。Name saa-alb-hc、Monitor an endpoint、Specify endpoint by Domain name、protocol HTTP、domainはALBのDNS name、port 80、path /。Advanced: labで速く切り替わるようRequest interval Fast (10 seconds)、Failure threshold 2。emailで通知を受けたければSNS alarmも作成します。1〜2分待つと状態がHealthyになり、Health checkersタブで世界各地のcheckerがそれぞれOKを報告しているのが見えます。

  3. 方法A（domainあり）: hosted zoneで、record www type A、routing policy Failover、Failover record type Primary、Alias → Application Load Balancer → saa-albを選択、Health check saa-alb-hc（またはEvaluate target healthを有効化）、Record ID primaryで作成します。2つ目のwww recordをFailover Secondary、Alias → S3 website endpoint → bucketを選択、Record ID secondaryで作成します。http://www.example.comを開くとALBからのページが表示されます。

    nslookup www.example.com 8.8.8.8    # ALBのIP
Resolve-DnsName www.example.com -Server 8.8.8.8 -Type A

  4. primaryを故障させます: 最も速いのはsaa-alb-sgからinbound 80のruleを削除する（health checkerが遮断される）か、ALBにtargetがなくなるようASGのdesired/minを0にすることです。instanceを手動でterminateしてはいけません。ASGが1分以内に作り直してしまいます。

    aws ec2 revoke-security-group-ingress --group-id $ALBSG --protocol tcp --port 80 --cidr 0.0.0.0/0

  5. 20〜40秒後、health checkがUnhealthyになります。方法A: nslookupを再実行すると応答がS3 websiteのIPに変わり、ブラウザで開き直すと「Site under maintenance」が表示されます（aliasのTTL 60秒を待ち、ipconfig /flushdnsでDNS cacheを消す必要があるかもしれません）。方法B: health checkの状態と切り替え時間だけを観察して秒数を記録し、方法Aの説明をよく読んでDNSの切り替えをイメージします。

  6. 復旧: saa-alb-sgにrule 80を戻します（またはdesiredを2に戻す）。health checkがHealthyに戻り、DNSもprimaryに戻ります。Route 53はprimaryがhealthyなら常にprimaryを優先し、「手動failback」はありません。

  7. 追加の実験: ASGのAlarmHigh alarmに紐付けたCloudWatch alarmタイプのhealth checkを作成し、privateなresourceの確認方法を体験します。その後、使わないhealth checkは削除します（1つあたり月額約0.50〜1 USD、要確認）。

終わったらhealth checkと試験用のrecordを削除します。手順1のpublic bucketはlab専用で、Lab 5で削除します。domainを購入した場合は残しておいて構いません。domainはhosted zoneの月額0.50 USD以外に追加費用はかかりません。

Lab 4. OACでprivate S3の前にCloudFront、S3への直接アクセスは403になること

  1. private bucketを作成し（Block Public Accessは有効のまま、static website hostingは有効にしない）、ファイルを1つuploadします:

  2. Console → CloudFront → Create distribution。Origin domain: bucketを選択（saa-cf-quy-2026.s3.ap-northeast-1.amazonaws.com形式、website endpointは選ばない）。Origin access: Origin access control settings (recommended) → Create new OAC、defaultのSign requestsのまま。Viewer protocol policy: Redirect HTTP to HTTPS。Cache policy: CachingOptimized。WAF: 費用を避けるため無効。Default root object: index.html。Price class: price classの効果を見たければUse only North America and Europe（Tokyoからは少し遅くなる）、またはAll。Create。

    {
  "Version": "2008-10-17",
  "Statement": [{
    "Sid": "AllowCloudFrontServicePrincipalReadOnly",
    "Effect": "Allow",
    "Principal": { "Service": "cloudfront.amazonaws.com" },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::saa-cf-quy-2026/*",

    S3 → bucket → Permissions → Bucket policyに貼り付けます。注目点: principalはCloudFrontサービス、conditionで1つのdistributionだけに限定、bucketはBlock Public Accessのまま。

第5週の3問と第4週の3問を自分の言葉で説明できること

AWS-SAA-checklist.mdの確認ポイントは第4〜5週のブロック全体で共通です。最初の3つが今週のもの、後の3つは第4週の振り返りで、quizの前に6つすべてを説明できる必要があります。

1. requestの流れ: ユーザー → Route 53 → CloudFront → ALB → ASG → EC2 private

回答の骨組みのヒント（隠してから自分で説明する）:

  • ブラウザがwww.example.comをDNSに問い合わせ、resolverがRoute 53のNSに到達し、alias recordが最寄りのCloudFront EdgeのIPを返します（latency / failover policyを経由することもある）。
  • clientはACM us-east-1の証明書でEdgeとTLS handshakeを行い、CloudFrontはcache keyでcacheを検索し、hitならすぐに返します。
  • Miss: CloudFrontはcustom headerを付けてAWS backbone経由でorigin ALB（public subnetのInternet-facing）へ向かいます。ALBのSGはCloudFrontのprefix listのみ許可します。
  • ALB listener 443がhost/pathのruleを評価してtarget groupを選び、healthyなtargetにのみ送ります。EC2のSGはALBのSGからのみ許可します。
  • private subnetのEC2はASGが2 AZでmin 2を維持し、target trackingでscaleします。public IPはなく、Internetへの出口はNAT Gateway（第4週）です。
  • responseは逆の経路をたどり、CloudFrontがTTLに従ってcacheしてclientに返します。各レイヤーの耐障害性のポイントを1つずつ挙げられること: Route 53 health check、origin group、multi-AZ ALB、ASG self-healing。

2. 状況に応じてRoute 53のrouting policyを正しく選ぶ

回答の骨組みのヒント:

  • 2つの問いを立てます: 設問が気にしているのは比率、性能、位置、冗長化のどれか?
  • 比率（canary、blue/green、A/B） → weighted。複数Regionでのグローバルな性能 → latency。
  • ユーザーの位置（法律、言語） → geolocation。resourceの位置 + biasでtrafficを寄せる → geoproximity。
  • Active-passive、DR、メンテナンスページ → failover。ELBなしで複数のhealthyなIP → multi-value。サーバー1台 → simple。
  • 併せて覚える: apexとAWS resourceにはalias、private resourceのhealth checkはCloudWatch alarm、ELBにはEvaluate target health。

3. 設問のキーワードからALB、NLB、Global Acceleratorを選ぶ

回答の骨組みのヒント:

  • HTTP、path/host routing、microservices、Lambda target、Cognito、WebSocketが見えたら → ALB。
  • 1つのRegion内のstatic IP、TCP/UDP、millions of requests、PrivateLink、preserve source IPが見えたら → NLB。
  • global users + static anycast IP、UDP gaming / VoIP、fast failover between Regions、non-HTTPが見えたら → Global Accelerator（ALB/NLBの前に置くもので、置き換えではない）。
  • cache、static content、S3、signed URLが見えたら → GAではなくCloudFront。third-party applianceが見えたら → GWLB。
  • 組み合わせ: 静的IPとlayer 7の両方が必要ならNLB → ALB。複数RegionならGA → ALB。

第4週の振り返り: VPCの図、Internetへ出るパケット、SGとNACL

checklistにある第4週の3つの確認ポイントを短く振り返ります:

  • 紙にVPCを描く: CIDR、2 AZ、各AZにpublicとprivateのsubnetを1つずつ、VPCに付けたIGW、public subnetのNAT Gateway、publicのroute table（0.0.0.0/0 → IGW）とprivateのroute table（0.0.0.0/0 → NAT）、S3のgateway endpoint。今週はpublic subnetにALB、private subnetにASGが加わります。
  • private EC2からInternetへ出るパケット: EC2 → privateのroute table → NAT Gateway（source IPをNATのEIPに変換） → publicのroute table → IGW → Internet。戻りは変換テーブルによりNATを通ります。IPv6ならEgress-only IGWを使います。
  • SGとNACL: SGはENIに付き、stateful、Allowのみ、全ruleを評価。NACLはsubnetに付き、stateless（戻りのephemeral portも開ける必要がある）、Denyあり、番号順に評価。例: 攻撃元IPを1つブロック → NACL Deny。ALBからEC2への通信を許可 → SGのsourceをALBのSGにする。
