S3 の基本と storage class

概要
  • Object storage: S3 は object（データ + metadata）を bucket に保存し、key で識別します。Key は logs/2026/10/app.log のようなフラットな文字列で、/ は名前の一部の文字にすぎません。Console は見やすさのために「フォルダ」として描画しますが、実際のディレクトリはありません。ディスクのようにマウントできず、object の一部だけを書き換えることもできません。内容を変えたいときは object 全体を再アップロードします。
  • Bucket: 名前は全世界で一意、3〜63文字の小文字、1つの Region 内に存在します（データが勝手に Region の外へ出ることはありません）。デフォルトは1アカウントあたり 100 bucket で、引き上げ申請ができます（現在の上限は要確認）。Bucket は Region レベルのリソースですが、S3 Console には全 Region の bucket が表示されます。
  • Object: 最大 5 TB。1回の PUT は通常最大 5 GB で、5 GB を超える場合は multipart upload が必須です（項目4）。Object 数と容量に上限はなく、事前の申告も不要です。
  • Durability はすべての storage class で 99.999999999%（11 nines）: データは複数の AZ に冗長化して書き込まれます（One Zone-IA だけは1 AZ ですが、その AZ 内では同じく 11 nines）。Object が失われることはほぼありません。Class 間で違うのは availability（今すぐアクセスできるか）と価格です。
  • Consistency: 2020年末以降、S3 はすべての PUT、DELETE、LIST で strong read-after-write です。書き込んだ直後に読めば新しい版が見え、list すれば新しい object が見えます。古い問題にある「overwrite は eventual consistency」はすでに時代遅れです。
  • アクセス手段: HTTPS 経由の REST API、SDK、CLI（aws s3 は高レベル、aws s3api は低レベルのコマンド）、Console。課金は保存量の GB・月、request 数（PUT/GET）、Internet へのデータ転送量、コールド class の retrieval 料金です。

Intelligent-Tiering: 各 tier
  • Frequent Access: アップロード時のデフォルト tier。
  • Infrequent Access: 30日 アクセスがないと自動で移動。
  • Archive Instant Access: 90日 アクセスがないと移動、それでも即時（ms）で読める。
  • Archive Access（任意、追加で有効化）: 90〜730日後、restore に数分〜数時間。
  • Deep Archive Access（任意）: 180〜730日後、restore に 12時間。
  • 再アクセスすると自動で Frequent に戻る。Retrieval 料金なし、min duration なし、object ごとの monitoring 料金のみ。128 KB 未満の object は monitoring されず、常に Frequent にとどまる。
Glacier Flexible Retrieval: 3つの restore 速度
  • Expedited: 1〜5分、最も高い。ピーク時にも確実に容量を確保したいなら Provisioned Capacity を購入。
  • Standard: 3〜5時間、デフォルト。
  • Bulk: 5〜12時間、最も安い（Flexible Retrieval では retrieval 無料）。
  • Deep Archive は Standard（12時間）と Bulk（48時間）のみで、Expedited はない。
  • Restore は指定した日数だけ Standard に一時コピーを作るもので、元の object は Glacier に残る。「restore したのに数日後にコピーが消えた」という設問は、restore の期限切れが原因。

2. 医療記録を10年間保管し、ほぼ読むことはありませんが、法的要請があれば24時間以内に取り出せる必要があります。lowest cost には何を選びますか。

S3 Glacier Deep Archive。 Deep Archive の Standard restore は12時間で、24時間以内に収まります。設問が「数時間以内」と言っている場合にはじめて Glacier Flexible Retrieval に上げる必要があります。罠: 念のため Flexible Retrieval を選ぶと、保存料金が約4倍高くなります。

3. あるアプリが 20 KB の log object を書き込み、20日間保持してから削除し、各 object は2〜3回読まれます。チームは安くするために Standard-IA に置くことを提案しました。どう評価しますか。

Lifecycle、versioning、replication、Object Lock

概要: lifecycle
  • Lifecycle rule は bucket に付け、prefix、tag、object サイズで絞り込み、current version と noncurrent version に別々に適用します。アクションは2種類: Transition（N日後に storage class を変更）と Expiration（N日後に削除）。
  • Transition は コールド方向への一方通行 のみ: Standard → Standard-IA / Intelligent-Tiering / One Zone-IA → Glacier IR → Glacier Flexible → Deep Archive。Standard へ戻す rule はなく、戻すには object をコピーします（Glacier なら restore）。
  • よく出る制約: lifecycle で Standard-IA や One Zone-IA へ移す前に、object は Standard に 最低30日 置く必要があります。30日目に IA、60日目に Glacier へ移す rule は有効ですが、10日目に IA へ移す rule は拒否されます。
  • 覚えておくべき補助アクション3つ: expire noncurrent versions（N日後に旧版を削除、または直近 N 版だけ保持）、remove expired object delete markers、abort incomplete multipart uploads（隠れて課金され続ける途中のアップロードを掃除）。
  • Lifecycle は毎日バックグラウンドで動き、即時ではありません。日数は object の作成時点（または noncurrent になった時点）から数えます。「X日後に Y へ移す」を least operational overhead で実現するなら、答えは常に lifecycle で、Lambda の cron を書くことではありません。
概要: versioning
  • Bucket 単位で有効化します。同じ key への PUT のたびに新しい version ID が作られ、旧版は残り続け 課金も続きます。Versioning 有効化前からあった object の version ID は null です。
  • 一度有効にすると 無効化はできず、suspend のみ可能: 旧版はそのまま残り、新しい書き込みは ID null で保存されます。
  • Version ID なしの DELETE は先頭に delete marker を置くだけで、object は list から「消えた」ように見えますが、すべての version は残っています。復元は delete marker を削除 するだけです。Version ID 付きの DELETE ではじめてその版が本当に削除されます。
  • Versioning は replication、Object Lock、MFA Delete の前提条件です。設問が protect against accidental deletion or overwrite → versioning（さらに厳しくするなら MFA Delete を追加）。
イメージ: versioning と delete marker
概要: replication（CRR と SRR）
  • Cross-Region Replication (CRR): 別 Region の bucket へ object をコピー。compliance（別地域にコピーを保持）、遠方ユーザー向けの lower latency、disaster recovery に使います。Same-Region Replication (SRR): 同じ Region の bucket へコピー。複数 bucket の log を1つに集約、prod から test への同期、同一 Region の別アカウントにコピーを保持、などに使います。
  • 条件: 両方の bucket で versioning が有効、S3 がソースを読み宛先に書くための IAM role。宛先は別アカウントでもよく（cross-account）、宛先に書くときに storage class を変えることもできます（例: 安価な backup として Deep Archive に直接書く）。
  • Replication は 非同期 で、遡及しません: rule を有効にする前からあった object はコピーされません。既存分をコピーするには S3 Batch Replication（S3 Batch Operations の job）を使います。これは非常によく出る罠です。
  • Replication Time Control (RTC): object の 99.99% を 15分 以内にコピー完了することを約束し、監視用の metric と event があり、追加料金がかかります。設問が predictable replication time、SLA、within 15 minutes → RTC。
  • 削除: delete marker は replicate できます（オプションで有効化）が、version ID 付きの削除は replicate されません（誤削除がコピー側へ波及するのを防ぐため）。「chaining」はなく、A から B へ replicate された object は B の rule で C へ自動的に replicate されません。
  • SSE-KMS で暗号化された object も replicate できますが、role にソース key の decrypt と宛先 key の encrypt 権限が必要です。SSE-C の object は replicate できません（この機能は最近変更があったため要確認）。

4. ある会社が先週、東京の bucket から大阪へ CRR を有効にしました。監査で、昨年アップロードしたファイルが大阪にないことが分かりました。least operational overhead でコピーする方法は。

5. Versioning 有効の bucket で、developer が aws s3 rm s3://b/config.json を実行しました。Object の状態と、最も速い復元方法は。

Object は delete marker に隠されているだけで、すべての version は無傷です。Delete marker を削除（marker の version-id 付きで delete-object）すれば object が再び現れます。 Backup からの restore は不要です。コマンドに --version-id が付いていた場合にはじめて、その版が本当に失われます。

6. 要件: 金融取引 log を7年間保持し、その期間中は no user, including the account administrator が削除や変更をできないこと。必要な作業を2つ選びます。

S3 のセキュリティ: 誰が入れるか、データをどう暗号化するか

概要: アクセス制御
  • S3 へのアクセスを許可または拒否できる層は4つ: IAM policy（identity-based、user/role に付ける、第1週の復習）、bucket policy（resource-based、Principal を持つ、JSON は最大 20 KB）、ACL（旧来の仕組み、bucket と object レベル）、Block Public Access（最上位の遮断スイッチ）。デフォルトではすべての bucket と object が private です。
  • ACL は 2023年4月からデフォルトで無効（Object Ownership = Bucket owner enforced）: すべての object は bucket 所有者のものとなり、権限は policy でのみ付与します。設問の objects uploaded by another account are not accessible to bucket owner は ACL が有効なままの古い bucket の話で、現代的な解決策は Bucket owner enforced を有効にすることです。AWS は特別な場合を除き ACL を使わないよう推奨しています。
  • Bucket policy でよく出る4つの用途: (1) static website 向けに public read を開く、(2) 別アカウントにアクセスを許可する（cross-account、assume role 不要）、(3) HTTPS 必須、encryption 必須、特定の VPC endpoint や IP 範囲からのみ許可といった 条件を強制 する、(4) 削除を遮断する。同一アカウントなら IAM Allow か bucket policy Allow のどちらかで十分、別アカウントなら両側で Allow が必要です（第1週の復習）。
  • Block Public Access: 4つのスイッチ（BlockPublicAcls、IgnorePublicAcls、BlockPublicPolicy、RestrictPublicBuckets）があり、account レベルと bucket レベルに存在し、account レベルはすべての bucket に優先します。新しい bucket ではデフォルトで有効。有効時、Principal * を持つ bucket policy は保存を拒否されるか無効化されます。設問が ensure no bucket in the account can ever be made public → account レベルで Block Public Access を有効化。
  • S3 Access Points: 同じ bucket に対してアプリケーションごとに専用の endpoint（hostname + 専用 policy）を持ち、特定の VPC からのみ に制限できます。「数十チームで共有する bucket の bucket policy が長すぎて管理しづらい」問題を解決します。Multi-Region Access Point は複数 bucket を指すグローバルな1つの endpoint を提供します。
  • IAM Access Analyzer for S3: アカウント外や public に共有されている bucket を理由（ACL、policy、access point）付きで一覧表示します。設問が identify buckets shared with external entities → Access Analyzer。一方 Macie（第8週）は object の中の機密データを探すもので、権限を探すものではありません。
  • S3 向け VPC Gateway Endpoint: private subnet の EC2 が NAT なしで AWS ネットワーク経由で S3 を呼び出せ、無料です。Bucket policy で condition aws:SourceVpce を使い、endpoint 以外からのアクセスをすべて遮断できます。第4週で詳しく学ぶので、今週は存在と無料であることだけ覚えれば十分です。

7. あるアプリが customer managed key の SSE-KMS を使う bucket に毎秒 20,000 object を書き込み、KMS から throttling エラーが出始めました。SSE-KMS を維持したまま most cost-effective な解決策は。

Bucket で S3 Bucket Key を有効にします。 Bucket Key は KMS 呼び出し回数を最大 99% 減らすため、throttling が解消し KMS 料金も下がります。KMS の quota 引き上げ申請も可能ですが、request ごとの料金は払い続けます。SSE-S3 への変更は KMS 維持の要件に反します。

8. Bucket に default encryption SSE-KMS があります。Security team は reject any upload that is not encrypted with the company KMS key を求めています。何をしますか。

s3:x-amz-server-side-encryption が aws:kms 以外のとき s3:PutObject を Deny する bucket policy を追加します（key ID が会社の key 以外のときも拒否するには condition s3:x-amz-server-side-encryption-aws-kms-key-id を使う）。 Default encryption は空欄を埋めるだけで、header AES256 を付けた upload を拒否しません。Block Public Access の有効化は encryption と無関係です。

9. アカウント A の user は、アカウント B の bucket に対する s3:GetObject を Allow する IAM policy を持ち、bucket B の policy もアカウント A を Allow しています。Bucket 内の object は B の customer managed key で SSE-KMS 暗号化されています。User A はダウンロード時に依然として AccessDenied になります。なぜですか。

B の key に対する kms:Decrypt 権限が足りません。B 側の key policy でアカウント A を許可し、user A の IAM にも kms:Decrypt が必要です。 SSE-KMS では object の読み取りは2つのリソース（S3 object と KMS key）に対する2つのアクションです。SSE-S3 ならこの手順は不要で、これが least overhead の設問で SSE-S3 がよく勝つ理由です。

Presigned URL署名付きの URL で、1つの object に対する GET または PUT を期間限定で許可します。受け取る人が AWS アカウントを持つ 必要はありません。SDK または aws s3 presign で作成し、URL は作成者の権限を持ちます。顧客に非公開ファイルを共有する、ユーザーに server を経由せず S3 へ直接 upload させる。IAM user で署名した場合の有効期限は最大 7日。一時 credential（role）で署名した場合は credential の期限までしか有効でない（instance profile は最大 6時間、要確認）。Bucket は private のままでよく、public にする必要はない。
Transfer AccelerationUpload/download が最寄りの Edge location に入り、AWS ネットワーク上を通って bucket に届きます。Endpoint は bucket.s3-accelerate.amazonaws.com。Region から遠い（世界中の）ユーザーが大きなファイルを upload し、公衆 Internet の経路が長い場合。GB 単位の追加料金で、実際に速くなったときだけ課金。Bucket 名にドットを含められない。Client が Region のすぐ近くなら効果なし。
Multipart uploadObject を複数の part（1 part あたり 5 MB〜5 GB、最大 10,000 part）に分割し、並列 で upload して S3 が結合します。Object が 5 GB 超なら 必須、100 MB 以上なら 推奨。利点: 速い（parallel）、失敗した part だけ再送、一時停止して再開できる。途中の part も課金される → lifecycle で abort incomplete multipart。CLI の aws s3 cp は大きなファイルで自動的に multipart を使う。
Byte-range fetchRange header で object の一部のバイト範囲を GET します。大きなファイルの並列ダウンロード（multipart の逆）、object の先頭部分だけ読む（ファイル header）、download の再開。設問が retrieve only part of an object、parallelize downloads。
Event notifications3:ObjectCreated:*、ObjectRemoved:*、ObjectRestore、Replication などが発生すると、S3 が SNS、SQS（Standard queue のみ、FIFO 不可）、Lambda、または EventBridge に event を送ります。Upload 時の画像処理、ファイル到着時の pipeline 実行。宛先には S3 からの送信を許可する resource policy が必要。通常は数秒以内に届く。prefix/suffix でフィルター。EventBridge はより多機能: metadata の内容でフィルター、複数 target、archive と replay。Bucket で有効化が必要。
Static website hostingBucket が bucket.s3-website-ap-northeast-1.amazonaws.com 形式の endpoint で HTML/CSS/JS を配信し、index document と error document を持ちます。HTTP のみ。HTTPS と独自ドメインが必要なら前段に CloudFront を置く（第4週）。Block Public Access の解除と public read の bucket policy が必要。Route 53 alias を使う場合は bucket 名をドメイン名と一致させる 必要がある。Server-side のコードは実行できない。
CORSBucket 上の Cross-Origin Resource Sharing 設定で、Access-Control-Allow-Origin header を返します。ドメイン A の web ページが JavaScript でドメイン B の bucket からファイルを取得しようとしてブラウザに遮断される → bucket B（呼ばれる側）に CORS を設定し、bucket A ではない。設問に「web font」「JavaScript fetch」「different domain」→ CORS。

Storage Lens容量、object 数、コスト、encryption や versioning の比率などを 組織全体、複数アカウント、複数 Region にわたって集計するダッシュボード。識別: organization-wide visibility into storage usage、identify cost optimization opportunities across buckets。無料の free metrics と有料の advanced metrics がある。

  • 流れ: Console で注文 → デバイスを受け取る → 社内ネットワークに接続し、AWS OpsHub または Snowball client でロック解除 → コピー（デバイスへ NFS または S3 API）→ 返送 → AWS が bucket に取り込む。データは 256-bit で暗号化され、key は KMS で管理、デバイスには E Ink の配送ラベルが付いている。
  • Snowball は S3 Standard（または job の設定に応じた別の class）に直接取り込む。Glacier に入れたいなら lifecycle rule を設定する。設問の「Snowball で Glacier に直接移行する」はたいてい古い誤答で、正しい方法は S3 + lifecycle。
  • Snow は S3 からオンプレミスへの 逆方向 の移行（export job）も可能。

AWS Backup Vault Lock と S3 Object Lockどちらも WORM の考え方だが、Vault Lock は vault 内の backup を、Object Lock は bucket 内の object を保護する。

確認クイズ

13. ある会社は NAS 上に 500 TB のデータがあり、Internet 回線は 200 Mbps で、3週間以内に S3 へ移行する必要があります。どの方法を選びますか。

Snowball Edge Storage Optimized を複数台注文し、コピーして返送します。 500 TB を 200 Mbps で送ると約230日かかり、DataSync や Transfer Acceleration では間に合いません。Snowmobile は 10 PB 以上向けです。Direct Connect は敷設に数週間かかり、3週間には間に合いません。

14. オンプレミスの会計アプリが SMB ファイルサーバーに書き込んでおり、使用中のファイルは低レイテンシを維持したいが NAS の容量が尽きました。古いデータは後で Athena を実行するため S3 に置く必要があります。Least change to the application。何を選びますか。

SMB share を持つ S3 File Gateway。 アプリからは SMB share のまま見え、よく使うファイルはローカル cache にあり、全データは S3 に object として保存されるので Athena で読め、lifecycle で古いファイルを IA/Glacier に移せます。DataSync は移行するだけで、アプリが使い続けることはできません。Volume Gateway は block なので Athena で読めません。

15. ある会社は Organizations 内に 40 アカウントがあり、EC2、RDS、EFS、DynamoDB を使っています。要件: 毎日 backup して35日保持する1つのポリシー、backup は専用アカウントにコピーし、ランサムウェア対策として admin でも削除できない こと。何を選びますか。

AWS Backup: tag によって Organizations 全体に適用する backup plan、隔離したアカウントの vault への cross-account コピー、Compliance mode の Vault Lock を有効化。 サービスごとに snapshot を取る Lambda を書いても4種類のリソースをカバーできず、WORM もありません。Object Lock は S3 にしか適用できません。

Lab 1. S3 static website、versioning、上書きアップロードと旧バージョンの復元

  1. 東京に bucket を作成します（us-east-1 以外では LocationConstraint が必須）:

    aws s3api create-bucket --bucket saa-s3-web-quy-2026 --region ap-northeast-1 --create-bucket-configuration LocationConstraint=ap-northeast-1
aws s3api get-public-access-block --bucket saa-s3-web-quy-2026   # 4つとも true: デフォルトで public を遮断

  2. この bucket だけ Block Public Access を解除し（website には public read が必要）、static website hosting を有効にします:

    aws s3api put-public-access-block --bucket saa-s3-web-quy-2026 --public-access-block-configuration BlockPublicAcls=false,IgnorePublicAcls=false,BlockPublicPolicy=false,RestrictPublicBuckets=false
aws s3 website s3://saa-s3-web-quy-2026/ --index-document index.html --error-document error.html

  3. ファイル public-read.json を作り、誰でも GetObject できる bucket policy を付けます（object のみ、ListBucket は不可）:

    {
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "PublicReadGetObject",
    "Effect": "Allow",
    "Principal": "*",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::saa-s3-web-quy-2026/*"
  }]
}
    aws s3api put-bucket-policy --bucket saa-s3-web-quy-2026 --policy file://public-read.json
aws s3api get-bucket-policy-status --bucket saa-s3-web-quy-2026   # "IsPublic": true

  4. HTML ファイルを2つ作ってアップロードします。ブラウザで website endpoint を開きます（http であり https ではない点に注意）:

    Set-Content -Path index.html -Value "<h1>Ban 1 - SAA tuan 3</h1>" -Encoding utf8
Set-Content -Path error.html -Value "<h1>Khong tim thay</h1>" -Encoding utf8
aws s3 cp index.html s3://saa-s3-web-quy-2026/ --content-type text/html
aws s3 cp error.html s3://saa-s3-web-quy-2026/ --content-type text/html
# 開く: http://saa-s3-web-quy-2026.s3-website-ap-northeast-1.amazonaws.com
# 試す: http://saa-s3-web-quy-2026.s3-website-ap-northeast-1.amazonaws.com/khong-co.html → error.html のページ

  5. Versioning を有効にし、index.html の2版目で上書きアップロードして、version 一覧を見ます:

    aws s3api put-bucket-versioning --bucket saa-s3-web-quy-2026 --versioning-configuration Status=Enabled
Set-Content -Path index.html -Value "<h1>Ban 2 - da sua</h1>" -Encoding utf8
aws s3 cp index.html s3://saa-s3-web-quy-2026/ --content-type text/html
aws s3api list-object-versions --bucket saa-s3-web-quy-2026 --prefix index.html --query "Versions[].{Id:VersionId,Latest:IsLatest,Date:LastModified}" --output table

    Version が2つ見えます: 1版目の VersionId は null（versioning 有効化前にアップロード）、2版目は長い ID で IsLatest = True。ページを再読み込みすると「Ban 2」が表示されます。

aws s3 ls s3://saa-s3-web-quy-2026/                          # error.html が消える
aws s3api list-object-versions --bucket saa-s3-web-quy-2026 --prefix error.html   # DeleteMarkers と Versions がある

Lab 2. Lifecycle rule: 30日後に Glacier へ移行、noncurrent version の expire

  1. 3つのアクションを持つ lifecycle.json を作ります: current version を30日後に Glacier Flexible Retrieval へ移行、noncurrent version を30日後に削除（最新3版までは保持）、途中の multipart を7日後に中止:

    {
  "Rules": [
    {
      "ID": "archive-and-clean",
      "Status": "Enabled",
      "Filter": { "Prefix": "" },
      "Transitions": [ { "Days": 30, "StorageClass": "GLACIER" } ],
      "NoncurrentVersionExpiration": { "NoncurrentDays": 30, "NewerNoncurrentVersions": 3 },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
    }
  ]
}

    API での class 名: STANDARD_IA、ONEZONE_IA、INTELLIGENT_TIERING、GLACIER_IR、GLACIER（= Flexible Retrieval）、DEEP_ARCHIVE。

  2. Lab 1 の bucket に付けて、読み直します:

    aws s3api put-bucket-lifecycle-configuration --bucket saa-s3-web-quy-2026 --lifecycle-configuration file://lifecycle.json
aws s3api get-bucket-lifecycle-configuration --bucket saa-s3-web-quy-2026

  3. 誤った rule を試して30日の制約を確認します: Transitions を { "Days": 10, "StorageClass": "STANDARD_IA" } に変えて再度 put します。期待されるエラーは InvalidArgument: 'Days' in Transition action must be greater than or equal to 30 for storageClass 'STANDARD_IA'。30日に戻せば通ります。Glacier にはこの制約はありません（Days 1 でも有効）。

  4. Console で確認: S3 → bucket → Management → Lifecycle rules で rule を開くと timeline 図が見えます。Lifecycle はバックグラウンドで動くため、今週中に class が変わる object はありません。すぐに Glacier の object を見たいなら直接アップロードします: aws s3 cp index.html s3://saa-s3-web-quy-2026/archive/test.html --storage-class GLACIER の後 aws s3api head-object --bucket saa-s3-web-quy-2026 --key archive/test.html で "StorageClass": "GLACIER" が見えます。aws s3 cp s3://saa-s3-web-quy-2026/archive/test.html . を試すと、まだ restore していないため InvalidObjectState エラーになります。

  5. コマンドを覚えるために restore を試します（Bulk、コピーを1日保持）。Glacier Flexible Retrieval の Bulk は5〜12時間かかるので、待つ必要はありません:

    aws s3api restore-object --bucket saa-s3-web-quy-2026 --key archive/test.html --restore-request "Days=1,GlacierJobParameters={Tier=Bulk}"
aws s3api head-object --bucket saa-s3-web-quy-2026 --key archive/test.html   # "Restore": "ongoing-request=\"true\""
GLACIER に置いた object は最低90日分課金されます（数 KB なので気にするほどではありません）。学習用アカウントなら Lab 5 で削除して問題ありません。

Lab 3. CLI で presigned URL を作り、ブラウザで開き、期限切れ後に試す

  1. 2つ目の private bucket を作り（Block Public Access はデフォルトのまま）、秘密のファイルをアップロードします:

    aws s3api create-bucket --bucket saa-s3-private-quy-2026 --region ap-northeast-1 --create-bucket-configuration LocationConstraint=ap-northeast-1
Set-Content -Path secret.txt -Value "chi nguoi co link moi doc duoc" -Encoding utf8
aws s3 cp secret.txt s3://saa-s3-private-quy-2026/secret.txt
# 直接開いてみる: https://saa-s3-private-quy-2026.s3.ap-northeast-1.amazonaws.com/secret.txt → AccessDenied (XML)

  2. 有効期間60秒の presigned URL を作り、ブラウザで開きます:

    aws s3 presign s3://saa-s3-private-quy-2026/secret.txt --expires-in 60

    URL にはパラメーター X-Amz-Algorithm、X-Amz-Credential（quy-admin の access key）、X-Amz-Date、X-Amz-Expires=60、X-Amz-Signature が含まれます。URL をそのままブラウザに貼ると、bucket が private でブラウザが AWS にログインしていなくてもファイルの内容が見えます。

# URL を貼り付ける: Invoke-WebRequest -Method Put -Uri "<URL>" -InFile secret.txt

Lab 5. 片付け: version 付き bucket を空にする、第2週のリソースを削除、Billing を確認

資料を見ずに自力でできるべき2つのこと

1. EBS、EFS、instance store、S3（と FSx）をどの場面で使うか区別する

回答の枠組みのヒント（隠してから自分で表を書く）:

  • EBS: block、1台 の EC2 にアタッチ（io1/io2 の multi-attach は同一 AZ 内で最大16台）、1つの AZ 内、boot volume、database、AZ/Region をまたぐには snapshot が必要。キーワード single instance、persistent block、IOPS。
  • Instance store: host 上の物理ディスク、stop/terminate で消える、IOPS が最も高い、instance に付属して無料。キーワード temporary、buffer / cache / scratch、highest IOPS、ephemeral。
  • EFS: NFS のファイル、複数 AZ の複数 EC2 から同時にマウント、Linux、自動で伸縮、EBS より高い。キーワード shared file system、concurrent access from multiple instances、POSIX、Linux。
  • FSx: 専用ファイルシステム: Windows（SMB、AD、NTFS ACL）、Lustre（HPC、ML、S3 連携）、NetApp ONTAP（NFS + SMB + iSCSI、snapshot、dedup）、OpenZFS。キーワード Windows file share、high-performance computing、hundreds of GB/s。
  • S3: HTTP 経由の object、容量無制限、11 nines、マウント不可（File Gateway/Mountpoint 経由を除く）、最安、lifecycle、static website、data lake。キーワード object、unlimited、static content、backup / archive、accessed over the internet / from Lambda。
  • 各ペアについて除外の一言を言えるようにする: 「複数 EC2 から同時に書く → EBS ではない」「boot volume が必要 → S3 ではない」「stop で消えてもよい → instance store」「Windows SMB → EFS ではなく FSx」。

2. 設問のキーワードから S3 の storage class を選ぶ

回答の枠組みのヒント: 4つの質問を順に自問してから class を決める。

  • アクセス pattern は分かっているか? 分からない / 変化する → Intelligent-Tiering。分かっている → 次へ。
  • 頻繁にアクセスするか? する → Standard。まれ（月単位）→ Standard-IA。再生成できるデータでさらに安くしたい → One Zone-IA。
  • Archive ならどれだけ待てるか? Milliseconds（四半期単位）→ Glacier Instant。数分〜数時間 → Glacier Flexible（Expedited 1〜5分、Standard 3〜5時間、Bulk 5〜12時間）。12〜48時間、長年保管、最安 → Deep Archive。
  • Min duration / min size の罠はないか? 128 KB 未満の object や30日未満で消えるデータは IA だと安くならない。90日未満なら Glacier、180日未満なら Deep Archive も安くならない。
  • あわせて覚える: 全 class が 11 nines。One Zone-IA は唯一の1 AZ の class。Lifecycle はコールド方向への一方通行で、IA へ移す前に30日必要。
