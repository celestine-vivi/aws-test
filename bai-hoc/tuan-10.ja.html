模擬試験の正しい進め方

概要

SAA-C03の本試験は65問（採点対象50問、採点されない試行問題15問。どれが試行問題かは分かりません）、130分、スコアは100〜1000で720以上が合格です。平均して1問2分です。模擬試験の効果は解いた回数ではなく、毎回何を記録できたかで決まります。間違いノートを丁寧に付けた3回分は、点数だけ見た10回分より価値があります。

1回分の手順（6ステップを守り、ステップ5を飛ばさない）

  1. 本番と同じように時間を計ります。 65問なら130分です。40問の問題は比率で計算し、40 × 2分 = 80分です。20問なら40分です。スマートフォンでタイマーをかけ、画面を伏せておきます。

  2. 途中で資料を調べたり、Claudeに聞いたりしません。 模擬試験は何を覚えているかを測るもので、調べる速さを測るものではありません。1問でも調べると、その回の点数は次回との比較に使えなくなります。

  3. 迷った問題に印を付けます。 問題番号を紙に書くか、Flagボタンを使います（Tutorials Dojo、Pearson VUEとも用意されています）。30秒読んでも方向性が見えない問題は、最も可能性の高い選択肢を仮に選んで印を付け、先に進みます。時間が余ったら戻ります。誤答による減点はないので、空欄にはしません。

  4. 採点し、総合点とDomain別の得点を記録します。 AWS-SAA-quiz-01.mdはPROMPT-session-tuan.mdの「総復習」promptを貼れば、Claudeが採点してDomain表を計算します。Tutorials DojoとSkill Builderは自動採点され、Domain別のグラフも表示されます。

  5. 正解した問題の解説も読みます。 多くの人が飛ばすステップです。正解は当て推量かもしれず、答えは合っていても理由が違うこともあります。正解した問題の解説を読んで初めて、残り3つの選択肢がなぜ誤りかが分かり、それこそが本試験で次に問われ方が変わるポイントです。

  6. 間違いノートを付けます。 so-ghi-cau-sai.mdに7列で記録します。記録するのは誤答と、当て推量で正解した問題だけです。1行2分以内で、第12週に読み返しても分かる程度に書きます。

SAAの設問の読み方

概要

SAAの設問は4〜8行ありますが、答えを決める制約の文は通常1つだけで、最後の文にあります。前半は背景（どんな会社か、何を動かしているか、どんな問題があるか）で、最後が「What should a solutions architect do to meet these requirements with the LEAST operational overhead?」です。多くの選択肢は「実現できる」ものの、その制約をきちんと満たすのは1つだけです。だから最後の文を先に読み、制約のキーワードに下線を引いてから背景を読みます。

1問を2分で読む手順

  1. 最後の質問文を先に読みます（10秒）。大文字の語や制約語を探します: LEAST operational overhead、MOST cost-effective、highly available、minimal changes、real time、within minutes、MOST secure、fastest。これを選択肢を順位付けする基準として覚えておきます。

  2. 背景を読み、数値と技術的な制約に下線を引きます（30秒）: protocol（SMB、NFS、POSIX）、OS、データ量（TB、PB）、頻度（daily、once a year）、許容できる遅延（ms、hours）、変えてはいけないもの（cannot modify application code）、どこで動いているか（on-premises、EC2、container）。

  3. まず誤りの選択肢を2つ消します（30秒）。誤りの選択肢はたいてい次のどれかです: protocolやplatformが合わないサービス（Windows向けにEFS）、明らかな制約違反（変更不可なのにcodeを修正する）、overheadを問われているのに手作業、costを問われているのに明らかに高価。

  4. 残った2つから、ステップ1の基準で選びます（30秒）。ここで下の2つのルールを使います。

  5. 選んだ選択肢をもう一度読みます（10秒）。技術的に正しいだけでなく、質問に正しく答えているかを確かめます。そして次の問題へ進み、引きずらないようにします。

ルール1: overheadを問われたら「よりmanagedな方が勝つ」
  • 設問にleast operational overhead、minimal administrative effort、fully managed、without managing servers、least amount of effortがあれば、選択肢をmanagedの度合いで並べ、最も高いものを選びます。
  • managedの度合いが低い順: EC2に自分でインストール → instanceのあるmanagedサービス（RDS、ECS on EC2、ElastiCache） → serverless（Lambda、Fargate、Aurora Serverless、DynamoDB、S3、Athena、Firehose）。
  • 例: 最小のoverheadでlogをS3へ送る場合、Kinesis Data Firehose（serverless、自動でbatchして書き込む）が、Kinesis Data Streams + 自作Lambda（shardとconsumerのcodeを管理する必要がある）に勝ちます。
  • 罠: Xを行うnativeなサービス（例: S3 Lifecycle、RDS automated backup、EventBridge Scheduler）があるのに、「EC2上でcron scriptを書く」「自作のLambdaでXを行う」という選択肢は、ほぼ必ず誤りです。
ルール2: costを問われたら「安い方が勝つ」
  • 設問にmost cost-effective、minimize cost、lowest cost、reduce costsがあれば、機能要件を満たす選択肢の中で最も安いものを選びます。
  • よく出る安くなる順: On-Demand → Reserved / Savings Plans → Spot、S3 Standard → Standard-IA → One Zone-IA → Glacier Instant → Flexible → Deep Archive、NAT Gateway → Gateway endpoint、Interface endpoint → Gateway endpoint、Provisioned → On-Demand（負荷が不規則なDynamoDB）、Direct Connect → VPN。
  • ただし安くても機能を満たす必要があります: production databaseにSpotは安くても誤り、設問がresilient to AZ failureと言うならOne Zone-IAは安くても誤り、設問がretrieve within minutesと言うならDeep Archiveは最安でも誤りです。
  • 罠: costを問われているが、最安の選択肢は大きなアーキテクチャ変更が必要で、設問はminimal changesと言っている場合。2つの制約が同時に出たら、技術的な制約（minimal changes、データを失わない）が絞り込み条件で、costは絞り込みを通過した選択肢の中での順位付け基準にすぎません。

確認クイズ

1. 設問:「A company runs a nightly batch job on EC2 that copies 2 TB of new log files from an on-premises NFS server to Amazon S3 over AWS Direct Connect. The job is written in Python and often fails midway. Which solution meets the requirement with the LEAST operational overhead?」選択肢を見る前に、どの語に下線を引き、どの種類の選択肢をすぐに消しますか?

下線: LEAST operational overhead、NFS、on-premises、毎晩2 TB、Direct Connect。すぐに消す: 「Python scriptにretryを追加する」「複数のEC2でscriptを実行する」といった選択肢すべて。 正解の方向: AWS DataSync agentがNFSを読み、スケジュールされたtaskでDirect Connect経由でS3に書き込む。Storage Gatewayもmanagedですが継続的なアクセス用で、定期的なデータ転送用ではありません。Snowballはnetwork回線があり毎晩繰り返すので合いません。

2. 読み取りクエリで過負荷になっているproductionのRDS MySQLについて、設問はmost cost-effectiveを求めています。残った2つの選択肢は(A) Read Replicaを作成する、(B) instance classを2倍に上げる、です。どちらを選び、なぜですか?

A、Read Replica。 どちらも読み取り負荷を解決しますが、Read Replicaはより小さいinstanceを1つ追加してレポートの負荷を切り離せます。一方instance classを2倍にすると、必要のない書き込み負荷の分まで2倍払うことになります。設問がminimal changes to applicationに変われば、Read Replicaはappの読み取り接続を新しいendpointへ向ける必要があるので、Bが勝ちます。

3. 「Choose TWO」の問題: private subnetのEC2がInternetに出ずにDynamoDBを呼ぶ必要があります。選択肢: (A) DynamoDB用のGateway VPC endpointを作成する、(B) NAT Gatewayを作成する、(C) private subnetのroute tableにendpointへのrouteを追加する、(D) DynamoDB用のInterface endpointを作成する、(E) Internet Gatewayを接続する。どの組み合わせを選びますか?

AとC。 DynamoDBのGateway endpointはroute table entryがあって初めて機能するので、2つは1つの解決策の2つの部品です。BとEはInternetに出るので設問に反します。D: DynamoDBには現在Interface endpointもあります（AWSドキュメントで要確認）が、時間単位で課金され、Cとは組になりません。そのためA + Cだけが単独で完結する組み合わせです。

4. ある動画レンダリング会社はS3に500 TBの元画像を持っています。各レンダリングでは200台のEC2 Linux nodeが数百GB/sのthroughputで1つのfile systemを共有して読み書きし、終わればもう不要です。most cost-effectiveなレンダリングclusterのstorageを選んでください。

FSx for Lustre、scratch file system、S3 bucketとlink。 LustreはS3からlazy-loadし、throughputが高く、scratchはpersistentより安くて「終われば不要」に合います。EFSはこの規模のthroughputに届かず、S3ともlinkしません。500 TBを各nodeのEBSに丸ごとコピーするのは余計で高価です。

5. 診療記録は法律により10年間保存する必要があり、ほとんど読まれませんが、裁判所の要求があればwithin 24 hoursで提出しなければなりません。adminを含め誰も期限前に削除できてはなりません。2つの設定を選んでください。

6. on-premisesのdata centerの空き容量は2 TBで、Windowsアプリケーションが毎日SMBでアクセスする必要のある60 TBのファイルデータがあり、頻繁に使われるのはそのうち5%だけです。minimal changesで大部分をAWSに移したいと考えています。何を選びますか?

S3 File Gateway（SMB share）。ローカルcacheによく使う5%を保持し、データはS3に置く。 アプリケーションからは1つのSMB shareに見えるのでminimal changesです。DataSyncは転送が終わるとアプリケーションがローカルでアクセスする経路を失います。FSx for WindowsはVPN/DX経由のmountが必要で、ローカルcacheがなく、あまり使わない60 TBには高価です。Volume Gatewayはblock iSCSIで、SMBではありません。

7. 300 TBの古いlogをdata centerからS3へ2週間以内に移す必要があります。500 MbpsのInternet回線は本番で使用中で、すべてを占有することはできません。何を選びますか?

複数台のSnowball Edge Storage Optimized（300 TBで約4台）。 ざっと計算すると、300 TBを500 Mbpsで全帯域を使っても約55日かかり、しかも帯域を占有できません。DataSyncにはbandwidth throttleがありますが、所要時間の計算は変わりません。Transfer Accelerationも同じ回線を通ります。

8. S3のobjectは最初の1か月は頻繁にアクセスされ、その後はときどき、1年後にはほとんどアクセスされません。いつでもすぐに取り出せることが必須で、AZ 1つの喪失に耐える必要があります。most cost-effectiveなlifecycleの設計は?

14. チケット販売のweb appは発売開始の5分間に50,000件の注文を受けますが、backendは1分あたり2,000件しか処理できません。注文を失ってはならず、各注文は1回だけ処理する必要がありますが、顧客間の順序は重要ではありません。何を選びますか?

web tierとworker tierの間にSQS Standardを置き、workerをidempotentにする（設問がexactly-onceを強調し、throughputが上限内ならSQS FIFO）。 Standardは重複配信がありうるのでconsumer側でidempotentにする必要があります。選択肢にMessageGroupIdを顧客IDにしたFIFOがあれば、5分間で50,000件は約170 msg/sで300 msg/s未満なので、FIFOも正解です。SNSで直接pushすると、過負荷のworkerで失われます。Kinesisは順序を保ちますが、作業queueの問題にはoverheadが大きくなります。

15. 毎秒100,000件のclickstreamがあります。3つのチームの要件: (1) 数秒以内に不正を検知する、(2) Athenaでqueryできるよう全データをParquet形式でS3に保存する、(3) algorithmを修正したら3日前のデータを再処理する。アーキテクチャを選んでください。

Kinesis Data Streams（retention 7日）を中心に置き、consumer 1はreal-time用のLambdaまたはManaged Flink、consumer 2はParquet変換付きでS3に書き込むFirehose。 独立した複数のconsumerとreplayが、Data Streamsが必須となる理由です。Firehose単体ではreplayできず、recordごとのreal-time処理もできません。SQSでは複数のconsumerが同じデータを読めません。

16. Aurora MySQLがTokyoにあります。要件: Tokyo Region全体が失われたら、RPO 1秒未満、RTO 1分未満でSingaporeで再稼働する必要があり、Singaporeのユーザーも速く読み取りたいと考えています。何を選びますか?

Aurora Global Database、Singaporeにsecondary cluster。 replicationはstorage層で行われ、lagは通常1秒未満、secondaryのpromoteは約1分で、secondaryは読み取りを処理します。RDSの通常のcross-Region Read Replicaはbinlogに依存してlagがあり、promoteも遅いです。Multi-AZはRegionの喪失を防ぎません。cross-Regionのbackupでは、RTOは数時間です。

17. ある会社はS3に毎月2 TBのALBのlogを持っています。月に1回、security teamが異常なIPを探すためにいくつかのSQLを実行する必要があります。Least operational overheadかつcost-effectiveな方法は?

AthenaでS3を直接queryし、日付でpartitionし、可能ならGlueでParquetに変換する。 Redshiftは数回のqueryのために1か月ずっとclusterを維持する必要があります。EMRはclusterの構築が必要です。OpenSearchは毎月2 TBをingestしてdomainを常時稼働させる必要があり、「月に1回」の用途には高価です。

18. 「注文の支払い完了」というイベントを、在庫システム（SQS）、メールシステム（Lambda）、data lake（Firehose）に届ける必要があります。どれか1つのシステムが一時的に障害になっても、各システムはすべて受け取らなければなりません。何を選びますか?

3つのsubscriberを持つSNS topic（fan-out）、または3つのtargetを持つEventBridge rule。 SNSでは、SQSのsubscriberは永続的なので、在庫システムが一時的に障害でもmessageは保持されます。Lambdaにはretryとdead-letter queueがあります。選択肢が「1つのSQSに送り、3つのシステムが一緒に読む」なら、1つのmessageを取得できるのは1つのconsumerだけなので誤りです。設問に「複雑な内容によるフィルタ」や「送信元がSaaS」が加われば、EventBridgeがSNSに勝ちます。

19. Security teamに、あるEC2がbotnetリストに載っているIPアドレスにtrafficを送っていること、あるaccess keyが見知らぬ国から使われていることを知らせるアラートが届きました。このアラートを生成したサービスはどれで、さらに調査するにはどのサービスを使いますか?

GuardDutyがfindingを生成し、Detectiveで根本原因を調査する。 この2つの兆候はVPC Flow LogsとCloudTrailからのthreat detectionで、まさにGuardDutyの役割です。InspectorはtrafficやAPIを見ません。MacieはS3のデータだけです。Security Hubはfindingを表示できますが、生成はしません。

20. ある会社はOrganizationsに50のaccountを持っています。要件: どのaccountも（そのaccountのadminを含めて）ap-northeast-1とap-northeast-3以外にresourceを作成できず、CloudTrailを停止できないこと。Least operational overheadな方法は?

rootまたはOUにSCPを付ける: aws:RequestedRegionがリストに含まれない場合のDeny（globalサービスにはNotAction）と、cloudtrail:StopLogging、cloudtrail:DeleteTrailのDeny。 各accountのIAM policyはadmin自身が外せるうえ、50回作成する必要があります。Permissions boundaryはprincipalごとに適用され、account全体をカバーしません。Configは違反を検出できますが、防止はしません。

21. あるmobileアプリケーションでは、ユーザーがemailまたはGoogleでサインアップでき、サインイン後は自分のS3 bucketに写真を直接uploadできます。2つの構成要素を選んでください。

Cognito User Pool（サインアップ、サインイン、Google federation）とCognito Identity Pool（tokenをIAM roleの一時的なcredentialに交換してS3を呼ぶ）。 罠: User Poolだけを選ぶと、appはJWTを持ちますがS3を呼ぶAWS credentialがありません。Identity Poolだけを選ぶと、emailでサインアップしたuserを保存する場所がありません。顧客ごとのIAM userは誤りです。選択肢にあり、設問が「clientからSDKで直接」と言っていなければ、backendが発行するpresigned URLも正しいアーキテクチャです。

22. 監査要件: (1) 新しいEBS volumeがすべて暗号化されていることを証明し、過去6か月でどのvolumeが違反していたかを把握する、(2) 誰が暗号化されていないvolumeを作成したかを把握する。2つのサービスを選んでください。

AWS Config（rule encrypted-volumes、configuration history、timeline）とCloudTrail（誰がCreateVolumeを呼んだか）。 Configは「設定が正しいか、いつからか」に答え、CloudTrailは「誰がやったか」に答えます。Trusted Advisorには履歴がなく、呼び出し元も記録しません。GuardDutyは暗号化とは無関係です。設問がさらに「最初から防止する」を求めるなら、account単位でEBS encryption by defaultを有効にするか、SCPを使います。
