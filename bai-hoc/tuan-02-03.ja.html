EC2: instance family、user data、metadata

instance type 名の読み方

例えば m6g.2xlarge の場合、m は family（general purpose）、6 は世代、g は AWS の Graviton（ARM）プロセッサー、2xlarge はサイズです。よく見る追加の文字: a AMD、i Intel、g Graviton、n ネットワーク強化、d ローカル NVMe ディスク付き（instance store）、e RAM やディスクが多い。

  • Nitro System: 新世代の仮想化基盤です。EBS で最大 256,000 IOPS、enhanced networking を実現し、現行のほとんどの type が Nitro です。
  • type は勘で選ばず Compute Optimizer（第8週で学習）で選びます。
User data
  • 初回起動時に1回だけ（first boot）実行されるスクリプトで、root で実行されるためスクリプト内に sudo は不要です。
  • 上限は raw 形式で 16 KB。Linux では #!/bin/bash で始め、Windows では <powershell> を使います。
  • 用途: パッケージのインストール、コードの取得、ドメイン参加、load balancer への登録。重いインストールは AMI に焼き込んでおくと起動が速くなります（5章参照）。
  • スクリプトが期待通りに動かないときは /var/log/cloud-init-output.log のログで調べます。
  • user data を変更するにはインスタンスを stop してから編集します。毎回の起動で再実行するには cloud-init の特別な設定が必要です（試験ではほぼ出ません）。
Instance metadata (IMDS)
  • アドレスは http://169.254.169.254/latest/meta-data/ で、インスタンス内部からのみ呼び出せます。
  • 取得できる情報: instance-id、instance-type、AZ、プライベート/パブリック IP、security group、iam/security-credentials/<role> にある IAM role の一時認証情報。user data は /latest/user-data で確認できます。
  • IMDSv2: 先に PUT で token を取得し、毎回のリクエストにヘッダーとして付けます。role の認証情報を盗む SSRF 脆弱性への対策です。Amazon Linux 2023 では IMDSv2 がデフォルトで有効です。「アプリが SSRF で認証情報を取られるのを防ぐ」→ IMDSv2 を強制（HttpTokens=required）。
  • EC2 上の SDK と CLI は IMDS から自動で認証情報を取得します。これが access key を埋め込まずに EC2 に role を付ける理由です（第1週の復習）。

確認クイズ

1. あるデータ分析アプリは、高速にクエリするため 500 GB のデータセットを RAM に保持する必要があります。どの family を選びますか？

Memory optimized（r または x）。キーワードは in-memory。Storage optimized（i）はひっかけです。高速なローカルディスクを提供するもので、大容量 RAM ではありません。

2. セキュリティチームが、EC2 上の Web アプリに IAM role の認証情報を取得されうる SSRF 脆弱性を発見しました。コード変更を最小限にしてリスクを下げる方法は？

インスタンスで IMDSv2 を必須にする。token は PUT とヘッダーで取得する必要があり、GET だけの単純な SSRF では取得できません。EC2 から role を外すとアプリが権限を失うため、正解ではありません。

Reserved と Savings Plans、どちらを選ぶか
  • 新しい問題では柔軟性の高い Savings Plans が正解になりやすく、AWS もこちらを推奨しています。
  • Compute Savings Plans: すべての family、サイズ、OS、Region、さらに Fargate と Lambda にも適用。最も柔軟ですが割引は小さめです。
  • EC2 Instance Savings Plans: 1つの Region の1つの family にコミット（例: 東京の m5）し、サイズ、OS、AZ は自由に変更可。割引は大きめです。
  • RI が正解になるのは、「1つの AZ で reserve capacity が必要」（Zonal RI）とある場合や、Savings Plans がないサービス（RDS、ElastiCache、OpenSearch、Redshift、DynamoDB reserved capacity）の場合です。
  • 両方に共通の支払いオプション: All Upfront（最安）、Partial Upfront、No Upfront（コミット型の中で最も高い）。
Spot の詳細
  • max price を設定します（デフォルトは On-Demand 価格）。Spot 価格が max を超えるか、AWS がキャパシティを必要とすると、2分前の通知（metadata または EventBridge で確認）の後にインスタンスが中断されます。
  • 中断時の動作: terminate、stop、hibernate のいずれか。
  • Spot Fleet / EC2 Fleet: 複数の type、複数の AZ をまとめ、capacity-optimized または price-capacity-optimized 戦略で中断を最小化します。「中断の確率を下げたい」→ type と AZ を分散。
  • Auto Scaling Group での組み合わせ: 最小台数部分はベースの On-Demand、スケールアウト分は Spot（第4週で学習）。
  • Spot block（1〜6時間確保）は提供終了しており、古い問題でしか出ません。

EBS: gp3、io2、st1、sc1、snapshot、encryption、multi-attach

概要
  • EBS は EC2 に接続するネットワークディスク（block storage）で、1つの AZ 内に存在し、stop/terminate 後もデータが残ります（delete on termination を有効にしていない場合）。1つのボリュームは1台のインスタンスに接続し（multi-attach を除く）、1台のインスタンスには複数のボリュームを接続できます。
  • AZ 内で自動的に複製されるため耐久性は高いですが、AZ がダウンするとアクセスできなくなります → AZ の外へ出すには snapshot が必要です。
  • 課金はプロビジョニングした GB/月（使用量ではない）に、購入した追加の IOPS/スループットを加えたものです。

  • 1つのボリュームで over 16,000 IOPS や sub-millisecond latency とあれば → io2。cost-effective で IOPS の指定がなければ → gp3。
  • Elastic Volumes: 稼働中のボリュームのサイズ拡張、タイプ変更、IOPS 変更が detach なしで可能です。サイズ拡張後は OS 内でパーティションとファイルシステムを自分で拡張します（growpart、xfs_growfs）。拡張のみで縮小はできません。
Snapshot
  • ボリュームのコピーで S3 に保存され（object は見えません）、incremental です: 2回目以降は変更されたブロックのみ保存しますが、途中の snapshot を削除しても残りの snapshot から復元できます。
  • Region レベルに存在 → データを別の AZ に移す方法（移行先 AZ で snapshot からボリュームを作成）や、別の Region に移す方法（snapshot をコピー）になります。
  • 稼働中でも取得できますが、整合性のため I/O を止めるか detach するのが望ましく、root ボリュームならインスタンスを stop します。
  • EBS Snapshots Archive: 約75%安いアーカイブ層で、復元に24〜72時間かかります。Recycle Bin: 削除した snapshot/AMI を1日〜1年保持し、誤削除から取り戻せます。
  • Fast Snapshot Restore (FSR): snapshot から作成したボリュームが最初の読み込みで遅くならず、すぐにフル性能を出します。時間単位で課金されます。
  • Data Lifecycle Manager (DLM): スケジュールに従って snapshot を自動作成・削除します（「EBS snapshot の自動化」→ DLM または AWS Backup）。
Encryption
  • KMS（AES-256）を使用します。ボリューム内の at rest、インスタンスとボリューム間の in transit、そこから作られるすべての snapshot とボリュームが暗号化されます。性能への影響はほぼありません。
  • EC2 の設定で Region 全体の encryption by default を有効にできます。
  • 暗号化されていないボリュームはその場で暗号化を有効にできません。手順: snapshot → encrypt にチェックを入れて snapshot をコピー → コピーから新しいボリュームを作成 → ボリュームを差し替え。定番の問題です。
  • 暗号化された snapshot を別アカウントに共有するには、customer managed key を使い、鍵も共有する必要があります。AWS managed key で暗号化した snapshot は共有できません。
Multi-attach
  • io1/io2 のみ。1つのボリュームを同じ AZ の最大 16台の Nitro インスタンスに接続でき、全台が読み書き可能です。
  • 通常のファイルシステム（ext4、XFS）は複数台からの同時書き込みを扱えない → cluster-aware file system を使うか、アプリ側で管理します（旧来の Oracle RAC など）。一般的な共有ストレージの方法ではありません。
  • 「複数 AZ の複数の EC2 が1つのファイルシステムを読み書き」→ multi-attach ではなく EFS。
確認クイズ

8. データベース用に接続した 200 GiB の gp2 ボリュームで IOPS が不足しています。アプリは最低コストで安定した 10,000 IOPS を必要とします。どうしますか？

gp3 に変更して 10,000 IOPS をプロビジョニングする。200 GiB の gp2 はベースライン 600 IOPS しかなく、10,000 にするには 3,334 GiB まで拡張する必要があり無駄です。io2 でも達成できますが、10,000（16,000 未満）で足りるなら gp3 より高くなります。

ボリュームの snapshot を取り、encrypt オプション付きで snapshot をコピーし、暗号化された snapshot から新しいボリュームを作成して旧ボリュームと差し替える。既存ボリュームに「暗号化を有効にする」ボタンはありません。

AMI と instance store

AMI (Amazon Machine Image)
  • EC2 を起動するためのテンプレートです。root ボリューム（と他のボリューム）の snapshot、block device mapping、launch permission、アーキテクチャー（x86/ARM）、仮想化タイプを含みます。
  • 入手元: AWS 提供（Amazon Linux 2023、Ubuntu、Windows）、AWS Marketplace（ソフトウェア料金が追加）、自分の AMI（golden AMI）、他アカウントから共有された AMI。
  • AMI は1つの Region に存在します。別の Region で起動するにはその Region へ AMI をコピーします。同じ Region 内ならどの AZ でも起動できます（EBS とは異なる）。
  • Golden AMI: パッチ済み OS、エージェント、アプリを AMI に焼き込み、インスタンスを速く同一構成で起動させます。「user data でインストールする代わりに Auto Scaling のインスタンス起動時間を短縮」→ golden AMI。焼き込みの自動化は EC2 Image Builder。
  • AMI の共有: 特定アカウント、Organization、または public。暗号化された AMI は KMS key も一緒に共有する必要があります。
  • AMI の削除は deregister です。付随する EBS snapshot は自動削除されないので、課金を止めるには手動で削除します。
Instance store
  • インスタンスが動くホストに物理的に接続されたディスク（NVMe/SSD）で、d の付く type や i、d、h family にあります。サイズは type ごとに固定で、追加購入はできません。
  • ネットワークを経由しないため非常に高性能です（i3en/i4i では数百万 IOPS）。
  • Ephemeral: stop、hibernate、terminate やハードウェア障害でデータが消えます。reboot では残ります。EBS のように snapshot は取れません。
  • 用途: キャッシュ、バッファ、スクラッチ、一時データ、他の場所にレプリカがあるデータ（NoSQL クラスターのノード）。
  • highest possible IOPS、temporary、can be lost とあれば → instance store。must persist after stop とあれば → EBS。
  • 料金はインスタンス料金に含まれ、別途課金はありません。
EC2 を取り巻く4種類のストレージのイメージ

EFS: performance mode、throughput mode、storage class

概要
  • マネージドの NFS v4.1 ファイルシステムで、Region 内の複数 AZ にある数百台の EC2（Regional）または1つの AZ（One Zone）から同時にマウントできます。Linux 専用で、Windows には FSx for Windows を使います。
  • ペタバイトまで自動で伸縮し、実際に使った GB で課金され、事前のプロビジョニングは不要です。GB 単価は EBS gp3 の数倍（価格は要確認）ですが、共有でき管理も不要です。
  • mount target（AZ ごとに1つの ENI）経由で接続し、Security Group で 2049 番ポートを開けます。Direct Connect/VPN 経由でオンプレミスからマウントすることも可能です。
  • at rest は KMS、in transit は TLS（mount helper の -o tls）で暗号化します。権限は POSIX、IAM、EFS Access Point（アプリごとに user/group とルートディレクトリを強制）で管理します。
  • Lambda や ECS/Fargate も EFS をマウントできます。「複数のコンテナで共有の永続ストレージが必要」→ EFS。
Performance mode（作成時に選択）
  • General Purpose: デフォルトで最も低レイテンシー。Web、CMS、ホームディレクトリ向け。特別な理由がなければこれを選びます。
  • Max I/O: より多くのクライアントの並列アクセスに耐えられる代わりに、レイテンシーがやや高くなります。ビッグデータ、メディア処理向け。Bursting/Provisioned の Regional でのみ利用でき、One Zone と Elastic では使えません。
Throughput mode（後から変更可）
  • Elastic（現在のデフォルト）: 負荷に応じて自動で伸縮し、読み書きした量で課金されます。spiky で予測困難な負荷のときに選びます。
  • Provisioned: 容量に関係なく MB/s を固定で設定します。データは小さいが常に高いスループットが必要なときに選びます。
  • Bursting: スループットが容量に比例（GB あたり 50 KB/s）し、burst credit が加わります。小さなファイルシステムは詰まりやすい → Elastic または Provisioned に変更します。

S3: lifecycle、versioning、replication（CRR、SRR）、Object Lock

Lifecycle rule
  • アクションは2種類: Transition（N 日後に class を変更）と Expiration（N 日後に削除）。prefix、tag、object サイズで絞り込めます。
  • noncurrent version（versioning 有効時の旧バージョン）にも適用できます。例: 旧バージョンを30日後に Glacier へ移し、365日後に削除。
  • よく問われる2つの後片付けアクション: N 日後の abort incomplete multipart upload（途中のアップロードも課金される）と、expired delete marker の削除。
  • 制約: Standard-IA / One Zone-IA へ移すには、object が Standard に最低 30日あることが必要です。Glacier へは0日目でも移せます。移行は下方向のみ（Standard → IA → Glacier）で、自動で上には戻りません。
  • 何日にすべきか分からない場合 → まず S3 Storage Class Analysis や Storage Lens を有効にしてパターンを確認します。
Versioning
  • bucket 単位で有効にします。有効化前からある object の version ID は null。一度有効にすると suspend しかできず、完全に無効にはできません。
  • 上書きアップロードで新しい version が作られ、旧版も残ります（課金も続きます）。通常の削除は delete marker を置くだけで、delete marker を削除すると「復元」になります。完全に削除するには version ID を指定して削除します。
  • MFA Delete: version の完全削除や versioning 状態の変更時に MFA を必須にします。有効化できるのは root のみで、CLI/API から行います。
  • Versioning は replication と Object Lock の必須条件です。
  • 「誤削除や誤上書きから保護」→ versioning（さらに強い保護に触れていれば + MFA Delete）。

Replication は有効化後の新しい object にしか適用されない。既存の object をコピーするには S3 Batch Replication を実行する。CLI で手作業コピーする必要はありません。

Object Lock、Compliance mode、retention 3年。Governance mode は、bypass 権限を持つ管理者が削除できるためひっかけです。Versioning 単体では version の削除を防げません。

delete marker を削除する（delete marker の version ID を指定して削除）と、直近の版が current に戻ります。バックアップからの restore は不要です。

23. コンプライアンスチームは、すべての object を会社の KMS key で暗号化し、暗号化されていないアップロードはすべて拒否するよう求めています。何を設定しますか？

S3: presigned URL、Transfer Acceleration、multipart upload、event notification

Presigned URL
  • 署名付きの URL で、特定の object に対する GET（ダウンロード）または PUT（アップロード）を期限付きで許可し、URL を作成した人の権限を引き継ぎます。
  • CLI の aws s3 presign（デフォルト3600秒）または SDK で作成します。IAM user の認証情報では最大 7日、一時認証情報（role）ではセッションの期限で失効します。
  • 用途: public にせず顧客に非公開ファイルをダウンロードさせる、サーバーを経由せずユーザーに S3 へ直接アップロードさせる（バックエンドの負荷軽減）、期限付きリンクを送る。
  • CloudFront signed URL/cookie（第4週）との比較: 広く配信し、キャッシュが必要で多数のファイルなら CloudFront、1つの object を直接なら S3 presigned。
Transfer Acceleration
  • アップロード/ダウンロードは最寄りの edge location に入り、AWS のバックボーンネットワークを通って bucket に届きます。endpoint は bucket.s3-accelerate.amazonaws.com。
  • 距離が遠い場合（世界中のユーザーが1つの Region にアップロード）や大きなファイルで効果があります。GB あたりの追加料金があり、有効化前に速度を比較するツールが AWS にあります。
  • 問題文: users worldwide upload large files to a single bucket, speed up → Transfer Acceleration（multipart と組み合わせ）。
Multipart upload
  • ファイルを複数の part（1 part あたり 5 MB〜5 GB、最大 10,000 part）に分けて並列にアップロードし、失敗した part だけを再送します。
  • 100 MB 以上で推奨、5 GB 超で必須。CLI の aws s3 cp は自動で multipart を行います。
  • 途中までアップロードされた part は、完了または abort するまで課金され続けます → lifecycle rule「abort incomplete multipart uploads after 7 days」。
  • ダウンロード側の対応機能は byte-range fetch: 範囲ごとに並列ダウンロードしたり、ファイルの先頭部分だけを取得したりできます。
Event notification
  • イベント（s3:ObjectCreated:*、ObjectRemoved、ObjectRestore、Replication など）が発生すると、SNS、SQS（standard queue のみ、FIFO は不可）、Lambda に送信します。prefix/suffix（例: images/、.jpg）で絞り込めます。
  • 送信先には S3 からの送信を許可する resource policy が必要です（SNS topic policy、SQS queue policy、Lambda resource policy）。
  • EventBridge（bucket で有効化）: より多くのイベント種別、JSON の内容によるフィルタリング、複数の送信先への同時配信、アーカイブとリプレイ。「複数の送信先、複雑なフィルター」→ EventBridge。
  • 定番: 画像アップロード → event → Lambda がサムネイルを作成（第7週でこのラボを実施）。
識別用に追加
  • S3 Select / Glacier Select: S3 内で SQL によりフィルタリングし、必要な部分だけを返して帯域を節約します。Athena（第9週）は複数の object を SQL でクエリするものです。
  • S3 Object Lambda: コピーを保存せずに、読み取り時に object を変換します（PII のマスク、リサイズ）。
  • Requester Pays: ダウンロードする側がデータ転送料を払い、bucket 所有者はストレージ料金だけを払います。大規模な公開データセット向けです。
  • CORS: 別ドメインの Web から bucket を呼び出せるようにします。ブラウザで CORS エラー → bucket に CORS ルールを追加。
  • Static website hosting: bucket.s3-website-region.amazonaws.com 形式の HTTP endpoint。bucket を public にするか、public にしないなら OAC 付きの CloudFront の背後に置きます（第4週）。
確認クイズ

26. モバイルアプリで、ユーザーが 2 GB の動画を会社のサーバーを経由せず S3 に直接アップロードし、bucket は private のままにしたい。方法は？

バックエンドが PUT 用の presigned URL を作成し、アプリが multipart で直接アップロードする。public write を開放するのは誤りです。EC2 経由のアップロードは帯域を消費し、scale しません。

27. Console で見える object の容量は小さいのに、S3 の請求額が異常に高い。最もよくある原因は？

未完了の multipart upload（または noncurrent version）が課金されている。abort incomplete multipart uploads と expire noncurrent versions の lifecycle rule を追加します。

Lab 6. 1つの EFS を2台の EC2 にマウントし、共有ファイルを確認

Lab 4. S3 static website を作成し、versioning を有効にして上書きアップロードし、旧版を復元
