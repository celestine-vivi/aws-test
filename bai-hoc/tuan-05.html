Elastic Load Balancing: ALB, NLB, Gateway Load Balancer

Giải thích ngắn

Load balancer là một điểm vào duy nhất (DNS name) nhận request rồi chia cho nhiều target (EC2, IP, Lambda, container) ở nhiều AZ. Nó che đi việc một instance chết, che IP private, và là chỗ gắn chứng chỉ TLS. ELB là dịch vụ managed: AWS tự scale node của load balancer, bạn chỉ chọn loại, listener, target group và health check.

  • Application Load Balancer (ALB): layer 7, hiểu HTTP/HTTPS, gRPC, WebSocket. Route theo host (api.example.com), path (/images/*), query string, HTTP header, method, source IP. Target group có thể là EC2, IP, ECS task, hoặc Lambda function. Hỗ trợ authentication ngay trên listener bằng Cognito User Pool hoặc OIDC (Google, Okta) trước khi request tới app. ALB chèn header X-Forwarded-For để app biết IP thật của client. Có security group.
  • Network Load Balancer (NLB): layer 4, TCP/UDP/TLS, chịu được hàng triệu request mỗi giây với độ trễ rất thấp (khoảng 100 ms so với khoảng 400 ms của ALB, cần kiểm tra lại). Mỗi AZ có một IP tĩnh, gắn được Elastic IP của bạn. Đây là loại duy nhất có static IP. Preserve source IP của client khi target là instance. Là điểm vào cho PrivateLink (endpoint service). Có thể đặt ALB làm target của NLB để vừa có IP tĩnh vừa có route layer 7. NLB từ 2023 cũng có security group (cần kiểm tra lại).
  • Gateway Load Balancer (GWLB): layer 3, dùng giao thức GENEVE port 6081 để đẩy toàn bộ gói tin qua một đội appliance bên thứ ba (firewall, IDS/IPS, deep packet inspection của Palo Alto, Fortinet…) rồi trả lại. Deploy "bump in the wire", transparent với app. Dùng với Gateway Load Balancer endpoint ở VPC khác.
  • Classic Load Balancer (CLB): thế hệ cũ, layer 4 và 7 sơ sài, một target group, không host/path routing. Đề thi chỉ cần nhận diện: khi thấy CLB trong đáp án thì gần như luôn là đáp án sai, chọn ALB hoặc NLB.

Kiểm tra nhanh

1. Một công ty có app chạy trên EC2 phía sau ALB. Đối tác yêu cầu whitelist IP của app trên firewall của họ, nhưng IP của ALB thay đổi. Giải pháp least operational overhead?

Đặt NLB với Elastic IP ở trước, dùng ALB làm target của NLB. Giữ được path routing của ALB mà vẫn có IP tĩnh. Thay ALB bằng NLB hoàn toàn thì mất rule layer 7. Global Accelerator cũng cho 2 IP tĩnh và là đáp án đúng nếu đề nói người dùng toàn cầu, nhưng với "đối tác whitelist" thì NLB + EIP là đủ và rẻ hơn.

2. Security Group của EC2 phía sau ALB nên có inbound rule nào để most secure?

Cho port 80 (hoặc 443) với source là Security Group của ALB. Mở 0.0.0.0/0 là sai vì ai biết private IP qua VPN cũng truy cập thẳng được. Dùng CIDR của public subnet cũng không chặt bằng SG id vì mọi máy trong subnet đó đều lọt.

3. NLB có 2 target ở AZ 1a và 6 target ở AZ 1c, cross-zone đang tắt. Người dùng phàn nàn một số request chậm. Vì sao và sửa thế nào?

Mỗi node NLB chỉ gửi tới target trong AZ của nó, nên 2 target ở 1a gánh 50% traffic. Bật cross-zone load balancing (chấp nhận phí data transfer giữa AZ) hoặc cân lại số instance. Với ALB câu này không xảy ra vì cross-zone mặc định bật.

4. Công ty muốn mọi traffic ra vào các VPC đều đi qua firewall của Palo Alto chạy trên EC2, quản lý tập trung, trong suốt với ứng dụng. Chọn dịch vụ nào?

Gateway Load Balancer với Gateway Load Balancer endpoint ở mỗi VPC. NLB cũng chia tải được nhưng không có GENEVE để trả gói tin về đúng chỗ, phải sửa route phức tạp. AWS Network Firewall là firewall managed của AWS, không chạy appliance bên thứ ba.

EC2 Auto Scaling

Giải thích ngắn

Auto Scaling Group (ASG) giữ cho số EC2 luôn nằm giữa min và max, hướng tới desired. Nó tự thay instance hỏng (self-healing), rải instance đều qua các AZ đã chọn, và tăng giảm số máy theo scaling policy. ASG miễn phí, chỉ trả tiền EC2. ASG cần một bản mô tả máy để tạo instance: launch template.

  • Launch template so với launch configuration: launch configuration là loại cũ, bất biến, mỗi lần đổi phải tạo cái mới, không hỗ trợ mixed instance type và Spot kết hợp, AWS đã ngừng cho tạo mới trong console từ 2023 (cần kiểm tra lại). Launch template có version, hỗ trợ nhiều instance type, Spot + On-Demand trộn trong một ASG, T2/T3 Unlimited, placement group, dedicated host. Đề thi: luôn chọn launch template.
  • min / desired / max: ví dụ 2 / 2 / 10. Desired là số ASG đang cố giữ; scaling policy thay đổi desired trong khoảng [min, max]. Đặt min 2 ở 2 AZ để chịu lỗi một AZ.
  • Health check: mặc định kiểu EC2 (instance status check). Khi ASG đứng sau ELB, bật thêm kiểu ELB để ASG thay cả instance mà app treo nhưng OS vẫn sống. Instance unhealthy bị terminate và tạo mới, không sửa.
  • AZ rebalance: nếu một AZ có nhiều instance hơn (do AZ khác từng hỏng), ASG tạo máy ở AZ ít trước rồi mới terminate ở AZ nhiều, nên có lúc tạm vượt desired tối đa 10%.
  • Termination policy mặc định khi scale in: chọn AZ có nhiều instance nhất → instance dùng launch template cũ nhất → instance gần giờ tính tiền tiếp theo nhất. Có thể đổi sang OldestInstance, NewestInstance, hoặc scale-in protection cho instance đang xử lý job dài.

Lifecycle hook
  • Chèn một trạng thái chờ vào vòng đời: Pending:Wait khi tạo, Terminating:Wait khi xóa. Instance đứng ở đó tối đa 1 giờ (mặc định, có thể tới 48 giờ) chờ bạn gọi complete-lifecycle-action hoặc hết giờ.
  • Dùng khi: cài phần mềm, tải cấu hình, đăng ký vào hệ thống khác trước khi nhận traffic; hoặc đẩy log ra S3, rút khỏi cluster, hoàn tất job trước khi terminate.
  • Thông báo hook qua EventBridge, SNS, SQS; xử lý bằng Lambda hoặc Systems Manager.
  • Khác deregistration delay: hook là của ASG (toàn bộ instance), deregistration delay là của ELB (chỉ chờ request HTTP đang mở).
Warm pool
  • Bể instance đã khởi tạo sẵn ở trạng thái Stopped (không tốn compute, chỉ tốn EBS), Hibernated hoặc Running. Khi scale out, ASG lấy từ pool nên vào service trong vài chục giây thay vì vài phút.
  • Dùng khi đề nói application takes long to initialize, reduce scale-out latency, pre-initialized instances.
  • Khác predictive scaling: warm pool giảm thời gian mỗi lần scale, predictive giảm việc scale muộn bằng dự báo.

Kiểm tra nhanh

5. Một web app có traffic tăng mạnh mỗi sáng từ 9 giờ và giảm sau 18 giờ, ngày nào cũng vậy. ASG hiện dùng target tracking nhưng sáng nào người dùng cũng bị chậm trong 15 phút đầu. Cách sửa most cost-effective?

Thêm scheduled scaling tăng desired lúc 8:45 (hoặc predictive scaling kết hợp target tracking). Tăng min lên cao cả ngày thì tốn tiền ban đêm. Giảm cooldown không giúp vì vấn đề là scale muộn chứ không phải scale chậm. Warm pool cũng giảm thời gian vào service nhưng với lịch cố định thì scheduled đơn giản và rẻ hơn.

6. Instance trong ASG phải upload log cục bộ lên S3 trước khi bị terminate khi scale in. Làm thế nào?

Lifecycle hook ở trạng thái Terminating:Wait, script hoặc Lambda upload log rồi gọi complete-lifecycle-action. Tăng deregistration delay của ALB chỉ giữ kết nối HTTP, không chạy script. Scale-in protection thì instance không bao giờ bị xóa, sai mục đích.

7. ASG đứng sau ALB. Một instance có process web bị treo, OS vẫn chạy bình thường. ALB báo target unhealthy nhưng ASG không thay instance. Vì sao?

ASG đang dùng health check type EC2 (mặc định), chỉ nhìn status check của instance. Đổi sang health check type ELB (kèm grace period đủ dài để app khởi động) thì ASG sẽ terminate và thay instance mà ALB báo unhealthy.

8. Worker đọc job từ SQS. Số job biến động, CPU của worker không phản ánh đúng tải. Scale ASG theo gì?

Metric tùy chỉnh "backlog per instance" = ApproximateNumberOfMessagesVisible chia số instance InService, rồi target tracking theo metric này. Scale theo CPU là sai vì đề đã nói CPU không phản ánh. Scheduled sai vì tải không theo lịch.

Route 53: DNS, routing policy, health check

Giải thích ngắn

Route 53 là DNS managed của AWS, dịch vụ global, SLA 100%. Nó làm ba việc: đăng ký domain (registrar), hosted zone chứa record trả lời truy vấn DNS, và health check để đổi câu trả lời khi endpoint hỏng. Tên "53" là port của DNS.

  • Public hosted zone: trả lời cho Internet (example.com). Private hosted zone: chỉ trả lời cho truy vấn từ trong các VPC đã gắn (db.internal), cần VPC bật enableDnsHostnames và enableDnsSupport. Mỗi hosted zone khoảng 0,50 USD/tháng (cần kiểm tra lại).
  • Record type: A (tên → IPv4), AAAA (tên → IPv6), CNAME (tên → tên khác, không dùng được ở apex như example.com), NS (name server của zone, Route 53 cấp 4 cái), SOA (thông tin zone), MX, TXT (xác minh domain, SPF), SRV, PTR.
  • Alias record: mở rộng riêng của Route 53, trỏ tên tới resource AWS (ALB, NLB, CloudFront, API Gateway, S3 website endpoint, Elastic Beanstalk, Global Accelerator, record khác cùng zone). Ưu điểm: dùng được ở apex domain, miễn phí truy vấn, tự theo IP của resource khi đổi, có thể bật Evaluate target health. Nhược: không trỏ được tới EC2 DNS name hay DNS ngoài AWS, không đặt TTL (lấy TTL của resource).
  • TTL: thời gian resolver cache câu trả lời. TTL cao (24 giờ) giảm tiền truy vấn nhưng đổi IP mất lâu; TTL thấp (60 giây) đổi nhanh, tốn tiền hơn. Trước khi migrate, giảm TTL trước vài ngày rồi mới đổi record.
  • Domain registration: Route 53 mua được domain, tự tạo hosted zone. Domain mua ở GoDaddy vẫn dùng Route 53 làm DNS bằng cách đổi NS ở registrar sang 4 NS của hosted zone. Ngược lại domain mua ở Route 53 cũng trỏ NS sang DNS khác được.

Health check
  • Endpoint health check: khoảng 15 health checker toàn cầu gọi IP hoặc domain của bạn qua HTTP/HTTPS/TCP mỗi 30 giây (hoặc 10 giây, đắt hơn). Healthy nếu trên 18% checker báo OK (cần kiểm tra lại).   • Calculated health check: gộp nhiều health check con bằng AND / OR / "ít nhất N trong M healthy". Dùng cho hệ thống nhiều thành phần.
  • CloudWatch alarm health check: healthy theo trạng thái một alarm. Đây là cách kiểm tra resource private (RDS, EC2 trong private subnet): tạo alarm trên metric rồi health check theo alarm.

  • Evaluate target health ở alias record: thay cho health check riêng, Route 53 hỏi trạng thái của ALB/NLB (healthy khi có ít nhất một target healthy). Không cần tạo health check tốn tiền.

  • Active-passive: chỉ primary nhận, secondary đứng chờ. Làm bằng failover routing. Secondary có thể là S3 static website (trang "đang bảo trì"), hoặc stack ở Region khác (DR pilot light, warm standby, học tuần 9).
  • Lồng nhau: failover ở ngoài, trong primary lại dùng weighted giữa hai ALB. Route 53 cho phép record trỏ tới record khác (alias cùng zone) để xây cây.

  • Inbound endpoint: ENI trong VPC có IP, để DNS server on-premises forward truy vấn tên AWS (db.internal) vào VPC qua VPN/DX.
  • Outbound endpoint + Resolver rule (forward rule): VPC forward truy vấn corp.local tới DNS server on-premises.
  • Đề nói resolve on-premises hostnames from VPC → outbound; on-premises servers resolve AWS private names → inbound; hai chiều → cả hai.

CloudFront: CDN ở Edge location

Giải thích ngắn

CloudFront là CDN của AWS: một distribution có DNS name dạng d123.cloudfront.net, nhận request ở Edge location gần người dùng (hơn 600 điểm, cần kiểm tra lại), trả từ cache nếu có, không thì về origin lấy rồi cache lại. Lợi ích: giảm độ trễ, giảm tải và chi phí data transfer của origin, chặn DDoS lớp 3/4 bằng Shield Standard, gắn WAF cho lớp 7. Dịch vụ global, cấu hình ở us-east-1.

  • Origin: S3 bucket (phổ biến nhất, kể cả S3 static website endpoint nhưng khi đó coi là custom origin), ALB, EC2 với public IP, API Gateway, MediaStore, bất kỳ HTTP server nào (custom origin, kể cả on-premises). Một distribution nhiều origin, chọn origin theo path pattern của cache behavior (/api/* → ALB, /* → S3).
  • Origin group: primary và secondary origin, CloudFront tự chuyển sang secondary khi primary trả lỗi 500/502/503/504 hoặc 403/404 (tùy chọn). Dùng cho origin failover giữa hai bucket ở hai Region (kết hợp S3 Cross-Region Replication).
  • Cache behavior: quy tắc cho một path pattern: origin nào, viewer protocol (redirect HTTP → HTTPS), method cho phép (GET/HEAD hay cả PUT/POST), cache policy, origin request policy, có cần signed URL không, gắn function nào.
  • TTL: origin gửi Cache-Control: max-age thì CloudFront theo, trong giới hạn min/max TTL của cache policy. Không có header thì dùng default TTL (24 giờ). Muốn bỏ cache ngay: invalidation (/images/*, tính tiền sau 1000 path mỗi tháng) hoặc đổi tên file có version (app.v2.js, cách khuyến nghị).

Cache policy và origin request policy
  • Cache policy quyết định cache key: URL cộng những header, cookie, query string nào. Cache key càng nhiều thành phần thì càng ít cache hit. Dùng managed policy CachingOptimized cho tĩnh, CachingDisabled cho API động.
  • Origin request policy: những header/cookie/query string được chuyển tiếp tới origin nhưng không nằm trong cache key. Ví dụ forward Authorization hay CloudFront-Viewer-Country cho app mà không làm vỡ cache.
  • Response headers policy: thêm CORS, security header (HSTS, CSP) ở Edge.
  • Đề nói cache hit ratio low → bỏ bớt header/cookie/query khỏi cache key, tăng TTL, hợp nhất origin.
Chạy code ở Edge
  • CloudFront Functions: JavaScript cực nhẹ, chạy ở hơn 200 Edge location, dưới 1 ms, chỉ ở viewer request / viewer response. Dùng cho rewrite URL, redirect, thêm header, kiểm tra JWT đơn giản, chuẩn hóa cache key. Rẻ hơn Lambda@Edge nhiều.
  • Lambda@Edge: Lambda (Node.js, Python) chạy ở Regional Edge Cache, tới 5 giây (viewer) hoặc 30 giây (origin), có 4 điểm: viewer request, origin request, origin response, viewer response. Có thể gọi dịch vụ khác, đọc body. Tạo ở us-east-1 rồi replicate.
  • Chọn: xử lý nhẹ, tần suất cao → CloudFront Functions. Cần network call, thao tác body, origin request/response → Lambda@Edge.

  • Viewer protocol policy: HTTP and HTTPS / Redirect HTTP to HTTPS / HTTPS only. Origin protocol policy: HTTP only (S3 bucket origin luôn HTTPS), HTTPS only, match viewer.
  • Price class: All (mọi Edge), 200 (bỏ nhóm đắt nhất như Nam Mỹ, Úc), 100 (chỉ Bắc Mỹ và châu Âu). Đề nói reduce CloudFront cost, users mostly in US and Europe → Price Class 100.
  • Data transfer từ S3 / EC2 ra CloudFront miễn phí; CloudFront ra người dùng tính tiền nhưng rẻ hơn S3 ra Internet trực tiếp. Nên đặt CloudFront trước S3 cả khi không cần cache chỉ để giảm phí egress và chống DDoS.
  • Hỗ trợ HTTP/2, HTTP/3 (QUIC), IPv6, WebSocket, gRPC. Có thể dùng cho nội dung động (API) với TTL 0 để tận dụng mạng backbone AWS từ Edge về origin.

AWS Global Accelerator (GA) cấp cho ứng dụng 2 địa chỉ IP tĩnh anycast được quảng bá từ mọi Edge location. Người dùng kết nối tới Edge gần nhất, rồi traffic đi trên mạng backbone của AWS (không qua Internet công cộng) tới endpoint ở Region: ALB, NLB, EC2, Elastic IP. GA không cache, không hiểu HTTP, chỉ chuyển gói TCP/UDP nhanh và ổn định hơn.

  • Accelerator → listener (port, TCP/UDP) → endpoint group theo Region (có traffic dial 0 đến 100% để chia hoặc tắt một Region) → endpoint với weight. Health check liên tục, endpoint hỏng thì chuyển trong khoảng dưới 30 giây đến 1 phút, không phụ thuộc TTL DNS của client (cần kiểm tra lại số giây).
  • Vì IP không đổi nên khách hàng whitelist một lần. Có thể mang IP của bạn (BYOIP). Hai IP thuộc hai network zone độc lập, một IP sập thì client dùng IP còn lại.
  • Client IP preservation: với ALB và EC2 endpoint, GA giữ IP thật của client; với NLB thì tùy cấu hình (cần kiểm tra lại).
  • Tích hợp Shield Standard. Giá: phí cố định theo giờ cộng phí theo GB vượt qua, cao hơn CloudFront cho nội dung tĩnh.
  • Phù hợp: gaming (UDP), VoIP, IoT (MQTT qua TCP), API nội dung động, ứng dụng cần deterministic failover giữa nhiều Region, ứng dụng không HTTP.

19. Ứng dụng HTTPS ở hai Region, mỗi Region một ALB. Yêu cầu: client dùng một địa chỉ cố định, khi một Region sập thì chuyển sang Region kia trong dưới 1 phút. Chọn gì?

Lab 1. ALB trước Auto Scaling Group 2 AZ, target tracking CPU 50%

  1. Tạo Security Group cho ALB (saa-alb-sg: inbound HTTP 80 từ 0.0.0.0/0) và cho web server (saa-web-sg: inbound HTTP 80 với source là saa-alb-sg, không mở 0.0.0.0/0):

    $env:AWS_PROFILE = "saa"
$VPC = (aws ec2 describe-vpcs --filters Name=tag:Name,Values=saa-vpc --query "Vpcs[0].VpcId" --output text)
$ALBSG = aws ec2 create-security-group --group-name saa-alb-sg --description "ALB" --vpc-id $VPC --query GroupId --output text
aws ec2 authorize-security-group-ingress --group-id $ALBSG --protocol tcp --port 80 --cidr 0.0.0.0/0
$WEBSG = aws ec2 create-security-group --group-name saa-web-sg --description "web behind ALB" --vpc-id $VPC --query GroupId --output text
aws ec2 authorize-security-group-ingress --group-id $WEBSG --protocol tcp --port 80 --source-group $ALBSG

  2. Tạo file userdata.sh cài Apache và in ra AZ của instance (lấy từ IMDSv2):

    #!/bin/bash
dnf install -y httpd stress-ng
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
AZ=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/placement/availability-zone)
ID=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/instance-id)
echo "<h1>Hello from $ID in $AZ</h1>" > /var/www/html/index.html
systemctl enable --now httpd

    Lưu file với line ending LF (trong VS Code chọn LF ở góc phải dưới), nếu CRLF thì script lỗi ở dòng đầu.

  3. Console → EC2 → Launch Templates → Create launch template. Name saa-web-lt, tick Provide guidance to help me set up a template that I can use with EC2 Auto Scaling. AMI: Amazon Linux 2023, instance type t3.micro, key pair của tuần 2 (hoặc không cần vì sẽ dùng Session Manager), không chọn subnet (ASG sẽ chọn), Security group saa-web-sg. Advanced details: IAM instance profile là role có AmazonSSMManagedInstanceCore (tạo ở tuần 2, nếu chưa có thì tạo), User data dán nội dung userdata.sh. Create.

  4. EC2 → Target Groups → Create: type Instances, name saa-web-tg, HTTP 80, VPC saa-vpc, Health check path /, Advanced: healthy threshold 2, interval 10 giây để lab chạy nhanh. Không đăng ký instance nào, Create.

  5. EC2 → Load Balancers → Create → Application Load Balancer: name saa-alb, Internet-facing, IPv4, VPC saa-vpc, chọn 2 public subnet ở 2 AZ, Security group saa-alb-sg (bỏ default), Listener HTTP 80 → forward saa-web-tg. Create. Ghi lại DNS name dạng saa-alb-xxxx.ap-northeast-1.elb.amazonaws.com.

  6. EC2 → Auto Scaling Groups → Create: name saa-web-asg, launch template saa-web-lt. Network: VPC saa-vpc, chọn 2 private subnet. Load balancing: Attach to an existing load balancer → chọn saa-web-tg. Health checks: tick Turn on Elastic Load Balancing health checks, grace period 120. Group size: desired 2, min 2, max 4. Scaling policies: Target tracking, metric Average CPU utilization, target value 50, instance warmup 120. Create.

  7. Chờ 2 đến 3 phút rồi kiểm tra:

    aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names saa-web-asg --query "AutoScalingGroups[0].Instances[].[InstanceId,AvailabilityZone,HealthStatus,LifecycleState]" --output table
$TG = aws elbv2 describe-target-groups --names saa-web-tg --query "TargetGroups[0].TargetGroupArn" --output text
aws elbv2 describe-target-health --target-group-arn $TG --query "TargetHealthDescriptions[].[Target.Id,TargetHealth.State]" --output table

    Mong đợi: 2 instance ở 2 AZ khác nhau, cả hai healthy. Nếu unhealthy lâu: kiểm tra NAT Gateway (instance không cài được httpd), SG saa-web-sg có cho từ saa-alb-sg, user data có bị CRLF.

  8. Mở DNS name của ALB trên trình duyệt, bấm F5 nhiều lần: dòng chữ đổi giữa hai instance id và hai AZ. Đây là bằng chứng ALB chia tải qua 2 AZ và cross-zone đang bật. Thử mở private IP của một instance thì không vào được, vì SG chỉ cho từ ALB.

  9. Thí nghiệm self-healing: terminate một instance bằng tay (aws ec2 terminate-instances --instance-ids i-xxx). Sau 1 đến 2 phút ASG tạo instance mới ở đúng AZ bị thiếu. Xem tab Activity của ASG để thấy dòng "launching a new EC2 instance" với lý do.

Lab 2. Stress test bằng stress-ng, xem ASG scale out rồi scale in

  1. Vào một instance bằng Session Manager (EC2 → chọn instance → Connect → Session Manager, cần role SSM ở Lab 1; không cần bastion hay mở port 22). Chạy tải CPU 100% trong 10 phút:

    sudo stress-ng --cpu 2 --timeout 600s &
top    # thấy CPU gần 100%, bấm q để thoát

    Nếu chưa cài stress-ng (user data lỗi): sudo dnf install -y stress-ng.

  2. Làm tương tự trên instance thứ hai để CPU trung bình của ASG vượt 50% (target tracking tính trung bình toàn nhóm, một máy 100% và một máy 0% chỉ là 50%).

  3. Xem CloudWatch: CloudWatch → Alarms có 2 alarm tự tạo tên dạng TargetTracking-saa-web-asg-AlarmHigh-... và AlarmLow-.... AlarmHigh cần 3 datapoint liên tiếp trên 50% (mỗi datapoint 1 phút) mới In alarm. Hoặc theo dõi bằng CLI:

    aws cloudwatch get-metric-statistics --namespace AWS/EC2 --metric-name CPUUtilization --dimensions Name=AutoScalingGroupName,Value=saa-web-asg --start-time (Get-Date).AddMinutes(-15).ToUniversalTime().ToString("yyyy-MM-ddTHH:mm:ssZ") --end-time (Get-Date).ToUniversalTime().ToString("yyyy-MM-ddTHH:mm:ssZ") --period 60 --statistics Average --query "Datapoints[].[Timestamp,Average]" --output table

  4. Sau khoảng 3 đến 5 phút, tab Activity của ASG hiện "Launching a new EC2 instance ... in response to alarm AlarmHigh". Desired tăng từ 2 lên 3 hoặc 4. Quan sát instance mới đi qua Pending → InService, và trong 120 giây warm-up không bị tính vào metric.

    aws autoscaling describe-scaling-activities --auto-scaling-group-name saa-web-asg --max-items 5 --query "Activities[].[StartTime,StatusCode,Cause]" --output table

  5. Khi stress-ng hết 600 giây, CPU về gần 0. AlarmLow cần 15 datapoint liên tiếp dưới ngưỡng (khoảng 15 phút) để tránh scale in vội. Sau đó ASG terminate instance về desired 2, chọn theo termination policy mặc định (AZ có nhiều instance hơn trước). Xem lại Activity và mục Instance management.

  6. Ghi lại vào sổ tay: thời gian từ lúc bắt đầu stress tới lúc instance mới healthy (thường 4 đến 7 phút), thời gian từ lúc hết tải tới lúc scale in (khoảng 15 phút). Đây là lý do đề thi nói scale out fast, scale in slow và vì sao có warm pool, predictive scaling.

Nếu không thấy scale out: kiểm tra max của ASG lớn hơn desired, CPU trung bình thật sự vượt 50% (chạy stress cả 2 máy), và alarm đã sang trạng thái In alarm. Target tracking dùng alarm 3 phút nên không phản ứng tức thì.

Lab 3. Route 53 failover với health check

Lab này có hai cách. Cách A cần một domain đang do Route 53 quản lý (mua trên Route 53 khoảng 13 USD/năm cho .com, hoặc domain có sẵn trỏ NS về Route 53). Cách B không cần domain: chỉ tạo health check và quan sát trạng thái đổi, đủ để hiểu cơ chế nhưng không thấy DNS chuyển. Nếu không có domain thì làm cách B và ghi rõ trong checklist.

  1. Chuẩn bị hai endpoint public: primary là DNS name của ALB ở Lab 1. secondary là một S3 bucket bật static website hosting với index.html ghi "Site under maintenance" (tên bucket phải trùng tên record nếu dùng cách A, ví dụ www.example.com; với cách B đặt tên tùy ý). Bucket phải tắt Block Public Access và có bucket policy cho s3:GetObject public, đây là ngoại lệ hiếm hoi được phép public.

  2. Tạo health check cho primary: Route 53 → Health checks → Create. Name saa-alb-hc, Monitor an endpoint, Specify endpoint by Domain name, protocol HTTP, domain là DNS name của ALB, port 80, path /. Advanced: Request interval Fast (10 seconds), Failure threshold 2 để lab chuyển nhanh. Tạo thêm alarm SNS nếu muốn nhận email. Chờ 1 đến 2 phút, trạng thái phải là Healthy, tab Health checkers cho thấy từng checker toàn cầu báo OK.

  3. Cách A (có domain): vào hosted zone, tạo record www type A, routing policy Failover, Failover record type Primary, Alias → Application Load Balancer → chọn saa-alb, Health check saa-alb-hc (hoặc bật Evaluate target health), Record ID primary. Tạo record www thứ hai, Failover Secondary, Alias → S3 website endpoint → chọn bucket, Record ID secondary. Mở http://www.example.com thấy trang từ ALB.

Resolve-DnsName www.example.com -Server 8.8.8.8 -Type A

  4. Làm primary hỏng: cách nhanh nhất là bỏ rule inbound 80 khỏi saa-alb-sg (health checker bị chặn), hoặc đặt desired/min của ASG về 0 để ALB không còn target. Không terminate instance bằng tay vì ASG sẽ tạo lại trong 1 phút.

    aws ec2 revoke-security-group-ingress --group-id $ALBSG --protocol tcp --port 80 --cidr 0.0.0.0/0

Cách A: chạy lại nslookup, câu trả lời đổi sang IP của S3 website; trình duyệt mở lại thấy "Site under maintenance" (có thể phải chờ TTL 60 giây của alias và xóa cache DNS bằng ipconfig /flushdns). Cách B: chỉ quan sát trạng thái health check và thời gian chuyển, ghi lại số giây, rồi đọc kỹ mô tả cách A để hình dung DNS đổi.

  6. Khôi phục: thêm lại rule 80 cho saa-alb-sg (hoặc đưa desired về 2). Health check về Healthy và DNS quay lại primary. Route 53 luôn ưu tiên primary khi nó healthy, không có "failback thủ công".

Lab 4. CloudFront trước S3 private bằng OAC, truy cập thẳng S3 phải bị 403

  1. Tạo bucket private (giữ Block Public Access bật, không bật static website hosting) và upload một file:

    $B = "saa-cf-quy-2026"    # đổi hậu tố cho duy nhất
aws s3 mb s3://$B --region ap-northeast-1
"<h1>Served via CloudFront</h1>" | Out-File -Encoding ascii index.html
aws s3 cp index.html s3://$B/index.html --content-type text/html
curl.exe -I https://$B.s3.ap-northeast-1.amazonaws.com/index.html    # mong đợi HTTP 403

  2. Console → CloudFront → Create distribution. Origin domain: chọn bucket (dạng saa-cf-quy-2026.s3.ap-northeast-1.amazonaws.com, không chọn website endpoint). Origin access: Origin access control settings (recommended) → Create new OAC, giữ mặc định Sign requests. Viewer protocol policy: Redirect HTTP to HTTPS. Cache policy: CachingOptimized. WAF: tắt để không tốn tiền. Default root object: index.html. Price class: Use only North America and Europe nếu muốn thấy tác dụng của price class (Tokyo sẽ chậm hơn một chút), hoặc All. Create.

  3. Sau khi tạo, CloudFront hiện banner "The S3 bucket policy needs to be updated" với nút Copy policy. Policy có dạng:

    {
  "Version": "2008-10-17",
  "Statement": [{
    "Sid": "AllowCloudFrontServicePrincipalReadOnly",
    "Effect": "Allow",
    "Principal": { "Service": "cloudfront.amazonaws.com" },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::saa-cf-quy-2026/*",
    "Condition": { "StringEquals": { "AWS:SourceArn": "arn:aws:cloudfront::<account-id>:distribution/E1XXXXXXXX" } }
  }]
}

    Dán vào S3 → bucket → Permissions → Bucket policy. Để ý: principal là dịch vụ CloudFront, condition khóa đúng một distribution, bucket vẫn Block Public Access.

  4. Chờ distribution từ "Deploying" sang "Enabled" (5 đến 10 phút). Kiểm tra:

    $D = "d1234abcd.cloudfront.net"    # Distribution domain name
curl.exe -I https://$D/index.html     # 200, có header x-cache: Miss from cloudfront
curl.exe -I https://$D/index.html     # 200, x-cache: Hit from cloudfront
curl.exe -I https://$B.s3.ap-northeast-1.amazonaws.com/index.html    # vẫn 403

    Hai dòng x-cache Miss rồi Hit là bằng chứng Edge đã cache. Dòng cuối 403 là mốc của lab: chỉ CloudFront đọc được bucket.

  5. Thử invalidation: sửa index.html thành "v2", upload lại, curl vẫn thấy bản cũ (TTL 24 giờ). Tạo invalidation:

    aws cloudfront create-invalidation --distribution-id E1XXXXXXXX --paths "/index.html"
curl.exe https://$D/index.html    # sau 1 đến 2 phút thấy v2

  6. Tùy chọn nâng cao nếu còn thời gian: tạo key group (CloudFront → Key management → Public keys, upload public key RSA 2048 tạo bằng ssh-keygen -t rsa -b 2048 -m PEM), bật Restrict viewer access ở default behavior với key group đó, curl lại thấy 403 MissingKey. Đây là signed URL; không cần làm bước ký URL, chỉ cần thấy cơ chế chặn.

CloudFront không có phí cố định theo giờ nhưng vẫn tính request và data. Distribution phải Disable rồi chờ Deployed mới Delete được, làm ở Lab 5. Nếu để lại thì gần như không tốn tiền khi không có traffic, nhưng vẫn nên xóa cho sạch.

Mốc kiểm tra

Ba câu của tuần 5 và ba câu của tuần 4 phải tự nói được

Mốc kiểm tra trong AWS-SAA-checklist.md tính chung cho cả khối tuần 4 đến 5. Ba mốc đầu là của tuần này, ba mốc sau nhắc lại từ tuần 4, phải nói được cả sáu trước khi làm quiz.

1. Luồng request: người dùng → Route 53 → CloudFront → ALB → ASG → EC2 private

Gợi ý khung trả lời (che lại rồi tự nói):

  • Trình duyệt hỏi DNS www.example.com; resolver tới NS của Route 53; record alias trả về IP của Edge CloudFront gần nhất (có thể qua latency / failover policy).
  • Client bắt tay TLS với Edge bằng chứng chỉ ACM us-east-1; CloudFront tra cache theo cache key; hit thì trả ngay.
  • Miss: CloudFront đi backbone AWS về origin ALB (Internet-facing ở public subnet), kèm custom header; SG của ALB chỉ cho CloudFront prefix list.
  • ALB listener 443 chạy rule host/path, chọn target group, chỉ gửi tới target healthy; SG của EC2 chỉ cho từ SG của ALB.
  • EC2 ở private subnet do ASG giữ min 2 ở 2 AZ, scale theo target tracking; không có public IP; ra Internet qua NAT Gateway (tuần 4).
  • Response đi ngược lại, CloudFront cache theo TTL, trả cho client. Nêu được một điểm chịu lỗi ở mỗi lớp: Route 53 health check, origin group, multi-AZ ALB, ASG self-healing.

2. Chọn đúng routing policy Route 53 theo tình huống

Gợi ý khung trả lời:

  • Hỏi hai câu: đề quan tâm tỷ lệ, hiệu năng, vị trí, hay dự phòng?
  • Tỷ lệ (canary, blue/green, A/B) → weighted. Hiệu năng toàn cầu nhiều Region → latency.
  • Vị trí người dùng (luật, ngôn ngữ) → geolocation. Vị trí resource cộng bias để nắn traffic → geoproximity.
  • Active-passive, DR, trang bảo trì → failover. Nhiều IP healthy không cần ELB → multi-value. Một server → simple.
  • Nhớ kèm: alias cho apex và resource AWS, health check cho private resource là CloudWatch alarm, Evaluate target health với ELB.

3. Chọn ALB, NLB hay Global Accelerator theo từ khóa đề

Gợi ý khung trả lời:

  • Thấy HTTP, path/host routing, microservices, Lambda target, Cognito, WebSocket → ALB.
  • Thấy static IP trong một Region, TCP/UDP, millions of requests, PrivateLink, preserve source IP → NLB.
  • Thấy global users + static anycast IP, UDP gaming / VoIP, fast failover between Regions, non-HTTP → Global Accelerator (đứng trước ALB/NLB, không thay thế).
  • Thấy cache, static content, S3, signed URL → CloudFront, không phải GA. Thấy third-party appliance → GWLB.
  • Kết hợp: NLB → ALB khi cần cả IP tĩnh lẫn layer 7; GA → ALB khi nhiều Region.

Nhắc lại tuần 4: vẽ VPC, gói tin ra Internet, SG với NACL

Ba mốc của tuần 4 trong checklist, nói lại ngắn:

  • Vẽ VPC trên giấy: CIDR, 2 AZ, mỗi AZ một public và một private subnet, IGW gắn VPC, NAT Gateway ở public subnet, route table public (0.0.0.0/0 → IGW) và private (0.0.0.0/0 → NAT), gateway endpoint S3. Tuần này thêm ALB ở public subnet, ASG ở private subnet.
  • Gói tin từ EC2 private ra Internet: EC2 → route table private → NAT Gateway (đổi source IP sang EIP của NAT) → route table public → IGW → Internet; chiều về qua NAT nhờ bảng dịch. IPv6 thì dùng Egress-only IGW.
  • SG với NACL: SG gắn ENI, stateful, chỉ Allow, đánh giá mọi rule; NACL gắn subnet, stateless (phải mở cả ephemeral port chiều về), có Deny, đánh giá theo số thứ tự. Ví dụ chặn một IP tấn công → NACL Deny; cho ALB vào EC2 → SG source là SG của ALB.
