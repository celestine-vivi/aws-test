Amazon RDS: Multi-AZ, Read Replica, backup, encryption, RDS Proxy

Giải thích ngắn
  • RDS là database quan hệ managed: AWS lo cài đặt, vá OS và engine, backup, Multi-AZ, monitoring. Bạn không SSH vào được máy, chỉ kết nối qua endpoint DNS. Engine: MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, Db2, cộng Aurora (học mục 2).
  • Mỗi DB instance chạy trên một instance class (db.t3.micro, db.m6g.large…), có EBS storage gp3 hoặc io1/io2, nằm trong một subnet group của VPC, mở cổng qua Security Group (MySQL 3306, PostgreSQL 5432, SQL Server 1433).
  • Storage autoscaling: đặt "maximum storage threshold", khi dung lượng còn dưới 10% RDS tự tăng, không downtime. Chỉ tăng được, không tự giảm.
  • RDS Custom (Oracle, SQL Server): bạn được quyền vào OS và DB để cài agent hoặc chỉnh sâu, đổi lại tự chịu một phần vận hành. Đề nói need OS access hoặc customize the database environment trên RDS → RDS Custom.

Multi-AZ DB cluster (loại mới, MySQL và PostgreSQL)
  • 1 writer + 2 reader standby ở 2 AZ khác, replication semi-synchronous (ghi được xác nhận khi ít nhất 1 standby nhận). Khác Multi-AZ instance ở chỗ standby đọc được, có reader endpoint riêng.
  • Failover nhanh hơn Multi-AZ instance (AWS nói thường dưới 35 giây, cần kiểm tra lại), độ trễ ghi thấp hơn vì chỉ chờ 1 standby.
  • Đề nói Multi-AZ with readable standbys, two readable standby instances → Multi-AZ DB cluster. Đừng nhầm với Aurora cluster.

Encryption và authentication
  • At rest bằng KMS: chỉ bật được lúc tạo instance. Đã tạo không mã hóa thì làm theo đường: chụp snapshot → copy snapshot và chọn mã hóa → restore từ snapshot đã mã hóa → trỏ app sang instance mới. Ngược lại, snapshot của DB mã hóa không copy thành bản không mã hóa được.
  • Read replica của DB mã hóa thì cũng mã hóa; không tạo replica mã hóa từ primary không mã hóa.
  • In transit: SSL/TLS, tải CA bundle của RDS; với MySQL/PostgreSQL có thể ép bằng parameter require_secure_transport hoặc rds.force_ssl.
  • IAM database authentication (MySQL, PostgreSQL, MariaDB): thay password bằng token do IAM cấp, sống 15 phút. EC2/Lambda dùng role, không giữ password. Đề nói avoid storing database passwords, use IAM to connect → IAM DB auth. Còn nếu đề nói rotate password automatically → Secrets Manager.
  • Transparent Data Encryption (TDE): cách mã hóa riêng của Oracle và SQL Server, có thể dùng cùng KMS encryption.
RDS Proxy và Performance Insights
  • RDS Proxy: lớp connection pooling managed đứng giữa app và DB. Giải quyết bài toán Lambda mở hàng nghìn connection làm DB hết connection ("too many connections"). Khi failover, proxy giữ connection phía app và chuyển sang instance mới nên downtime cảm nhận giảm tới 66% (số AWS công bố, cần kiểm tra lại). Dùng được với IAM auth và Secrets Manager. Chỉ truy cập được từ trong VPC, không public.
  • Performance Insights: dashboard xem DB load theo wait event, theo SQL, theo user, để biết câu lệnh nào gây tải. 7 ngày dữ liệu miễn phí. Đề nói identify the SQL statements causing high load → Performance Insights. Enhanced Monitoring là thứ khác: metric OS (CPU theo process, memory) mỗi 1 giây, lấy từ agent trên host.
Khi nào dùng RDS
  • Dữ liệu quan hệ, cần SQL, join, transaction, app sẵn có viết cho MySQL/PostgreSQL/Oracle/SQL Server và muốn lift and shift mà không muốn vận hành OS.
  • Không chọn RDS khi: cần quyền vào OS (EC2 tự cài hoặc RDS Custom), dữ liệu không quan hệ với lượng request cực lớn (DynamoDB), kho phân tích hàng TB (Redshift), hoặc cần scale ghi theo chiều ngang gần như vô hạn (RDS scale ghi chỉ bằng tăng instance class, có downtime ngắn).

Kiểm tra nhanh

1. Ứng dụng dùng RDS MySQL Single-AZ. Mỗi lần AWS bảo trì OS, app bị gián đoạn vài phút. Cách giảm gián đoạn với least operational overhead?

Bật Multi-AZ. RDS sẽ vá standby trước, failover, rồi vá primary cũ, app chỉ mất vài chục giây reconnect với cùng endpoint. Read Replica không giúp vì bảo trì primary vẫn gián đoạn ghi, và replica không tự nhận traffic.

2. RDS PostgreSQL được tạo không mã hóa, giờ compliance yêu cầu mã hóa at rest. Làm thế nào?

Chụp snapshot, copy snapshot với tùy chọn mã hóa KMS, restore thành instance mới, trỏ app sang. Không có cách bật encryption trên instance đang chạy. Tạo read replica mã hóa từ primary không mã hóa cũng không được.

3. Hàng trăm Lambda function gọi RDS MySQL, lỗi "Too many connections" xuất hiện lúc cao điểm. Chọn gì?

RDS Proxy. Proxy gom connection, chia sẻ lại cho Lambda, đồng thời giảm thời gian failover. Tăng max_connections hay instance class chỉ đẩy giới hạn, còn Lambda scale vẫn vượt. Read Replica không giúp vì vấn đề là số connection chứ không phải tải đọc.

4. Chọn 2 phát biểu đúng: (A) Standby của Multi-AZ instance phục vụ đọc, (B) Read Replica dùng async replication, (C) Automated backup giữ tối đa 35 ngày, (D) Restore từ snapshot ghi đè instance hiện tại.

B và C. A sai với Multi-AZ instance (chỉ Multi-AZ DB cluster mới có standby đọc được). D sai: restore luôn tạo instance mới với endpoint mới.

Amazon Aurora: cluster volume, endpoint, Global Database, Serverless

Giải thích ngắn
  • Aurora là engine quan hệ do AWS tự xây, tương thích MySQL và PostgreSQL (app kết nối như bình thường, driver không đổi). AWS công bố nhanh tới 5 lần MySQL và 3 lần PostgreSQL trên RDS, giá cao hơn RDS cùng cỡ khoảng 20% (cần kiểm tra lại).
  • Khác biệt gốc: storage tách khỏi compute. Dữ liệu nằm trong cluster volume chung, tự sao 6 bản trên 3 AZ (2 bản mỗi AZ). Ghi cần 4/6 bản xác nhận, đọc cần 3/6, nên mất cả một AZ vẫn đọc ghi được. Volume tự lớn theo bước 10 GB tới 128 TiB (cần kiểm tra lại), chỉ trả tiền dung lượng thực dùng.
  • Một cluster có 1 writer (primary) và tối đa 15 Aurora Replica đọc chung volume, nên replica lag thường dưới 100 ms (không phải copy dữ liệu như RDS Read Replica). Replica cũng chính là standby: failover sang replica mất khoảng 30 giây, thứ tự chọn theo priority tier 0 đến 15 (số nhỏ ưu tiên hơn, cùng tier thì chọn instance to hơn).
  • Backup liên tục lên S3, PITR tới giây, retention 1 đến 35 ngày, không ảnh hưởng hiệu năng. Mã hóa KMS cũng chỉ chọn lúc tạo.

Replica auto scaling, Global Database, Serverless v2
  • Aurora Replica auto scaling: đặt policy theo CPU trung bình hoặc số connection của replica, Aurora tự thêm bớt replica (trong giới hạn 15). Reader endpoint tự gồm replica mới. Đề nói read traffic varies throughout the day → replica auto scaling.
  • Aurora Global Database: 1 Region primary + tối đa 5 Region secondary (cần kiểm tra lại), replication ở tầng storage, lag thường dưới 1 giây. Mỗi secondary có tới 16 replica đọc. Khi Region primary sập: RPO khoảng 1 giây, RTO dưới 1 phút bằng cách promote secondary (managed failover hoặc detach). Dùng cho disaster recovery across Regions và low-latency global reads. Có write forwarding: app ở Region secondary gửi lệnh ghi, Aurora chuyển về primary.
  • Aurora Serverless v2: compute đo bằng ACU (Aurora Capacity Unit, 1 ACU khoảng 2 GiB RAM), scale tức thì từ 0,5 ACU lên tối đa theo bạn đặt, không ngắt kết nối khi scale. Trộn được instance thường và serverless trong cùng cluster, dùng được Global Database, Multi-AZ. Chọn khi unpredictable, intermittent, spiky workload, môi trường dev/test, pay only for capacity used. v1 cũ scale chậm và hay bị đề đưa ra làm mồi, nhớ tên "v2".

Kiểm tra nhanh

5. Aurora MySQL có 1 writer và 3 replica. App báo cáo đang trỏ vào instance endpoint của một replica, khi replica đó bị failover thành writer thì báo cáo làm chậm ghi. Sửa thế nào với ít thay đổi nhất?

Trỏ app báo cáo vào reader endpoint (hoặc custom endpoint chỉ gồm replica). Reader endpoint luôn loại writer ra, tự cân bằng giữa các replica. Instance endpoint gắn cứng vào một máy nên vai trò đổi là hỏng.

6. Công ty cần DB PostgreSQL phục vụ người dùng ở Tokyo và Frankfurt, đọc nhanh ở cả hai, và nếu Tokyo sập thì chuyển sang Frankfurt trong vài phút với RPO dưới 1 phút. Chọn gì?

Aurora PostgreSQL Global Database, primary Tokyo, secondary Frankfurt. RDS cross-Region Read Replica cũng đọc được ở Frankfurt nhưng lag lớn hơn và promote thủ công, không đạt RPO/RTO chặt. Multi-AZ chỉ trong một Region.

7. Developer chạy nhầm UPDATE không WHERE trên Aurora MySQL production 20 phút trước. Cách khôi phục fastest?

Backtrack cluster về trước thời điểm chạy lệnh. Vài phút, tại chỗ, không đổi endpoint. PITR cũng được nhưng tạo cluster mới rồi phải chuyển app, chậm hơn. Backtrack phải được bật từ trước (lúc tạo hoặc sửa cluster) và chỉ có trên Aurora MySQL.

DynamoDB: capacity, index, DAX, Streams, TTL, Global Table

Giải thích ngắn
  • DynamoDB: key-value và document NoSQL, serverless hoàn toàn (không instance, không patch), độ trễ một chữ số ms ở mọi quy mô, tự replicate 3 AZ, scale ghi và đọc gần như vô hạn. Luôn mã hóa at rest.
  • Primary key: hoặc chỉ partition key (hash, phải duy nhất), hoặc partition key + sort key (cặp phải duy nhất, cùng partition key có nhiều item sắp xếp theo sort key). Partition key quyết định item nằm ở partition vật lý nào, nên phải chọn khóa phân tán đều (user ID tốt, "status = active" xấu).
  • Item tối đa 400 KB. Object lớn (ảnh, file) để trên S3, DynamoDB lưu key S3 và metadata. Không có join, không có schema cố định ngoài key.
  • Truy vấn: Query (theo partition key, lọc sort key, rẻ) và Scan (đọc cả bảng, đắt, tránh). GetItem/PutItem theo khóa.

DAX, Streams, TTL
  • DAX (DynamoDB Accelerator): cache in-memory chuyên cho DynamoDB, tương thích API nên app chỉ đổi endpoint, không viết logic cache. Giảm đọc từ ms xuống microsecond, cache cả GetItem lẫn Query/Scan. Multi-AZ cluster tới 10 node. Chọn khi read-heavy, microsecond latency, reduce read cost, minimal code changes. Không cache ghi, không cache strongly consistent read. Nếu đề cần cache dùng chung cho nhiều nguồn hoặc cấu trúc như sorted set → ElastiCache (mục 4).
  • DynamoDB Streams: log thay đổi của bảng (insert, update, delete) theo thứ tự, giữ 24 giờ. Chọn view: KEYS_ONLY, NEW_IMAGE, OLD_IMAGE, NEW_AND_OLD_IMAGES. Thường nối Lambda trigger để làm: gửi thông báo khi có record mới, sao chép sang OpenSearch, tổng hợp số liệu, audit. Kinesis Data Streams for DynamoDB là lựa chọn thay thế: giữ tới 1 năm, nhiều consumer, nối Firehose; nhưng thứ tự không đảm bảo chặt và có thể trùng record.
  • TTL (Time to Live): chọn một attribute kiểu number chứa epoch giây; item quá hạn bị xóa trong vài ngày (thường trong 48 giờ, cần kiểm tra lại), không tốn WCU. Item quá hạn chưa xóa vẫn đọc thấy nếu không lọc. Record xóa bởi TTL xuất hiện trong Streams với userIdentity.principalId = dynamodb.amazonaws.com, nên phân biệt được với xóa thủ công. Dùng cho session, OTP, log tạm, dữ liệu phải xóa sau N ngày để giảm dung lượng.
Global Table, PITR, backup
  • Global Table: bảng replicate active-active nhiều Region, app đọc ghi ở Region gần nhất, lag thường dưới 1 giây. Bắt buộc bật Streams (NEW_AND_OLD_IMAGES). Xung đột ghi cùng item ở 2 Region giải quyết bằng last writer wins. Dùng cho multi-Region active-active, low latency for global users, Region failover for DynamoDB. Khác Aurora Global Database (một Region ghi).
  • Point-in-time recovery: bật là có backup liên tục 35 ngày, restore về bất kỳ giây nào ra bảng mới. On-demand backup: giữ vô thời hạn, không ảnh hưởng hiệu năng. Cả hai tích hợp AWS Backup, copy cross-Region và cross-account được.
  • Export to S3 (không tốn RCU) để phân tích bằng Athena. Import from S3 để nạp dữ liệu lớn.
Khi nào chọn DynamoDB
  • Đề nhấn serverless, single-digit millisecond, millions of requests per second, key-value, session state, shopping cart, IoT data, leaderboard with simple lookup, schema flexible, no database administration.
  • Không chọn khi đề cần join phức tạp, SQL ad hoc, transaction nhiều bảng rộng, hoặc item hơn 400 KB (trừ khi kết hợp S3). Khi đó RDS/Aurora. Phân tích hàng TB thì Redshift.

ElastiCache: Redis với Memcached, cache-aside và write-through

Giải thích ngắn
  • ElastiCache là cache in-memory managed, đặt trước database để giảm tải đọc và độ trễ xuống dưới 1 ms. Hai engine: Redis (và bản mở Valkey, tương thích Redis) và Memcached. Nằm trong VPC, truy cập qua Security Group, không public.

Redshift và Redshift Spectrum

Giải thích ngắn
  • Redshift là data warehouse (OLAP) managed, dựa trên PostgreSQL, lưu columnar (theo cột) và nén tốt nên quét hàng tỷ dòng cho truy vấn tổng hợp (SUM, GROUP BY) nhanh hơn RDS nhiều lần. Quy mô petabyte. Dùng cho báo cáo, BI (QuickSight, Tableau), không dùng cho OLTP (ghi từng dòng liên tục, transaction ngắn).
  • Kiến trúc cluster: 1 leader node nhận SQL, lập kế hoạch, gom kết quả; nhiều compute node chia dữ liệu thành slice và chạy song song (MPP, massively parallel processing). Node type RA3 tách compute và storage (dữ liệu trên S3 managed), DC2 SSD cục bộ cho dữ liệu nhỏ.
  • Nạp dữ liệu: lệnh COPY từ S3 (song song, nhanh nhất), từ DynamoDB, EMR, hoặc qua Kinesis Data Firehose. Không nên INSERT từng dòng.
  • Nằm trong một AZ (Multi-AZ mới có cho RA3, cần kiểm tra lại). HA kiểu Redshift: tự thay node hỏng, snapshot tự động lên S3 và có thể copy snapshot sang Region khác để DR. Đề nói disaster recovery for Redshift → cross-Region snapshot copy.
  • Enhanced VPC Routing: ép traffic COPY/UNLOAD đi trong VPC (qua endpoint) thay vì internet. Concurrency Scaling: tự thêm cluster tạm khi nhiều truy vấn đồng thời.
Redshift Spectrum và Redshift Serverless
  • Redshift Spectrum: chạy SQL trực tiếp trên file trong S3 (Parquet, ORC, CSV, JSON) mà không cần load vào cluster, join được với bảng bên trong Redshift. Cần có cluster Redshift đang chạy; bảng S3 định nghĩa qua external schema (Glue Data Catalog). Chọn khi đề nói query exabytes in S3 from Redshift, join historical data in S3 with warehouse data, without loading.
  • Redshift Serverless: không quản lý cluster, đo bằng RPU, tự scale, trả theo giây truy vấn chạy. Chọn khi ad hoc, intermittent analytics, no cluster management. Vẫn là Redshift (columnar, SQL, Spectrum dùng được).
  • Data sharing: chia sẻ dữ liệu live giữa các cluster/account không copy. Zero-ETL từ Aurora sang Redshift: replicate tự động để phân tích gần realtime, không viết pipeline.

DMS và Schema Conversion Tool

Giải thích ngắn
  • Database Migration Service (DMS): di chuyển dữ liệu từ DB nguồn sang DB đích khi nguồn vẫn đang chạy. Chạy trên một replication instance (EC2 do DMS quản lý, bạn chọn cỡ, có Multi-AZ) với source endpoint, target endpoint và migration task. Nguồn có thể on-premises, EC2, RDS, S3; đích là RDS, Aurora, DynamoDB, Redshift, S3, OpenSearch, Kinesis, DocumentDB…
  • Ba kiểu task: Full load (copy một lần), Full load + CDC (copy rồi tiếp tục đồng bộ thay đổi), CDC only. CDC (change data capture) đọc transaction log của nguồn để replicate liên tục với downtime gần bằng 0: app chuyển sang đích chỉ khi hai bên đã đồng bộ. Đề nói minimal downtime migration, continuous replication, keep source running → DMS với CDC.
  • Homogeneous (cùng engine, Oracle → Oracle, MySQL → Aurora MySQL): DMS làm trực tiếp. Heterogeneous (đổi engine, Oracle → Aurora PostgreSQL, SQL Server → MySQL): phải dùng SCT chuyển schema trước, rồi DMS chuyển dữ liệu.
  • Schema Conversion Tool (SCT): phần mềm cài trên máy, phân tích schema, stored procedure, view của nguồn và chuyển sang cú pháp engine đích, kèm báo cáo đánh giá phần nào phải sửa tay. SCT còn có extractor chuyển data warehouse (Oracle, Teradata, Netezza) sang Redshift. Nay có thể chạy SCT ngay trong console DMS (DMS Schema Conversion).
  • Dữ liệu lớn hoặc mạng yếu: DMS kết hợp Snowball Edge: SCT trích dữ liệu lên Snowball, ship về AWS, DMS load vào đích từ S3, rồi CDC đồng bộ phần thay đổi trong lúc vận chuyển. Đề nói terabytes, limited bandwidth, migrate database → DMS + Snowball.

    import json, os, time, uuid
import boto3

table = boto3.resource("dynamodb").Table(os.environ["TABLE"])

def lambda_handler(event, context):
    action = event.get("action", "write")
    user_id = event.get("userId", "quy")
    if action == "write":
        item = {"userId": user_id, "noteId": str(uuid.uuid4()),
                "body": event.get("body", "hello"), "createdAt": int(time.time())}
        if "ttlSeconds" in event:

        table.put_item(Item=item)
        return {"written": item}
    resp = table.query(KeyConditionExpression=boto3.dynamodb.conditions.Key("userId").eq(user_id))
    return {"count": resp["Count"], "items": resp["Items"]}

Mốc kiểm tra

Hai câu phải tự nói được không nhìn tài liệu

1. Chọn RDS, Aurora, DynamoDB hay ElastiCache theo đề bài?

Gợi ý khung trả lời (che lại rồi tự nói):

  • Hỏi đầu tiên: dữ liệu quan hệ (SQL, join, transaction) hay key-value? Quan hệ → RDS/Aurora. Key-value, serverless, scale vô hạn, ms → DynamoDB.
  • Trong quan hệ: engine Oracle/SQL Server hoặc chỉ cần managed đơn giản, rẻ → RDS. MySQL/PostgreSQL cần hiệu năng, HA cao nhất, 15 replica, Global Database, Serverless v2 → Aurora.
  • ElastiCache không thay DB, nó đứng trước DB: đề nói sub-millisecond, reduce read load, session store, leaderboard. Redis khi cần HA/persistence/cấu trúc dữ liệu, Memcached khi đơn giản. Cache riêng cho DynamoDB là DAX.
  • Kể được 1 ví dụ mỗi loại: ERP kế toán → RDS; app web MySQL lớn cần 10 replica → Aurora; giỏ hàng, session → DynamoDB; giảm tải đọc trang sản phẩm → ElastiCache.

2. Multi-AZ phục vụ HA, Read Replica phục vụ scale read?

Gợi ý khung trả lời:

  • Multi-AZ: standby ở AZ khác, replication synchronous, failover tự động 1 đến 2 phút, endpoint không đổi, standby không đọc được (trừ Multi-AZ DB cluster). Mục đích: không mất dữ liệu và ít downtime khi AZ hỏng hoặc bảo trì.
  • Read Replica: bản sao asynchronous, có lag, endpoint riêng, app tự gửi truy vấn đọc sang, có thể cross-Region, tối đa 15. Không tự failover, muốn dùng làm primary phải promote thủ công.
  • Hai thứ bổ sung nhau, production thường bật cả hai. Aurora gộp hai vai trò: replica vừa đọc vừa là standby.
  • Kể được 1 ví dụ: báo cáo làm chậm app → Read Replica; đề đòi survive AZ failure → Multi-AZ.
