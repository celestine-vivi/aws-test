Design Secure Architectures (30%)

exam guideにおける配点とtask statement

最も比重の大きいdomainで、65問中およそ20問です。SAA-C03の3つのtask statementを言い換えると次のとおりです。

  • 1.1 AWS resourceへの安全なアクセスを設計する: IAM user/group/role、policy evaluation、cross-account、federation（Identity Center、SAML、Cognito）、MFA、least privilege、OrganizationsとSCP、root account。
  • 1.2 安全なworkloadとアプリケーションを設計する: VPC（Security Group、NACL、public/private subnet、NAT、VPC endpoint）、WAF、Shield、Network Firewall、Secrets ManagerとParameter Store、検出系サービス（GuardDuty、Inspector、Macie、Detective）、記録（CloudTrail、Config、VPC Flow Logs）。
  • 1.3 適切なデータセキュリティ統制を選ぶ: 保存時の暗号化（KMS、SSE-S3/SSE-KMS/SSE-C、EBS、RDS）、転送時の暗号化（TLS、ACM）、S3 security（Block Public Access、bucket policy、Object Lock、versioning、MFA Delete）、key rotation、data classification、complianceに沿った保持とbackup。
必ず覚えるfact
  • policyの評価順: explicit denyがすべてに優先 → SCPがAllowしている必要がある → resource-based policyのAllowで足りる（同一account） → permissions boundary → session policy → identity-based policy。どこもAllowしなければimplicit denyです。
  • SCPは権限を付与せず、上限を決めるだけです。member account内のrootを含むすべてのprincipalに適用されますが、management accountには適用されません。
  • Permissions boundaryも権限を付与しません。実際の権限 = identity policy ∩ boundary。「developerに自分でroleを作らせたいがXを超えさせたくない」と問われたらboundaryです。
  • Cross-account: 両側のAllow（呼び出し側accountのidentity policyと所有側accountのresource policy）が必要です。または role + sts:AssumeRoleを使います。
  • STS AssumeRole: sessionはdefault 1時間、roleの設定で最大12時間。role chainingは最大1時間です。
  • IAM Identity Center: 社員が複数accountへSSOするためのもので、permission setを使い、identity sourceはIdentity Center directory、AD、SAML IdPのいずれかです。Cognitoはアプリケーションのユーザー向けです。User Poolが認証（JWTを返す）、Identity Poolがtokenを一時的なAWS credentialに交換します（unauthenticated identityもあり）。
  • KMS keyはregionalです。multi-Region keyは同じkey IDとkey materialを持つ複製で、あるRegionで暗号化し別のRegionで復号するために使います。暗号化されたEBS snapshotを別Regionへcopyするには、コピー先Regionのkeyで再暗号化します。
  • KMS: AWS managed keyは毎年自動でrotateされ、無効にできません。customer managed keyはautomatic rotationを有効にできます（defaultは毎年、周期は設定可能。日数の範囲はAWSドキュメントで要確認）。imported key materialのkeyは自動rotateしません。直接暗号化できるのは4 KBまでなので、GenerateDataKeyによるenvelope encryptionを使います。
  • KMS keyのkey policyはprincipalを許可する（またはIAMに委ねる）必要があります。cross-accountでKMS keyを使うには、key policyと呼び出し側のIAM policyの両方が必要です。
  • S3の暗号化: SSE-S3（AES-256、AWSがkeyを管理、2023年初めから新しいobjectでdefault有効）、SSE-KMS（CloudTrailでaudit可能、KMSのquotaでthrottleされることがあり、S3 Bucket Keyを有効にしてKMS呼び出しを減らす）、SSE-C（利用者がheaderでkeyを送る、HTTPS必須）、client-side encryption（AWSはkeyを見ない）。
  • upload時の暗号化を強制: header s3:x-amz-server-side-encryptionがない場合にDenyするbucket policy。HTTPSを強制: aws:SecureTransport = falseのときDeny。
  • S3 Block Public Accessはaccountまたはbucketの単位で設定し、どのbucket policyやACLよりも優先されます。新しいbucketのObject OwnershipはBucket owner enforced（ACL無効）がdefaultです。
  • S3 Object Lock: versioningが必要です。Governance mode（特別な権限を持つuserは削除可能）とCompliance mode（retention period中はrootを含め誰も削除不可）、さらに期限のないLegal Holdがあります。Glacier Vault Lockは旧来のGlacier vault向けのWORMです。
  • MFA Delete: rootだけがCLIで有効化でき、versioningが必要です。versionの削除やversioningの停止時にMFAを要求します。
  • Pre-signed URLは作成者のcredentialを使い、パラメータで指定した時間で失効します。CloudFrontのsigned URL/cookieとOACを組み合わせ、S3への直接アクセスを防ぎます。
  • Security Group: statefulで、Allow ruleしかなく、defaultでinboundはすべて拒否、outboundはすべて許可、他のSGを参照できます。NACL: statelessでDenyがあり、番号付きruleを小さい順に評価し、defaultはallow all。特定IPをブロックしたい → NACL。statelessなので、戻りの通信用にephemeral port 1024〜65535を開ける必要があります。
  • VPC endpoint: Gateway endpointはS3とDynamoDBのみ、無料で、route tableにrouteを追加します。Interface endpoint（PrivateLink）はprivate IPを持つENIを作り、時間とGBで課金され、残りのほとんどのサービスとS3にも使えます。endpoint policyでendpoint経由のresourceを制限でき、bucket policyではaws:SourceVpceを使えます。
  • WAFはCloudFront、ALB、API Gateway、AppSync、Cognito User Poolに付けられます。NLBやEC2には付けられません。ruleはIP、geo、rate-based、SQL injection、XSS、managed rule groupなど。Shield Standardは無料で自動適用（L3/L4）。Shield Advancedは月額有料で、DDoS Response Team、cost protectionがあり、EC2/ELB/CloudFront/Global Accelerator/Route 53を保護します。Firewall ManagerはOrganizations全体でWAF、Shield、SGを一元管理します。
  • GuardDuty: CloudTrail、VPC Flow Logs、DNS logs、S3 data events、EKS audit logsから脅威を検出し、agent不要です。Inspector: EC2、ECR image、Lambdaの脆弱性スキャン。Macie: MLでS3内のPIIや機密データを探します。Detective: GuardDutyの検出後に詳しく調査します。Security Hub: findingを集約し、基準に沿ってスコア化します。
  • CloudTrail: API call（誰が、何を、いつ）を記録します。Event historyは90日間無料。trailでS3に送れば長期保存でき、log file validationで改ざんを検知できます。data events（S3 object-level、Lambda invoke）はdefault無効です。AWS Config: resourceの構成を時系列で記録し、ruleでcomplianceを評価し、SSM Automationでremediationします。Configは変更を防がず、検出するだけです。
  • Secrets Manager: secretを保存し、Lambdaで自動rotateします。RDS/Redshift/DocumentDBとの統合が組み込まれ、secret数とAPI callで課金されます。SSM Parameter Store SecureString: KMSで暗号化し、Standard tierは無料ですが、自動rotationはありません。
  • ACM: public証明書を無料で発行し、自動更新し、ELB、CloudFront、API Gatewayに付けます。private keyはexportできず、EC2に直接インストールできません。CloudFront用の証明書はus-east-1に置く必要があります。社内向け証明書にはACM Private CAを使います。
  • EBS: Region単位で「encryption by default」を有効にできます。暗号化済みvolumeは解除できません。未暗号化volume → snapshot → 暗号化を有効にしてsnapshotをcopy → 新しいvolumeを作成。RDS: 暗号化は作成時にしか有効にできません。未暗号化DB → snapshot → 暗号化付きでcopy → restore。暗号化DBのread replicaも暗号化が必須です。
  • defaultで転送時に暗号化されるもの: VPN（IPsec）、CloudFront HTTPS、S3 HTTPS。Direct Connectは暗号化されません（VPN over DXかMACsecが必要）。Nitro instance間のVPC trafficは物理層で暗号化されますが、試験ではアプリケーションのTLSを答えに期待することが多いです。
  • VPC Flow LogsはVPC、subnet、ENIの単位でmetadata（送信元/宛先IP、port、accept/reject）を記録します。payloadは記録せず、Route 53 Resolver、metadata 169.254.169.254、DHCPへのtrafficも記録しません。payloadを取得できるのはTraffic Mirroringです。
  • Root account: MFAを有効にし、access keyを作らず、限られた作業（support planの変更、accountの解約、MFA Deleteの有効化）にだけ使います。Credential reportはuserとkey/MFAの状態を一覧化します。Access Advisorはサービスの最終利用を示します。Access Analyzerは外部に共有されたresourceを見つけ、CloudTrailからpolicyを生成します。

確認クイズ

1. ある会社は財務報告書をS3に保存しています。監査で、administratorを含め誰も5年間はfileを削除または変更できないことが求められています。どの解決策が要件を満たしますか?

versioningを有効にし、retention 5年のCompliance modeでS3 Object Lockを使う。 Governance modeはよく誤って選ばれますが、s3:BypassGovernanceRetention権限を持つuserは削除できます。bucket policyのDenyはadminがpolicyを変更できます。MFA Deleteはversionの削除を守るだけで、rootを止めません。

2. private subnetのLambdaが、trafficをAWSネットワークの外に出さずにDynamoDBとSecrets Managerを呼び出す必要があり、most cost-effectiveにしたい。2つ選んでください。

DynamoDBにはGateway endpoint、Secrets ManagerにはInterface endpoint。 DynamoDBには無料のgateway endpointがあるので、interface endpointは使いません。Secrets Managerにはinterface endpointしかありません。NAT Gatewayはtrafficがpublicに出るうえ費用がかかります。

3. Account Aのbucket policyはaccount Bの読み取りを許可しています。account Bのuserはそのbucketに対するs3:GetObjectをAllowするidentity policyを持っていますが、AccessDeniedになります。最も考えられる原因は?

account BがOrganizations内にあり、S3を許可しないSCPがある。またはobjectがaccount AのKMS keyで暗号化されていて、key policyがaccount Bの利用を許可していない。 両側でAllow済みなので通常の権限不足は除外され、SCP、boundary、KMSを考える必要があります。「評価の連鎖を最後までたどる」習慣を練習する問題です。

4. ALBの背後のweb appが多数のIPからHTTP floodを受けており、各IPが毎分数千のrequestを送ってきます。least operational overheadでブロックしたい。

ALBに付けたAWS WAFのrate-based rule。 NACLはIPごとに手作業で更新する必要があり、defaultで20 ruleしかありません。Shield Standardは有効ですがL3/L4を扱い、L7のHTTP floodにはWAFが必要です。Shield Advancedでも防げますが費用がかかり、設問はDRTが必要とは言っていません。

5. us-east-1のEC2で動くアプリケーションが、customer managed KMS keyで暗号化されたS3 objectを読みます。ap-northeast-1へDRしたいと考えており、bucketをreplicateしても読めるようにしたい。何に注意が必要ですか?

KMS keyはregionalです。CRRを有効にする際はコピー先RegionのKMS keyを指定して複製を暗号化し、replication roleにはコピー元keyのdecrypt権限とコピー先keyのencrypt権限が必要です。 または、multi-Region keyを使って両Regionで同じkey materialを持たせます。よくある誤答は「KMS keyは自動的にどのRegionでも使える」です。

Design Resilient Architectures (26%)

exam guideにおける配点とtask statement

65問中およそ17問です。task statementは2つです。

  • 2.1 拡張性があり疎結合（loosely coupled）なアーキテクチャを設計する: ELB、Auto Scaling、decoupleのためのSQS/SNS/EventBridge、API Gateway、Lambda、container（ECS/EKS/Fargate）、microservice、scaleに適したstorageとdatabaseの選択、caching、event-driven。
  • 2.2 高可用性と耐障害性（highly available, fault-tolerant）を備えたアーキテクチャを設計する: Multi-AZとMulti-Region、Route 53のroutingとhealth check、RDS Multi-AZとread replica、Aurora、DynamoDB Global Tables、RPO/RTOに応じた4つのDR戦略、AWS Backup、S3 replication、EFS、Storage Gateway、Direct ConnectとバックアップのVPN、immutable infrastructure、single point of failure。
必ず覚えるfact
  • Multi-AZは1つのAZ障害に耐え、費用は低めです。Multi-RegionはRegion全体の障害に耐え、DRやグローバルユーザー向けに使います。設問がhighly availableと言うなら通常Multi-AZで十分で、disaster recovery、Region failureならMulti-Regionです。
  • High availabilityは停止時間を減らすこと（failover時に短い中断はありうる）。Fault toleranceは一切中断しないこと（より高価で、例えば複数AZでN+1を動かす）。fault-tolerantを問う設問は、requestを1つも失わないレベルの冗長化を求めていることが多いです。
  • RDS Multi-AZ instance: 別AZのstandbyへ同期レプリケーションし、standbyは読み取り不可です。failoverはDNSを自動で切り替え、約60〜120秒かかります。AZ障害、OSのpatch、instance typeの変更時に使われます。RDS Multi-AZ DB cluster: 読み取り可能なstandbyが2つあり、failoverがより速い（時間はAWSドキュメントで要確認）。
  • RDS read replica: 非同期で読み取り可能、最大15個（engineによる、AWSドキュメントで要確認）、cross-Regionも可能で、独立したDBにpromoteできます（手動DRに使う）。read replicaにはソースでautomated backupの有効化が必要です。
  • Aurora: データを3 AZに6コピー保持し、自己修復します。writerとstorageを共有するAurora Replicaは最大15個で、replicaはfailover先となり、lagは通常1秒未満です。failoverは約30秒。Reader endpointが自動で負荷分散します。Aurora Global Database: primary Region 1つ、secondary Region最大5つ、replication lagは通常1秒未満、RPOは約1秒、promote時のRTOは1分未満（AWS公表値、AWSドキュメントで要確認）。
  • DynamoDB Global Tables: 複数Regionでmulti-active、DynamoDB Streamsの有効化が必要で、競合はlast writer winsで解決します。PITRは35日以内の任意の時点に復元でき、on-demand backupは無期限に保持します。
  • ELB: ALBはlayer 7（HTTP/HTTPS、path/host routing、WebSocket、targetはinstance、IP、Lambda）。NLBはlayer 4（TCP/UDP/TLS、static IPとElastic IP、毎秒数百万request、送信元IPを保持）。Gateway Load Balancerはサードパーティの仮想firewall向け（GENEVE）。Cross-zone load balancing: ALBはdefault有効で無料、NLBはdefault無効で、有効にするとAZ間のdataに課金されます。
  • ELBのhealth checkは異常なtargetを外します。deregistration delay（connection draining）はdefault 300秒。ALBのsticky sessionはcookieで実現します。ALBにはstatic IPがないので、固定IPが必要ならALBの前にNLBを置くかGlobal Acceleratorを使います。
  • Auto Scaling Group: 複数AZにまたがり、min/desired/maxを持ちます。health check typeはEC2（default）またはELB（ELB health checkに失敗したinstanceを置き換える。「unhealthyなinstanceがなぜ置き換えられないか」はよく出題され、答えはASGがEC2 health checkを使っているから）。grace periodはdefault 300秒、cooldownはdefault 300秒。
  • Scaling policy: target tracking（CPU 50%を維持など、最も簡単）、alarmに基づくstep/simple scaling、scheduled（ピーク時間が事前にわかる）、predictive（履歴からMLで予測）。lifecycle hookでservice投入前やterminate前にscriptを実行します。instance refreshで新しいAMIへrollingします。
  • ASGのdefault termination policy: instanceが最も多いAZを選ぶ → 最も古いlaunch template/configを使うinstance → 次の課金時間に最も近いもの。scale-in protectionで長いjobを処理中のinstanceを守ります。
  • Route 53のrouting policy: simple、weighted（負荷を%で分配、blue/green）、latency（最も速く応答するRegion）、failover（health check付きのactive-passive）、geolocation（ユーザーの国に基づく、コンテンツのcompliance）、geoproximity（biasを付けた距離に基づく、Traffic Flowが必要）、multivalue answer（healthyなrecordを最大8つ、ELBの代わりにはならない）、IP-based。Alias recordは無料で、apex domainをELB/CloudFront/S3 websiteに向けられます。CNAMEはapexを指せません。
  • Route 53 health check: publicなendpointを確認し、private IPは直接確認できません。private resourceにはCloudWatch alarmに基づくhealth checkを作ります。failoverではrecordにhealth checkを付けられます。

  • EFS StandardはRegion内の複数AZにまたがり、数千のEC2がNFSで同時にmountできます。EFS One Zoneは安価ですが1 AZです。EFS Replicationで別Regionへ複製できます。instance storeとEBSは複数instanceで共有できません（同一AZ内のEBS multi-attach io1/io2を除く）。
  • Storage Gateway: File Gateway（NFS/SMB → S3 object、ローカルcache）、Volume Gateway（iSCSI。cached: 主データはS3、頻繁に使うデータをローカルにcache。stored: 全データをローカルに置き、S3へsnapshotしてEBS snapshotにする）、Tape Gateway（磁気テープに代わるVTL、Glacierに保存）。設問がon-premises backup to cloud with existing backup softwareならTape Gateway、low-latency access to frequently used data, rest in S3ならcached volumeかFile Gatewayです。
  • Direct Connect: 専用接続で帯域が安定しますが、自動では暗号化されず、構築に数週間〜数か月かかり、1本だけではsingle point of failureです。冗長化: 異なる2つのlocationに2本のDX（maximum resiliency）、またはメインのDX + バックアップのSite-to-Site VPN（最も安価）。Direct Connect Gatewayで1本のDXを複数Regionの複数VPCに接続します。
  • Site-to-Site VPN: IPsec tunnelが2本、tunnelごとに約1.25 Gbps、数分で構築できます。Transit Gateway経由ならECMPで複数VPNの帯域を束ねられます。Transit Gatewayは複数VPCとon-premisesをつなぐhubで、mesh型のVPC peering（peeringはtransitiveでない）の代わりになります。
  • Immutable infrastructure: その場でpatchせず、新しいAMIを作り（EC2 Image Builder）、ASGのinstance refreshやCodeDeployでrollingまたはblue/greenします。状態はinstanceの外（S3、EFS、DynamoDB、ElastiCache session）に置きます。statelessなinstanceは、ASGが自由にinstanceを置き換えるための前提です。
  • Lambdaの非同期呼び出しは2回retryし、DLQまたはdestinationを持てます。SQS triggerはvisibility timeoutに従ってretryします。Step Functionsはretry/catch付きで長いworkflowを調整します。設問がorchestrate multiple Lambda with retryならStep Functionsです。
  • 手動failover時にElastic IPを別instanceへremapする、2つ目のENIを同一AZのinstance間で移す。これらは古いタイプのHAで、least operational overheadの設問では通常EIPのremapではなくELB + ASGを選びます。

exam guideにおける配点とtask statement

65問中およそ13問です。task statementは4つで、いずれもcost-optimizedという語を含みます。

  • 4.1 Storage: S3 storage classとlifecycle、Intelligent-Tiering、Glacier retrieval、EBS typeとsnapshot、EFS class、backupの保持期間、data transfer cost。
  • 4.2 Compute: EC2 pricing（On-Demand、Spot、Reserved、Savings Plans、Dedicated）、right sizing、Auto Scaling、Lambda、FargateとEC2、Graviton、Compute Optimizer。
  • 4.3 Database: RDS Reserved、Aurora Serverless、DynamoDBのon-demandとprovisioned、I/Oを減らすためのcaching、より安価なengineの選択、使わないDBの停止。
  • 4.4 Network: NAT Gateway、NATの代わりのVPC endpoint、CloudFrontによるegress削減、Direct ConnectとVPNの比較、同一AZと別AZ、Transit Gatewayの費用、Route 53。

さらにツールとして: Cost Explorer、Budgets、Cost and Usage Report、Cost Anomaly Detection、cost allocation tags、Organizationsのconsolidated billing。

必ず覚えるfact
  • On-Demand: Linuxは秒単位（最低60秒）、Windowsや一部のOSは時間単位で課金。契約不要で、短期間や予測できないworkload向けです。
  • Reserved Instance: 1年または3年、最大約72%割引（3年all upfront）。Standard RIは割引が最も大きく、同じfamily内でAZとsizeを変更でき（Linux）、familyは変更できず、RI Marketplaceで売却できます。Convertible RIは割引が小さめ（最大約66%）ですが、family、OS、tenancyを変更できます。支払いはall upfront、partial、no upfront。scopeはregional（AZに柔軟、capacityは確保しない）またはzonal（特定AZのcapacityを確保）。
  • Savings Plans: 1年または3年で、1時間あたりのUSD額を約束します。Compute SPはEC2のあらゆるfamily、Region、Fargate、Lambdaに適用され最大66%割引。EC2 Instance SPはfamilyとRegionが固定で最大72%割引。設問がflexible across instance family, Region, Fargate, LambdaならCompute Savings Plansです。%はAWSドキュメントで要確認です。
  • Spot: 最大90%割引。AWSが必要なときに2分前の通知で回収します。batch、CI、big data、render、ASG mixedのstatelessなweb向けで、databaseや中断に耐えられないworkloadには使いません。Spot FleetやASGのmixed instances policyで、On-DemandとSpotを複数のinstance typeで組み合わせ、回収リスクを下げます。戦略はprice-capacity-optimized。
  • Dedicated Host: 物理マシン丸ごとで、socket/coreが見えるのでsocket単位のlicense（Windows Server、SQL Server BYOL）に使えます。最も高価です。Dedicated Instance: 専用hardwareで動きますが、配置は制御できずsocketも見えません。Capacity Reservation: 1つのAZでOn-Demandのcapacityを確保します。割引はないので、regional RIやSPと組み合わせてcapacityと安さを両立させます。
  • Right sizing: Compute OptimizerはCloudWatchに基づいてEC2、ASG、EBS、Lambda、ECS Fargateのsizeを提案します（over-provisioned、under-provisioned）。Trusted Advisorはidleなload balancer、低稼働のEC2、未関連付けのEIP、低稼働のEBSを報告します（多くのcheckにはBusiness/Enterprise supportが必要）。Cost Explorerにもright sizing recommendationがあります。
  • S3 storage class: Standard（頻繁なアクセス）。Intelligent-Tiering（アクセスに応じて自動でtierを移動、objectごとに少額の監視料金、retrieval料金なし、128 KB未満のobjectはtier移動されないが保存はされる、Archive AccessとDeep Archive Access tierはopt-in）。Standard-IA（GB単位のretrieval料金、最低30日と128 KBで課金、複数AZ）。One Zone-IA（IAより約20%安い、1 AZ、再作成できるデータ向け）。Glacier Instant Retrieval（ミリ秒、最低90日、四半期に1回程度アクセスするデータ向け）。Glacier Flexible Retrieval（Expedited 1〜5分、Standard 3〜5時間、Bulk 5〜12時間、最低90日）。Glacier Deep Archive（Standard 12時間、Bulk 48時間、最低180日、最も安価）。最低日数はAWSドキュメントで要確認です。
  • Lifecycle rule: objectの経過日数によるtransition（Standard → IAはStandardで最低30日が必要）、expiration、N日後のnoncurrent versionの削除、abort incomplete multipart upload（隠れた費用の原因）、expired delete markerの削除。lifecycleでGlacierからStandardへ戻すことはできません（restoreしてからcopyする）。どのclassに移すべきかはS3 Storage Class AnalysisとStorage Lensで把握します。設問がunknown or changing access patternならIntelligent-Tieringです。
  • Glacierのrestoreは、指定した日数だけ一時的なStandardのコピーを作り、両方の料金がかかります。Expeditedはprovisioned capacityを購入してthroughputを確実に確保できます。
  • EBS: gp3はgp2より約20%安くbaselineも高いので、ほとんどの場合cost-effectiveです。io2は16,000 IOPSを超える場合や高いdurabilityが必要な場合のみ。st1/sc1は大きなthroughputや冷たいデータ向け。snapshotはincrementalで、変更されたblockだけ課金されます。EBS Snapshots Archiveは90日以上保持するsnapshotで約75%安く、restoreに24〜72時間かかります。Data Lifecycle Managerで古いsnapshotを削除します。terminate後に残った孤立volumeを削除します（Delete on terminationを確認）。
  • Data transfer: AWSへの受信は無料。同一AZ内のprivate IP経由は無料。同一Region内の別AZ間は双方向それぞれに課金（各方向約0.01 USD/GB）。別Region間（約0.02 USD/GB）。Internetへの送信は約0.09 USD/GBで段階的に下がり、毎月最初の100 GBは無料。S3やEC2からCloudFrontへは無料で、CloudFrontからInternetへの方が安価です。同一AZのinstance間でもpublic IPやEIPを使うとregionalとして課金されます。価格はAWSドキュメントで要確認です。
  • NAT Gateway: 約0.045 USD/時間 + 処理量約0.045 USD/GB（Tokyoは少し高い）。HAとAZ間料金の回避のため、AZごとにNATを1つ置きます。private subnetからS3/DynamoDBへのtrafficはNATを通るとGB単位で課金されるので、無料のGateway endpointに置き換えます。Interface endpointはAZごとに約0.01 USD/時間 + 0.01 USD/GBで、通信量が多ければやはりNATより安価です。NAT instanceは安価ですが自前管理でHAがありません。
  • CloudFrontはegressとoriginの負荷を減らします。Global Acceleratorは時間単位の固定料金 + GB単位のpremium。Direct Connect: portの時間料金があり、egressはInternetよりかなり安く、大量で安定した通信に向いています。VPNは安く素早く構築でき、少量の通信向けです。Transit GatewayはattachmentとGBで課金、VPC peeringはdata transferだけ課金されます。
  • RDS Reserved Instanceは1年または3年で最大約69%割引（AWSドキュメントで要確認）、同じengineとfamily内でsize-flexibleです。RDSのinstanceは最大7日間stopでき、その後自動で起動します（Multi-AZとread replicaはstopできない）。dev DBはInstance SchedulerやLambdaで時間外に停止するスケジュールにします。Multi-AZは費用が2倍になり、dev/testには不要です。
  • Aurora Serverless v2はACU時間で課金され、不規則なworkloadやあまり使わないworkloadに向いています。Aurora StandardはI/Oを別途課金し、Aurora I/O-OptimizedはI/Oを課金しません。I/Oが請求額の約25%を超えるなら後者を選びます。replicaがstorageを共有するため、多くのreplicaが必要な場合は同じengineのRDSよりAuroraの方が安価です。
  • DynamoDB on-demand: request単位で支払い、不規則なtrafficや予測できないtraffic向けで、requestあたりの単価はprovisionedの数倍です。provisioned + auto scalingは安定したtraffic向けで、1年または3年のreserved capacityを購入するとさらに安くなります。Standard-IA table classはアクセスが少なくデータが多いテーブル向けです（storageは安く、throughputは高い）。modeの切り替えは24時間に最大1回です。
  • Lambdaはrequest数とGB秒で課金されます。Free Tierは毎月100万requestと400,000 GB秒（always free、AWSドキュメントで要確認）。arm64のGravitonは約20%安価。memoryを増やすと速く終わるため、かえって安くなることもあります。Compute Savings PlansはLambdaにも適用できます。
  • FargateはvCPUとGBを秒単位で課金し、serverの管理が不要です。Fargate Spotは中断に耐えるtaskで最大70%割引。EC2上のECSはclusterを使い切りRI/Spotがあれば安価ですが、hostの管理が必要です。設問がleast operational overheadならFargate、高い稼働率が続く場合のmost cost-effectiveならRIまたはSavings Plans付きのEC2です。
  • ツール: Cost Explorer（費用の表示とfilter、予測、RI/SPの推奨、right sizing、APIあり）。AWS Budgets（cost、usage、RI/SPのutilizationとcoverage、実績と予測によるアラート、budget actionでpolicyを付与したりEC2/RDSを停止したりする）。Cost and Usage Report（最も詳細、S3に出力、Athenaでquery）。Cost Anomaly Detection（MLで異常な支出を検出、SNSでアラート）。cost allocation tags（BillingでtagをActivateしないとCost Explorerに表示されない）。Cost Categoriesはteam別に費用をまとめます。Pricing Calculatorは事前の見積もりです。
  • OrganizationsのConsolidated billing: 全accountで請求書が1つになり、usageを合算して段階的な価格（S3、data transfer）の恩恵を受け、RIとSavings Plansをaccount間で共有します（特定accountでRI sharingを無効化可能）。支払いはmanagement accountです。SCPは費用とは無関係ですが、高価なresourceの作成を防ぐことはできます（例: 大きなinstance typeをDeny）。
