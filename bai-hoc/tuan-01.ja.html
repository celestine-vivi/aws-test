Region、Availability Zone、Edge location

概要
  • Region: 地理的な地域（東京 ap-northeast-1、シンガポール ap-southeast-1、バージニア北部 us-east-1）。各 Region は他の Region から完全に独立したインフラの集まりです。AWS には現在 30 以上の Region があります。
  • Availability Zone (AZ): Region 内の1つ以上のデータセンターで、電源、ネットワーク、冷却を個別に持ちます。火災、洪水、停電などの障害が他の AZ に及ばない距離に置かれつつ、AZ 間のネットワーク遅延はごく小さく保たれています。名前は ap-northeast-1a、1c、1d のような形式です。各 Region には少なくとも3つの AZ があります（新しい Region の場合）。
  • Edge location: 数百の都市にある拠点（Point of Presence）で、Region よりユーザーに近い場所にあります。CloudFront（コンテンツのキャッシュ）、Route 53（DNS）、Global Accelerator、AWS Shield が使います。ここで EC2 や RDS は動きません。
  • あわせて覚える: Local Zones（Region を大都市へ拡張、EC2/EBS が動く）、Wavelength（通信事業者の 5G 網内）、Outposts（自社データセンターに置く AWS のラック）。
イメージ
どの Region を選ぶか
  • Compliance / data residency: 法律でデータの国内保管が求められる → その国の Region を選ぶ。
  • Latency: ユーザーに最も近い Region。
  • サービスの提供状況: 新しい Region はサービスが不足しがちで、us-east-1 が最も揃っています。
  • 料金: Region ごとに異なり、東京はバージニアより高めです。
Global と Regional のサービス
  • Global: IAM、Route 53、CloudFront、WAF（CloudFront 用）、Organizations、Billing。
  • Regional: EC2、VPC、RDS、Lambda、DynamoDB。S3 bucket は1つの Region にありますが、bucket 名は全世界で一意です。
  • 1つの AZ に紐づく: EC2 instance、EBS volume、subnet。EBS は別 AZ の EC2 にはアタッチできません。

確認クイズ

1. ある企業は、東京のデータセンター1つが停電してもアプリケーションを稼働させ続けたいと考えており、コストは最小にしたいです。どのようにデプロイすべきですか。

東京 Region 内の2つ以上の AZ にデプロイする（Multi-AZ）。 Multi-Region でも要件は満たせますが高コストで複雑であり、設問に cost とあるので除外します。AZ が1つだけでは障害に耐えられません。

2. ap-northeast-1a にある EBS volume を ap-northeast-1c の EC2 にアタッチできますか。

できません。 EBS は1つの AZ に紐づきます。別の AZ に移すには snapshot を取り（snapshot は Region 単位）、移動先の AZ でその snapshot から新しい volume を作ります。

Shared responsibility model

概要

AWS はクラウドのセキュリティ（security of the cloud）に責任を持ちます。対象はハードウェア、データセンター、物理ネットワーク、ハイパーバイザー、マネージドサービスのソフトウェアです。利用者はクラウド内のセキュリティ（security in the cloud）に責任を持ちます。対象はデータ、アクセス権限（IAM）、ネットワーク設定（Security Group、NACL）、暗号化、自分で導入した OS とアプリケーションです。

境界はサービスによって変わります。マネージド度が高いほど AWS の担当範囲が広がります。

RDS (managed)OS と DB engine 両方のパッチ適用、自動バックアップDB アカウント、Security Group、暗号化の有効化、データ、クエリの最適化
Lambda、S3、DynamoDB (serverless / abstracted)インフラとランタイムのほぼすべてコード、IAM policy、bucket policy、暗号化、データの分類
共通の責任（shared controls）
  • Patch management: AWS はインフラにパッチを当て、利用者は EC2 上の guest OS にパッチを当てます。
  • Configuration management: AWS はインフラを設定し、利用者は OS、データベース、アプリケーションを設定します。
  • Awareness and training: AWS は AWS の従業員を、利用者は自社の従業員を教育します。

IAM: user、group、role、policy

4つの概念
概念内容Credential用途
Userアカウント内の固定されたアイデンティティ長期: password（コンソール）、access key（CLI/SDK）長期間アクセスが必要な人。1アカウントあたり最大 5,000 user（AWSドキュメントで要確認）。
Groupuser の集まり。グループ全体に policy を付与なし。ログインできない職務ごとの権限管理（Developers、Admins）。Group は入れ子にできず、1人の user が所属できるのは最大 10 group。
Role引き受ける（assume）アイデンティティで、特定の人に固定されない一時的。STS が発行し自動で失効（デフォルト1時間、最大12時間）EC2、Lambda、AWS サービス、他アカウントの user、フェデレーションユーザー（SSO、Google、AD）。
Policy権限を記述した JSON ドキュメントなしuser、group、role に付与（identity-based）、または S3 bucket などのリソースに付与（resource-based）。
Role には2つの policy がある
  • Trust policy: 誰がこの role を assume できるか（Principal: ec2.amazonaws.com、他アカウント、SAML provider）。
  • Permission policy: assume した後に role が何をできるか。
  • EC2 は instance profile を通じて role を受け取ります。一時的な credential はメタデータサービスから提供され自動でローテーションされるので、access key をマシンに埋め込む必要は一切ありません。
user ではなく role を使う場面（確認ポイント 1）
原則: ソフトウェアと一時的なアクセス → role。長期間ログインが必要な人 → user（より良いのは IAM Identity Center で、裏側は同じく role）。設問に temporary、cross-account、EC2 / Lambda needs access、federated、rotate credentials、no long-term credentials があれば、答えはほぼ必ず role です。
  • EC2 が S3 を読む → EC2 に role を付与する。access key を作ってマシンにコピーしない。
  • アカウント A がアカウント B の S3 にアクセスする → B が A を信頼する role を作り、A が sts:AssumeRole を使う。
  • 社員が社内の Active Directory でログインする → SAML 2.0 フェデレーションまたは IAM Identity Center で role にマッピングする。
  • モバイルアプリから S3 に画像をアップロードする → Cognito Identity Pool が role から一時的な credential を発行する。
policy JSON の構造 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadOnlyOneBucket",
      "Effect": "Allow",                       // Allow または Deny
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": ["arn:aws:s3:::saa-lab-quy", "arn:aws:s3:::saa-lab-quy/*"],
      "Condition": { "Bool": { "aws:MultiFactorAuthPresent": "true" } }
    }
  ]
}
  • Principal は resource-based policy（bucket policy、KMS key policy、SQS、SNS、Lambda）にだけ存在します。identity-based policy はすでにアイデンティティに付与されているので Principal を持ちません。
  • ARN: arn:partition:service:region:account-id:resource。S3 と IAM には region がありません。bucket と object は別々の ARN なので、ListBucket には bucket の ARN、GetObject には bucket/* の ARN が必要です。policy を自分で書くときに最も多い間違いです。
  • よく出る Condition: aws:SourceIp、aws:MultiFactorAuthPresent、aws:RequestedRegion、aws:PrincipalOrgID、s3:prefix、ec2:ResourceTag/…。

試験によく出る IAM のベストプラクティス
  • root はごく一部の作業（サポートプランの変更、アカウントの解約、一部の請求設定）にだけ使います。root には MFA を有効にし、access key を作りません。
  • Least privilege: 必要な権限だけを付与し、最小から始めて段階的に広げます。IAM Access Analyzer で CloudTrail から policy を生成し、外部に共有されているリソースを見つけます。
  • Credential report（アカウント全体、CSV ファイル）と Access Advisor（1つの user/role がどのサービスを最後にいつ使ったか）で不要な権限を整理します。
  • 強い権限を持つ user には MFA を有効にし、危険な操作には condition aws:MultiFactorAuthPresent を使います。
  • Password policy: 長さ、複雑さ、有効期限、再利用の禁止。

確認クイズ

5. EC2 上で動くアプリケーションが S3 にログを書き込む必要があります。開発者は IAM user を作成し、access key を発行してインスタンス上の設定ファイルに保存することを提案しました。most secure にするにはアーキテクトはどうすべきですか。

bucket への書き込み権限を持つ IAM role を作成し、instance profile で EC2 に付与する。 マシン上の長期 access key は漏洩するおそれがあります（AMI、snapshot、git）。role は一時的な credential を発行して自動でローテーションするため、漏れるものがありません。

6. user に付与した policy には arn:aws:s3:::bucket/* に対する s3:GetObject がありますが、aws s3 ls s3://bucket を実行すると AccessDenied になります。なぜですか。

bucket の ARN（/* なし）に対する s3:ListBucket がないためです。 一覧表示は bucket に対する操作で、object のダウンロードは object に対する操作です。リソースが異なるので2つの記述が必要です。

7. ある企業は 20 の AWS アカウントを持ち、社員に既存の Active Directory アカウントでログインさせたいと考えています。least operational overhead を満たすには何を選びますか。

IAM Identity Center を AD に接続し（AD Connector または AWS Managed Microsoft AD 経由）、各アカウントに permission set を割り当てる。 20 のアカウントそれぞれに IAM user を作るのは手間がかかり、SSO にもなりません。Cognito はアプリの利用者向けで、管理担当の社員向けではありません。

ポリシーの評価順序

覚えるべき3つのルール
  1. デフォルトではすべてのリクエストが拒否されます（implicit deny）。
  2. 該当する explicit deny が1つでもあれば → ただちに拒否し、それ以上は評価しません。
  3. deny がなく、該当する Allow の policy があれば → 許可します。それ以外は implicit deny です。

まとめ: explicit deny > explicit allow > implicit deny。

IAM ドキュメント「Policy evaluation logic」を簡略化したフローです。SAA の試験では次の点を覚えておけば十分です: deny はすべてに勝つ、boundary と SCP は上限であり権限を付与しない、同一アカウントなら identity policy か resource policy のどちらかが許可すれば足りる。

同一アカウントとクロスアカウント
  • 同一アカウント: identity-based の Allow または resource-based の Allow があれば十分（和集合）。
  • クロスアカウント: 呼び出し側アカウントの identity-based とリソース所有アカウントの resource-based の両方が Allow する必要がある（積集合）。
  • 例: アカウント A の user がアカウント B の bucket を読みたい → A が user に s3:GetObject を付与し、さらに B の bucket policy で Principal にアカウント A またはその user を指定する。
explicit deny が allow に勝つ理由（確認ポイント 2）

explicit deny はセーフティネットだからです。管理者は、どこかの Allow policy に解除される心配なしに、特定の操作（CloudTrail の削除、許可リスト外の Region の利用、暗号化の無効化）を確実に禁止できます。もし allow が deny に勝てるなら、policy を付与できる人なら誰でも自分で禁止を解除でき、deny は意味を失います。deny は先に評価されてその場で終了するので、「allow を追加する」ことで回避する方法はありません。

試験によく出る2つの Deny パターン 
// 東京と大阪以外でのすべての操作を禁止（global サービスは除く）
{
  "Effect": "Deny",
  "NotAction": ["iam:*", "sts:*", "route53:*", "cloudfront:*", "support:*"],
  "Resource": "*",
  "Condition": { "StringNotEquals": { "aws:RequestedRegion": ["ap-northeast-1", "ap-northeast-3"] } }
}

// S3 のすべての削除操作に MFA を必須にする
{
  "Effect": "Deny",
  "Action": ["s3:DeleteObject", "s3:DeleteBucket"],
  "Resource": "*",
  "Condition": { "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" } }
}
  • NotAction + Deny =「このリスト以外をすべて deny」。ゆっくり読むこと。試験では引っかけによく使われます。
  • NotAction + Allow =「このリスト以外をすべて allow」で非常に広く、設問が least privilege を問う場合はたいてい誤答です。

確認クイズ

8. Developers グループに所属する user には ec2:* を Allow する policy があります。この user にはさらに ec2:TerminateInstances を Deny する inline policy もあります。user が TerminateInstances を実行するとどうなりますか。

拒否されます。 該当するどの policy の explicit deny でも勝ちます。Allow のほうが範囲が広くても、group に付与されていても同じです。付与の順序や policy の種類は関係ありません。

9. アカウントが属する OU の SCP は ec2:* と s3:* だけを Allow しています。そのアカウントの IAM user は AdministratorAccess を持っています。この user は RDS を作成できますか。

できません。 SCP はアカウントの上限です。AdministratorAccess はすべてを許可しますが、実際の権限 = SCP ∩ identity policy であり、RDS は SCP の範囲外です。そのアカウントの root でも作成できません。

10. アカウント A の user はアカウント B の bucket に対する s3:GetObject を Allow されていますが、B の bucket には bucket policy がありません。読み取れますか。

読み取れません。 クロスアカウントでは両側の許可が必要です。アカウント B が Principal をアカウント A とする bucket policy を追加する必要があります（または A が assume する role を作る）。

11. 管理者が user X に s3:* だけを許可する permissions boundary を設定しました。X の identity policy は s3:* と dynamodb:* を Allow しています。X は何ができますか。

S3 だけです。 boundary は権限を付与せず、制限するだけです: 実際の権限 = identity ∩ boundary。DynamoDB は boundary の範囲外なので implicit deny になります。

理論 5 / 5

料金の基本と Free Tier

料金の3原則
  • Pay as you go: 使った分だけ支払い、契約は不要。
  • Save when you commit: 1年または3年のコミット（Reserved Instances、Savings Plans）で最大約 70% 安くなる。
  • Pay less by using more: 段階制の料金。S3 やデータ転送は量が多いほど GB 単価が下がる。
請求を生む3つの要素
種類課金の単位試験での注意点

現行の Free Tier
2025年7月15日以降に作成したアカウントは新しい Free Tier が適用されます。クレジット（登録時に 100 USD、初期設定のアクティビティを完了するとさらに最大 100 USD）が付与され、6か月で失効します。選択肢は2つです: Free plan（クレジットを超えて課金されることはないが、一部サービスに制限あり）と Paid plan（すべてのサービスを使え、クレジットを超えた分は支払う）。それ以前のアカウントは従来どおり12か月無料の方式です。always free のサービス（Lambda 月 100 万リクエスト、DynamoDB 25 GB、CloudWatch 10 メトリクス）は引き続き利用できます。具体的な数値は、アカウント作成前に AWS Free Tier のページで要確認です。

このロードマップでは、第4〜6週の NAT Gateway、ALB、RDS のラボを行えるよう Paid plan を選び、Budget とラボ直後にリソースを削除する習慣で費用を管理するのがおすすめです。

Lab 1. AWS アカウントを作成し、root の MFA を有効化

  1. aws.amazon.com/free を開き、Create account を選びます。AWS 専用のメールアドレス（ten+aws@gmail.com の形式でも可）を使い、アカウント名は quy-saa-lab のように分かりやすくします。本人確認にクレジットカードが必要です。

  2. プランを聞かれたら Paid plan を選びます（理由は Free Tier の項を参照）。サポートは Basic support（無料）を選びます。

  3. root でサインインします。右上のアカウント名 → Security credentials → Multi-factor authentication (MFA) → Assign MFA device。

  4. Authenticator app（Microsoft Authenticator、Google Authenticator、1Password のどれでも可）または Passkey を選びます。QR コードを読み取り、連続する2つのコードを入力します。AWS は root の MFA を必須化しているので、この手順は省略できません。

  5. 同じページで root の Access keys が 0 であることを確認します。root の access key は絶対に作りません。

  6. Billing and Cost Management → Account を開き、IAM user and role access to Billing information までスクロールして Edit → Activate を押します。これを有効にしないと、Lab 2 の管理者用 IAM user が請求情報を見られません。

このラボ以降、root は本当に必要なときだけ使います。root のパスワードと MFA の復旧コードはパスワードマネージャーに保管します。

Lab 2. 管理者用 IAM user と 10 USD の Budget を作成

  1. root のまま IAM → Users → Create user を開きます。User name は quy-admin。Provide user access to the AWS Management Console にチェック → 「I want to create an IAM user」を選択 → パスワードを設定し、必要なら「must create a new password at next sign-in」のチェックを外します。

  2. Permissions: Attach policies directly → AdministratorAccess を検索 → Next → Create user。実際の会社では Identity Center を使いますが、一人で学習するアカウントなら IAM user で十分です。

  3. 作成した user を開き → Security credentials タブ → この user にもすぐ MFA を割り当てます（Authenticator アプリでは別のエントリを使う）。

  4. Account ID（12桁、右上に表示）と、https://<account-id>.signin.aws.amazon.com/console 形式のサインイン URL を控えます。root からサインアウトし、quy-admin でサインインし直します。以降はこの user だけを使います。

  5. 右上の Region を Asia Pacific (Tokyo) ap-northeast-1 に切り替えます。ロードマップを通して1つの Region に固定すると、リソースの消し忘れを防げます。

  6. Billing and Cost Management → Budgets → Create budget → Use a template → Monthly cost budget。Budget name は saa-lab-10usd、Enter your budgeted amount は 10、Email recipients に自分のメールアドレスを入れて → Create budget。このテンプレートは actual 85%、actual 100%、forecast 100% のアラートを自動で作成します。

Lab 3. AWS CLI のインストール、profile の設定、アイデンティティの確認

  1. Windows に winget で AWS CLI v2 をインストールします（または AWS のページから MSI ファイルをダウンロード）:

    winget install --id Amazon.AWSCLI -e
aws --version

    インストール後はターミナルを開き直します。期待される結果は aws-cli/2.x.x Python/3.x Windows/10 ... の形式です。

  2. 管理者 user の access key を作成します: コンソール → IAM → Users → quy-admin → Security credentials → Create access key →「Command Line Interface (CLI)」を選択 → 確認にチェック → Create。CSV ファイルをダウンロードし、git にはコミットしません。これは長期の credential で、パスワード保護された個人 PC なら許容範囲です。会社では aws configure sso を使います。

  3. saa という名前の profile を設定します:

    aws configure --profile saa
# AWS Access Key ID: キーを貼り付け
# AWS Secret Access Key: シークレットを貼り付け
# Default region name: ap-northeast-1
# Default output format: json

    設定は C:\Users\<ユーザー名>\.aws\credentials と .aws\config に書き込まれます。

  4. 現在使っているアイデンティティを確認します:

    aws sts get-caller-identity --profile saa

    期待される結果:

    {
    "UserId": "AIDAEXAMPLE...",
    "Account": "123456789012",
    "Arn": "arn:aws:iam::123456789012:user/quy-admin"
}

    ARN を見て、root ではなく user/quy-admin であることを確かめます。

  5. 毎回 --profile を入力しなくて済むよう、PowerShell で:

    $env:AWS_PROFILE = "saa"
aws sts get-caller-identity

    すべてのウィンドウで固定したい場合は、Windows のユーザー環境変数に AWS_PROFILE を追加します。

  6. 課金されない読み取り系コマンドをいくつか試します: aws ec2 describe-regions --output table、aws iam list-users、aws s3 ls（空なら正常）。

InvalidClientTokenId が出る場合: キーの入力ミスか、まだ有効になっていません。sts get-caller-identity は権限不要なので、AccessDenied はほぼ発生しません。コマンドが長く固まる場合は社内プロキシを確認します。

Lab 4. 1つの bucket だけ読める IAM policy を書き、Policy Simulator で確認

  1. テスト用 bucket を作成します（bucket 名は全世界で一意である必要があるので、末尾を変えてください）:

    aws s3 mb s3://saa-lab-quy-2026 --region ap-northeast-1
echo hello > hello.txt
aws s3 cp hello.txt s3://saa-lab-quy-2026/hello.txt

  2. readonly-bucket.json ファイルを作成します。bucket と object で Resource が異なる点に注意します:

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListBucket",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::saa-lab-quy-2026"
    },
    {
      "Sid": "GetObjects",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::saa-lab-quy-2026/*"
    }
  ]
}

  3. policy を作成し、テスト用 user saa-reader を作って policy を付与し、access key と profile reader を作成します:

    aws iam create-policy --policy-name SaaLabReadOnlyBucket --policy-document file://readonly-bucket.json
aws iam create-user --user-name saa-reader
aws iam attach-user-policy --user-name saa-reader --policy-arn arn:aws:iam::<account-id>:policy/SaaLabReadOnlyBucket
aws iam create-access-key --user-name saa-reader
aws configure --profile reader   # saa-reader のキーを貼り付け

  4. IAM Policy Simulator を開きます: policysim.aws.amazon.com（quy-admin でサインイン）。左の列で Users → saa-reader を選択。右側で Select service は Amazon S3、Select actions は GetObject、PutObject、ListBucket、DeleteObject。Simulation Settings を開き、GetObject/PutObject/DeleteObject には Resource ARN arn:aws:s3:::saa-lab-quy-2026/*、ListBucket には arn:aws:s3:::saa-lab-quy-2026 を入力します。Run Simulation を押します。

    期待される結果: GetObject と ListBucket は allowed、PutObject と DeleteObject は denied で理由は「Implicitly denied (no matching statements)」。

  5. 実際の CLI で確認します:

    aws s3 ls s3://saa-lab-quy-2026 --profile reader            # 成功する
aws s3 cp s3://saa-lab-quy-2026/hello.txt . --profile reader  # 成功する
aws s3 cp hello.txt s3://saa-lab-quy-2026/x.txt --profile reader  # AccessDenied

  6. explicit deny の実験: policy に statement "Effect": "Deny", "Action": "s3:GetObject", "Resource": "arn:aws:s3:::saa-lab-quy-2026/*" を追加します（aws iam create-policy-version --set-as-default で新しいバージョンを作るか、コンソールで編集）。Policy Simulator を再実行すると、Allow の statement はそのまま残っているのに、GetObject は「Explicitly denied」の理由で denied になります。これがまさに確認ポイント 2 です。

  7. Sid ListBucket の Resource を .../* に変えてシミュレーターを再実行し、よくある ARN の間違いを自分で確かめます: ListBucket が denied になります。

確認ポイント

資料を見ずに自分で説明できるべき2つの問い

1. user ではなく role を使うのはいつか

回答の骨組み（隠してから自分で言ってみる）:

  • role は STS 経由で一時的な credential を発行し、user は長期の credential を持つ。
  • 主体がソフトウェア（EC2、Lambda、ECS）のとき、cross-account のとき、federated（AD、Google、SSO）のとき、自動でローテーションしたいときは role を使う。
  • 1つのアカウントに長期間ログインする人で、SSO の仕組みがない場合は user を使う。
  • 例を1つ挙げられる: EC2 が S3 に書き込むなら role を付与し、access key を埋め込まない。

2. explicit deny が allow に勝つのはなぜか

回答の骨組み:

  • デフォルトは deny。AWS は該当するすべての policy を集め、まず Deny を探し、見つかればそこで終了する。
  • 目的: 他の場所の Allow policy によって解除されないセーフティネットを管理者に与える。
  • allow が勝てるなら、Allow を追加できる人は誰でも回避できてしまい、deny は無意味になる。
  • 例を1つ挙げられる: aws:RequestedRegion を使った Deny で Region を制限する、または MFA なしの削除を Deny する。
