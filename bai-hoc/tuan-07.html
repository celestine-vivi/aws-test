Lambda: limit, concurrency, layer, VPC, event source

Giải thích ngắn

Lambda chạy một hàm (function) khi có sự kiện, bạn chỉ nộp code và chọn memory, AWS lo server, OS, scale. Tính tiền theo số request và GB-second (memory cấp × thời gian chạy, làm tròn 1 ms). Không có request thì không mất tiền. Always free: 1 triệu request và 400.000 GB-s mỗi tháng.

  • Runtime có sẵn: Python, Node.js, Java, .NET, Ruby, Go (dạng provided), hoặc custom runtime, hoặc container image (tới 10 GB) dựa trên base image của AWS.
  • Một lần gọi = một execution environment (micro VM Firecracker). Môi trường được giữ ấm một lúc để tái dùng cho lần gọi sau, nên biến khởi tạo ngoài handler (kết nối DB, SDK client) được giữ lại.
  • Execution role: IAM role Lambda assume để gọi dịch vụ khác (ghi CloudWatch Logs, đọc DynamoDB). Ngược lại, ai được gọi Lambda là chuyện của resource-based policy trên function (S3, API Gateway, account khác cần được thêm vào đây).

Concurrency và cold start
  • Cold start: lần gọi đầu (hoặc khi phải tạo thêm môi trường) mất thêm thời gian tải code, khởi tạo runtime, chạy phần init. Java, .NET lâu nhất; Python, Node.js nhanh. Hàm trong VPC ngày nay không còn cold start lâu như xưa vì ENI đã được tạo sẵn khi deploy (Hyperplane ENI).
  • Reserved concurrency: dành riêng một số slot cho hàm này, đồng thời là trần của hàm đó. Không mất tiền. Đặt bằng 0 là cách tắt hàm khẩn cấp. Dùng khi muốn bảo vệ downstream (DB chỉ chịu được 50 kết nối → reserved 50).
  • Provisioned concurrency: giữ sẵn N môi trường đã init, không còn cold start, có tính tiền theo giờ dù không gọi. Scale theo lịch hoặc Application Auto Scaling. Đề nói consistent low latency, eliminate cold start → provisioned.
  • SnapStart (nhận diện): chụp snapshot môi trường sau init rồi khôi phục khi gọi, giảm cold start tới 10 lần. Ban đầu chỉ cho Java, đã mở rộng sang Python và .NET (cần kiểm tra lại). Khác provisioned concurrency: SnapStart không giữ môi trường chạy sẵn.
  • Scale: Lambda thêm môi trường mới theo tốc độ khoảng 1.000 mỗi 10 giây cho mỗi function (cần kiểm tra lại); downstream không chịu nổi thì phải tự giới hạn bằng reserved concurrency hoặc chèn SQS làm buffer.

Lambda trong VPC
  • Mặc định Lambda chạy ngoài VPC của bạn, có Internet, gọi được dịch vụ AWS public, nhưng không vào được RDS / ElastiCache private.
  • Gắn vào VPC: chọn subnet và Security Group, Lambda tạo ENI trong subnet đó. Từ đây hàm chỉ có mạng như một máy trong subnet: muốn ra Internet phải là private subnet + NAT Gateway (đặt vào public subnet không có tác dụng vì Lambda không có public IP). Muốn gọi S3, DynamoDB không qua Internet → VPC endpoint.
  • Execution role cần AWSLambdaVPCAccessExecutionRole để tạo ENI.
  • Đề nói Lambda cannot connect to RDS in private subnet → đặt Lambda vào VPC, mở Security Group của RDS cho SG của Lambda. Thêm RDS Proxy khi nhiều Lambda mở quá nhiều kết nối DB.
Layer, URL, Edge
  • Layer: gói zip chứa thư viện, runtime tùy chỉnh hoặc file cấu hình, gắn vào nhiều function. Giảm kích thước package, chia sẻ dependency, nhưng tổng vẫn tính vào 250 MB.
  • Function URL: HTTPS endpoint gắn thẳng vào function, auth AWS_IAM hoặc NONE. Đủ cho webhook đơn giản, không có throttling, usage plan, cache như API Gateway.
  • Lambda@Edge: chạy ở Edge location của CloudFront, viết bằng Node.js hoặc Python, deploy từ us-east-1, hook 4 sự kiện (viewer request / response, origin request / response). Dùng cho A/B test, chỉnh header, chọn origin theo quốc gia, xác thực token. So với CloudFront Functions (JavaScript, chạy dưới 1 ms, chỉ viewer request / response, rẻ hơn, không gọi mạng): việc nhẹ như rewrite URL, thêm header → CloudFront Functions; cần gọi dịch vụ khác, xử lý lâu → Lambda@Edge.
  • Alias và version: publish version bất biến, alias (prod, dev) trỏ tới version; alias chia tải theo tỉ lệ để canary.

Kiểm tra nhanh

1. Một Lambda xử lý ảnh mất 20 giây với memory 512 MB. Developer muốn hàm chạy nhanh hơn mà không sửa code. Làm gì?

Tăng memory. CPU của Lambda tỉ lệ với memory, khoảng 1.769 MB thì được trọn 1 vCPU. Tăng timeout chỉ cho phép chạy lâu hơn chứ không nhanh hơn. Nhiều người chọn "thêm layer" nhưng layer chỉ là cách đóng gói thư viện.

2. Lambda được S3 gọi khi có file upload. Thỉnh thoảng hàm lỗi vì dịch vụ bên ngoài hết hạn mức, công ty không muốn mất sự kiện nào. Cách least operational overhead?

Cấu hình on-failure destination (hoặc DLQ) là một SQS queue cho function. S3 gọi Lambda theo kiểu asynchronous, Lambda tự retry 2 lần rồi đẩy sự kiện lỗi ra destination để xử lý lại sau. Viết code tự ghi lỗi ra DynamoDB cũng được nhưng tốn công hơn. S3 không tự retry.

3. Lambda đặt trong private subnet không gọi được một API public trên Internet, dù Security Group cho phép outbound. Vì sao?

Thiếu NAT Gateway (route 0.0.0.0/0 của private subnet). Lambda trong VPC không có public IP nên dù đặt ở public subnet có Internet Gateway cũng không ra được. Đáp án "chuyển Lambda sang public subnet" là bẫy kinh điển.

4. Account có 20 Lambda. Một hàm xử lý batch ban đêm thỉnh thoảng chiếm gần hết concurrency, khiến hàm phục vụ API của khách bị 429. Sửa thế nào rẻ nhất?

Đặt reserved concurrency cho hàm batch (ví dụ 200) và / hoặc cho hàm API. Reserved vừa là phần dành riêng vừa là trần, không mất tiền. Provisioned concurrency cũng giúp hàm API nhưng tốn tiền theo giờ và không ngăn hàm batch ăn hết phần còn lại.

API Gateway: REST với HTTP API, throttling, cache, authorizer

Giải thích ngắn

API Gateway là "cửa trước" managed cho API: nhận HTTPS request, xác thực, giới hạn tốc độ, cache, chuyển đổi, rồi gọi backend (Lambda, HTTP endpoint, dịch vụ AWS). Có ba loại API: REST API (đầy đủ tính năng nhất), HTTP API (nhẹ, rẻ, đủ cho đa số app mới) và WebSocket API (kết nối hai chiều lâu dài).

  • Ba lớp cấu hình: API → resource / route và method → integration tới backend. Deploy ra stage (dev, prod) có URL riêng, mỗi stage có stage variable để trỏ tới Lambda alias khác nhau.
  • Integration timeout tối đa 29 giây (REST API Regional có thể xin nâng, cần kiểm tra lại); quá thì client nhận 504. Payload tối đa 10 MB.
  • Mã lỗi hay gặp: 429 bị throttle, 502 backend trả sai định dạng (Lambda proxy không trả statusCode), 504 backend quá 29 giây, 403 authorizer từ chối hoặc thiếu API key.

Endpoint type (REST API)
  • Edge-optimized (mặc định): đi qua mạng CloudFront do AWS quản lý, tốt cho client toàn cầu.
  • Regional: client cùng Region, hoặc khi bạn tự đặt CloudFront riêng ở trước để kiểm soát cache, WAF.
  • Private: chỉ gọi được từ trong VPC qua interface VPC endpoint (execute-api), kết hợp resource policy giới hạn aws:SourceVpce. Đề nói API must not be reachable from the Internet → Private.
Throttling và caching
  • Giới hạn account mỗi Region: 10.000 request/giây, burst 5.000 (cần kiểm tra lại). Vượt → 429. Đặt thêm giới hạn theo stage, theo method, hoặc theo khách hàng qua usage plan + API key (rate, burst, quota tháng).
  • Cache (REST): bật theo stage, TTL mặc định 300 giây (0 đến 3.600), dung lượng 0,5 đến 237 GB, tính tiền theo giờ. Client có quyền execute-api:InvalidateCache gửi header Cache-Control: max-age=0 để bỏ cache. Giảm tải Lambda / DB, giảm độ trễ cho dữ liệu ít đổi.
  • Backend bị quá tải → ngoài throttling, cân nhắc đổi integration sang SQS (API Gateway ghi thẳng vào queue, Lambda xử lý sau).

API key không phải cơ chế xác thực, chỉ để nhận diện khách hàng cho usage plan. Đề hỏi authentication mà đáp án là API key thì là bẫy.

Integration: API Gateway gọi gì phía sau
  • Lambda proxy: chuyển nguyên request (header, path, query, body) thành event, Lambda phải trả object có statusCode, headers, body. Đơn giản nhất, dùng trong lab.
  • Lambda non-proxy (custom, REST): dùng mapping template VTL để biến đổi request / response, Lambda không cần biết HTTP.
  • HTTP: chuyển tiếp tới endpoint HTTP bất kỳ (EC2 public, on-prem, ALB). Backend private trong VPC → qua VPC Link.
  • AWS service: gọi thẳng API của dịch vụ AWS không cần Lambda: ghi vào SQS, Kinesis, DynamoDB, start Step Functions. Đề nói without writing code, directly to SQS → integration kiểu này.
  • Mock: trả response cố định, dùng để làm CORS preflight hoặc test khi chưa có backend.

CORS: trình duyệt gọi API từ domain khác cần header Access-Control-Allow-Origin. HTTP API bật bằng cấu hình; REST API proxy integration thì Lambda phải tự trả header này, còn method OPTIONS tạo bằng Mock. Lỗi CORS trên trình duyệt nhưng curl chạy được là dấu hiệu quên bật CORS.

WebSocket API, stage, canary
  • WebSocket API: kết nối hai chiều lâu dài cho chat, dashboard real-time, game. Route $connect, $disconnect, $default và route tùy chỉnh theo nội dung message; backend gửi ngược cho client qua @connections callback URL bằng connectionId (thường lưu trong DynamoDB).
  • Stage: mỗi lần sửa REST API phải deploy lại vào stage, quên deploy là lỗi hay gặp. Stage variable ánh xạ tới Lambda alias để cùng một API trỏ dev / prod khác nhau.
  • Canary release (REST): chia một phần trăm traffic sang deployment mới của cùng stage, xem metric rồi promote hoặc rollback.
  • Monitoring: CloudWatch metric 4XXError, 5XXError, Latency, IntegrationLatency, Count; access log và execution log; X-Ray trace end-to-end.

SQS và SNS: hàng đợi và pub/sub

Giải thích ngắn

SQS (Simple Queue Service) là hàng đợi: producer gửi message vào, consumer kéo (poll) ra xử lý rồi xóa. Mỗi message được một consumer xử lý. Dùng để decouple và làm buffer: frontend nhận đơn nhanh, backend xử lý theo tốc độ của nó, downstream chết thì message vẫn nằm chờ. SNS (Simple Notification Service) là pub/sub: publisher gửi vào topic, SNS đẩy (push) ngay tới mọi subscriber, không lưu lại. Dùng để fan-out một sự kiện tới nhiều nơi.

EventBridge: event bus, rule, schedule

Giải thích ngắn

EventBridge là event bus serverless: sự kiện (JSON) đổ vào bus, rule so khớp theo event pattern rồi gửi tới target. Là phiên bản mở rộng của CloudWatch Events (cùng API, cùng bus default), thêm custom bus, partner bus, schema registry, archive và replay. Chọn EventBridge khi cần định tuyến sự kiện theo nội dung giữa nhiều dịch vụ AWS, ứng dụng của bạn và SaaS bên ngoài.

  • Default bus: nhận sự kiện của các dịch vụ AWS (EC2 state change, S3 qua CloudTrail hoặc S3 Event Notifications, CodePipeline, Health, GuardDuty finding...). Custom bus: cho ứng dụng của bạn PutEvents. Partner bus: SaaS như Zendesk, Datadog, Auth0, Stripe đẩy sự kiện thẳng vào account bạn.
  • Rule: một bus có nhiều rule; mỗi rule tối đa 5 target. Target: Lambda, SQS, SNS, Step Functions, Kinesis Data Streams, Firehose, ECS task, Batch, CodeBuild, SSM Run Command, API Gateway, API Destination (HTTP endpoint ngoài có auth), bus khác (cross-account, cross-Region).
  • Event pattern lọc theo field: source, detail-type, detail.state, có prefix, numeric, exists, anything-but. Input transformer chỉnh lại payload trước khi gửi target.
  • Giao hàng at-least-once, retry tới 24 giờ, có DLQ (SQS) theo từng target cho sự kiện không giao được.

Schedule và EventBridge Scheduler
  • Scheduled rule (cách cũ): rule chạy theo rate(5 minutes) hoặc cron(0 2 * * ? *) gọi target, chỉ trên default bus, giờ UTC.
  • EventBridge Scheduler (dịch vụ riêng, mới hơn): lịch một lần hoặc lặp, chọn time zone, flexible time window, gọi hơn 270 dịch vụ qua API, giới hạn số lịch cao hơn nhiều (hàng triệu), tự xóa sau khi chạy. AWS khuyên dùng Scheduler cho mọi lịch mới. Đề nói run a task at a specific time, schedule in local time zone, one-time schedule → Scheduler.
  • Thay cho cron trên EC2: eliminate the EC2 instance that only runs cron jobs → EventBridge Scheduler + Lambda.
Archive, replay, schema, Pipes
  • Archive: lưu sự kiện khớp pattern trong N ngày hoặc vô hạn. Replay: phát lại sự kiện trong khoảng thời gian vào bus để tái xử lý sau khi sửa bug, hoặc nạp consumer mới. SNS và SQS không có khả năng này.
  • Schema registry: lưu cấu trúc sự kiện, schema discovery tự suy ra từ sự kiện trên bus, sinh code binding (Java, Python, TypeScript) để developer có type.
  • EventBridge Pipes (nhận diện): nối điểm tới điểm một nguồn (SQS, Kinesis, DynamoDB Streams, MSK) với một target, có bước lọc và làm giàu (enrich bằng Lambda / API) ở giữa, không cần code glue.
  • Cross-account: resource policy trên bus của account B cho phép account A (hoặc cả Organization qua aws:PrincipalOrgID) PutEvents; account A tạo rule với target là bus của B. Mẫu "central event bus" cho nhiều account.

Kiểm tra nhanh

19. Một service trên ECS Fargate chạy được nhưng mọi lệnh ghi DynamoDB đều AccessDenied. Container pull image và ghi log bình thường. Sửa ở đâu?

Thêm quyền DynamoDB vào task role trong task definition. Pull image và log là việc của task execution role (đang ổn). Bẫy: chọn sửa execution role hoặc instance role (Fargate không có instance).

20. Công ty có 40 microservice chạy 24/7 với CPU ổn định 70%, đã mua Compute Savings Plans; muốn giảm chi phí container. ECS trên EC2 hay Fargate?

ECS trên EC2 (xếp nhiều task vào instance lớn, tận dụng mật độ cao, và nếu có EC2 Reserved thì càng rẻ). Fargate tốt cho tải biến động hoặc đội không muốn quản lý host; với tải ổn định dày đặc thì EC2 thường rẻ hơn. (Compute Savings Plans áp dụng cho cả hai, nên không phải yếu tố quyết định.)

21. Team không có kinh nghiệm Kubernetes cần chạy một web API container sau load balancer, tự scale theo lượng request, least operational overhead. Chọn?

AWS App Runner (hoặc ECS Fargate + ALB nếu App Runner không có trong đáp án). App Runner tự lo build, HTTPS, LB, scale. EKS mang thêm độ phức tạp của Kubernetes không cần thiết.

22. Ứng dụng Java on-prem dùng ActiveMQ với giao thức JMS, cần chuyển lên AWS trong 2 tuần, không được sửa code. Chọn?

Amazon MQ (engine ActiveMQ). SQS / SNS cần đổi code sang API AWS. Đề nói new application thì mới chọn SQS / SNS.

Lab 1. CRUD API: API Gateway HTTP API + Lambda (Python) + DynamoDB

  1. Tạo bảng DynamoDB on-demand, partition key id:

    aws dynamodb create-table --table-name saa-items `
  --attribute-definitions AttributeName=id,AttributeType=S `
  --key-schema AttributeName=id,KeyType=HASH `
  --billing-mode PAY_PER_REQUEST
aws dynamodb wait table-exists --table-name saa-items

  2. Tạo execution role cho Lambda. File trust.json:

    { "Version": "2012-10-17", "Statement": [{ "Effect": "Allow",
  "Principal": { "Service": "lambda.amazonaws.com" }, "Action": "sts:AssumeRole" }] }

    File ddb-policy.json (chỉ bảng này, đây là task role kiểu Lambda):

    { "Version": "2012-10-17", "Statement": [{ "Effect": "Allow",
  "Action": ["dynamodb:GetItem","dynamodb:PutItem","dynamodb:DeleteItem","dynamodb:Scan"],
  "Resource": "arn:aws:dynamodb:ap-northeast-1:<account-id>:table/saa-items" }] }
    aws iam create-role --role-name saa-items-lambda-role --assume-role-policy-document file://trust.json
aws iam attach-role-policy --role-name saa-items-lambda-role `
  --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole
aws iam put-role-policy --role-name saa-items-lambda-role --policy-name ddb --policy-document file://ddb-policy.json

    AWSLambdaBasicExecutionRole chỉ cho ghi CloudWatch Logs. Quyền DynamoDB là inline policy riêng, giới hạn đúng một bảng.

  3. Viết lambda_function.py. Hàm nhận event của HTTP API (payload v2), rẽ nhánh theo method và path, trả object có statusCode và body (Lambda proxy integration):

    import json, os, boto3
table = boto3.resource("dynamodb").Table(os.environ["TABLE"])

def lambda_handler(event, context):
    method = event["requestContext"]["http"]["method"]
    path = event.get("rawPath", "/")
    parts = [p for p in path.split("/") if p]      # ["items"] hoặc ["items","1"]
    item_id = parts[1] if len(parts) > 1 else None
    try:
        if method == "GET" and item_id:
            r = table.get_item(Key={"id": item_id})
            body, code = r.get("Item", {}), 200 if "Item" in r else 404
        elif method == "GET":
            body, code = table.scan(Limit=50).get("Items", []), 200
        elif method == "PUT":
            data = json.loads(event.get("body") or "{}")
            table.put_item(Item=data)
            body, code = {"ok": True, "id": data.get("id")}, 200
        elif method == "DELETE" and item_id:
            table.delete_item(Key={"id": item_id})
            body, code = {"deleted": item_id}, 200
        else:
            body, code = {"error": "unsupported route"}, 400
    except Exception as e:
        body, code = {"error": str(e)}, 500
    return {"statusCode": code, "headers": {"content-type": "application/json"},
            "body": json.dumps(body, default=str)}

    Lưu ý: giá trị số trong DynamoDB trả về dạng Decimal, default=str để json.dumps không lỗi.

  4. Đóng gói và tạo function (Python 3.12, memory 256 MB, timeout 10 giây). Chờ vài giây cho IAM role lan truyền nếu gặp lỗi "role cannot be assumed":

    Compress-Archive -Path .\lambda_function.py -DestinationPath .\function.zip -Force
aws lambda create-function --function-name saa-items-api --runtime python3.12 `
  --handler lambda_function.lambda_handler --zip-file fileb://function.zip `
  --role arn:aws:iam::<account-id>:role/saa-items-lambda-role `
  --memory-size 256 --timeout 10 --environment "Variables={TABLE=saa-items}"

    Test trực tiếp không qua API (gọi synchronous RequestResponse):

    '{"requestContext":{"http":{"method":"GET"}},"rawPath":"/items"}' | Set-Content -Encoding ascii evt.json
aws lambda invoke --function-name saa-items-api --payload fileb://evt.json out.json
Get-Content out.json      # mong đợi statusCode 200, body "[]"

  5. Tạo HTTP API bằng quick create (tự sinh integration Lambda proxy, route $default và stage $default auto deploy), rồi cấp quyền cho API Gateway gọi Lambda (resource-based policy của function):

    aws apigatewayv2 create-api --name saa-items-http --protocol-type HTTP `
  --target arn:aws:lambda:ap-northeast-1:<account-id>:function:saa-items-api
# ghi lại ApiId và ApiEndpoint trong kết quả
aws lambda add-permission --function-name saa-items-api --statement-id apigw `
  --action lambda:InvokeFunction --principal apigateway.amazonaws.com `
  --source-arn "arn:aws:execute-api:ap-northeast-1:<account-id>:<ApiId>/*"

    Mở Console → API Gateway → API vừa tạo → Routes: chỉ có $default bắt mọi path, nên code mới phải tự đọc rawPath. Thử thêm route tường minh GET /items/{id} trỏ cùng integration để thấy event["routeKey"] và pathParameters đổi.

  6. Test CRUD bằng curl. Trong PowerShell curl là alias của Invoke-WebRequest nên dùng curl.exe:

    $API = "https://<ApiId>.execute-api.ap-northeast-1.amazonaws.com"
curl.exe -s -X PUT "$API/items" -H "content-type: application/json" -d '{\"id\":\"1\",\"name\":\"pen\",\"price\":3}'
curl.exe -s -X PUT "$API/items" -H "content-type: application/json" -d '{\"id\":\"2\",\"name\":\"book\",\"price\":12}'
curl.exe -s "$API/items"
curl.exe -s "$API/items/1"
curl.exe -s -X DELETE "$API/items/1"
curl.exe -s -i "$API/items/1"     # mong đợi HTTP 404

  7. Quan sát: Console → Lambda → Monitor → View CloudWatch logs, xem dòng REPORT có Duration, Billed Duration, Max Memory Used, và Init Duration ở lần gọi đầu (cold start). Gọi lại ngay thì không còn Init Duration. Vào tab Configuration → Concurrency để thấy reserved và provisioned concurrency. Ở API Gateway → Throttling trên stage để thấy giới hạn mặc định.

  8. Thí nghiệm nhỏ: đặt reserved concurrency của function bằng 0 rồi gọi API: nhận 500 / 429 ngay lập tức, đây là cách "tắt" hàm khẩn cấp. Xóa reserved concurrency sau khi thử.

  1. Tạo topic và ba queue (hai queue nhận, một DLQ):

aws sqs create-queue --queue-name saa-orders-email

# Lấy URL và ARN, ghi lại

  2. Bật DLQ cho queue analytics với maxReceiveCount = 3 và giảm visibility timeout xuống 5 giây để thí nghiệm nhanh. File redrive.json (giá trị RedrivePolicy là chuỗi JSON lồng, phải escape):

}
    aws sqs set-queue-attributes --queue-url <url-analytics> --attributes file://redrive.json

  3. Cho phép SNS gửi vào hai queue (access policy của queue, bước hay quên nhất). File qpolicy-email.json, làm tương tự cho analytics:

    {
  "Policy": "{\"Version\":\"2012-10-17\",\"Statement\":[{\"Effect\":\"Allow\",\"Principal\":{\"Service\":\"sns.amazonaws.com\"},\"Action\":\"sqs:SendMessage\",\"Resource\":\"arn:aws:sqs:ap-northeast-1:<account-id>:saa-orders-email\",\"Condition\":{\"ArnEquals\":{\"aws:SourceArn\":\"arn:aws:sns:ap-northeast-1:<account-id>:saa-orders\"}}}]}"
}

aws sqs set-queue-attributes --queue-url <url-analytics> --attributes file://qpolicy-analytics.json

  4. Subscribe hai queue vào topic, bật raw message delivery để message trong queue là body gốc:

    aws sns subscribe --topic-arn arn:aws:sns:ap-northeast-1:<account-id>:saa-orders `
  --protocol sqs --notification-endpoint arn:aws:sqs:ap-northeast-1:<account-id>:saa-orders-email `
  --attributes RawMessageDelivery=true --return-subscription-arn
aws sns subscribe --topic-arn arn:aws:sns:ap-northeast-1:<account-id>:saa-orders `
  --protocol sqs --notification-endpoint arn:aws:sqs:ap-northeast-1:<account-id>:saa-orders-analytics `
  --attributes RawMessageDelivery=true --return-subscription-arn

  5. Publish một message có attribute type=normal rồi nhận ở cả hai queue bằng long polling 10 giây:

    aws sns publish --topic-arn arn:aws:sns:ap-northeast-1:<account-id>:saa-orders `
  --message '{\"orderId\":101,\"total\":40}' `
  --message-attributes '{\"type\":{\"DataType\":\"String\",\"StringValue\":\"normal\"}}'

aws sqs receive-message --queue-url <url-analytics> --wait-time-seconds 10

    Cả hai queue đều có message: đó là fan-out. Nếu queue trống, kiểm tra lại access policy ở bước 3 (Console → SNS → Subscriptions → cột Status phải là Confirmed).

  6. Thêm filter policy cho subscription email, chỉ nhận type=vip:

    aws sns set-subscription-attributes --subscription-arn <arn-sub-email> `
  --attribute-name FilterPolicy --attribute-value '{\"type\":[\"vip\"]}'

    Publish thêm hai message, một type=vip (orderId 102) và một type=normal (orderId 103). Nhận lại: queue email chỉ có 102, queue analytics có cả 102 và 103. Xóa message đã đọc bằng aws sqs delete-message --receipt-handle hoặc Console → Purge.

  7. Thí nghiệm DLQ: publish một message mới, rồi receive-message trên queue analytics 4 lần liên tiếp, mỗi lần cách nhau hơn 5 giây, không delete. Lần 1 đến 3 thấy message, lần 4 trống. Kiểm tra DLQ:

    aws sqs get-queue-attributes --queue-url <url-dlq> --attribute-names ApproximateNumberOfMessages

    Message đã sang DLQ vì bị nhận quá maxReceiveCount = 3. Vào Console → SQS → saa-orders-dlq → Start DLQ redrive để đẩy ngược về queue nguồn, đây chính là "redrive" trong đề.

  8. Đọc lại trên Console: SNS topic → tab Subscriptions xem filter policy; SQS queue → Monitoring xem NumberOfMessagesSent, ApproximateAgeOfOldestMessage (metric hay dùng để cảnh báo consumer chết).

    import * as cdk from 'aws-cdk-lib';
import { Construct } from 'constructs';
import * as dynamodb from 'aws-cdk-lib/aws-dynamodb';
import * as lambda from 'aws-cdk-lib/aws-lambda';
import * as apigwv2 from 'aws-cdk-lib/aws-apigatewayv2';
import { HttpLambdaIntegration } from 'aws-cdk-lib/aws-apigatewayv2-integrations';

export class SaaCdkApiStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    const table = new dynamodb.Table(this, 'Items', {
      partitionKey: { name: 'id', type: dynamodb.AttributeType.STRING },
      billingMode: dynamodb.BillingMode.PAY_PER_REQUEST,
      removalPolicy: cdk.RemovalPolicy.DESTROY,   // để cdk destroy xóa luôn bảng
    });

    const fn = new lambda.Function(this, 'ItemsFn', {
      runtime: lambda.Runtime.PYTHON_3_12,
      handler: 'lambda_function.lambda_handler',
      code: lambda.Code.fromAsset('lambda'),
      memorySize: 256,
      timeout: cdk.Duration.seconds(10),
      environment: { TABLE: table.tableName },
    });
    table.grantReadWriteData(fn);                  // tự sinh IAM policy đúng bảng

    const api = new apigwv2.HttpApi(this, 'ItemsApi', {
      defaultIntegration: new HttpLambdaIntegration('ItemsInt', fn),
    });
    new cdk.CfnOutput(this, 'ApiUrl', { value: api.apiEndpoint });
  }
}

Mốc kiểm tra

Hai câu phải tự nói được không nhìn tài liệu

1. Khi nào dùng SQS, SNS, EventBridge, Kinesis?

Gợi ý khung trả lời (che lại rồi tự nói):

  • SQS: hàng đợi, consumer pull, mỗi message một consumer xử lý rồi xóa. Dùng để decouple và buffer (web tier → queue → worker). Standard: không giới hạn, at-least-once; FIFO: thứ tự + exactly-once, 300/3.000 msg/s. Nhớ visibility timeout, DLQ, long polling.
  • SNS: pub/sub, push tới nhiều subscriber ngay, không lưu. Dùng để fan-out (SNS → nhiều SQS) và gửi cho người (email, SMS, push). Filter policy để lọc.
  • EventBridge: event bus, rule định tuyến theo nội dung; nguồn là dịch vụ AWS, SaaS partner, app của bạn; có schedule, archive / replay, schema registry. Dùng cho tích hợp event-driven giữa nhiều dịch vụ và lịch chạy.
  • Kinesis: streaming real-time tốc độ MB/s, dữ liệu giữ trong shard 24 giờ đến 365 ngày, nhiều consumer đọc cùng dữ liệu, replay, thứ tự theo partition key. Firehose khi chỉ cần đổ vào S3 / Redshift / OpenSearch gần real-time.
  • Kể được 1 ví dụ mỗi loại: đơn hàng vào SQS cho worker; thông báo đơn tới kho + hóa đơn + email qua SNS; EC2 terminate tạo ticket qua EventBridge; clickstream phân tích theo phút qua Kinesis.

2. ECS trên EC2 khác Fargate ở đâu?

Gợi ý khung trả lời:

  • Cùng ECS (cluster, task definition, service), khác ở ai quản lý host: EC2 là bạn (instance type, AMI, vá OS, ECS agent, ASG); Fargate là AWS, bạn chỉ khai báo vCPU / memory cho task.
  • Tính tiền: EC2 theo instance chạy (trả cả chỗ trống, dùng được RI / Spot); Fargate theo vCPU và memory của từng task theo giây.
  • Khi nào chọn EC2: GPU, mật độ cao tải ổn định để rẻ hơn, cần truy cập host / docker daemon, network mode bridge / host, RI sẵn có. Khi nào chọn Fargate: serverless, least operational overhead, tải biến động, nhiều service nhỏ, cô lập từng task bằng ENI riêng (awsvpc bắt buộc).
  • Scale: EC2 có hai tầng (task và instance, cần capacity provider managed scaling); Fargate chỉ một tầng task.
  • Kể được: task role (ứng dụng) khác task execution role (pull ECR, ghi log) ở cả hai launch type.
