Amazon RDS：Multi-AZ、Read Replica、backup、encryption、RDS Proxy

概要
  • RDS はマネージドなリレーショナルデータベースです。インストール、OS とエンジンのパッチ適用、backup、Multi-AZ、monitoring は AWS が担当します。サーバーに SSH はできず、DNS endpoint 経由で接続します。エンジン：MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, Db2、さらに Aurora（第2項で学習）。
  • 各 DB instance は instance class（db.t3.micro、db.m6g.large…）上で動作し、EBS storage は gp3 または io1/io2、VPC の subnet group 内に配置され、Security Group でポートを開けます（MySQL 3306、PostgreSQL 5432、SQL Server 1433）。
  • Storage autoscaling：「maximum storage threshold」を設定すると、空き容量が10%を下回ったときに RDS が自動で拡張します。ダウンタイムはありません。拡張のみで、自動で縮小はしません。
  • RDS Custom（Oracle、SQL Server）：OS と DB にアクセスしてエージェントの導入や詳細な調整ができる代わりに、運用の一部を自分で担います。RDS で need OS access や customize the database environment とあれば → RDS Custom。

Multi-AZ DB cluster（新しいタイプ、MySQL と PostgreSQL）
  • writer 1台 + 別々の2つの AZ にreader standby 2台、レプリケーションはsemi-synchronous（少なくとも1台の standby が受信した時点で書き込みが確定）。Multi-AZ instance との違いは standby が読み取り可能で、専用の reader endpoint があることです。
  • Failover は Multi-AZ instance より速く（AWS によると通常35秒未満、AWSドキュメントで要確認）、待つ standby が1台だけなので書き込みレイテンシも低くなります。
  • Multi-AZ with readable standbys、two readable standby instances とあれば → Multi-AZ DB cluster。Aurora cluster と混同しないこと。

  • Multi-AZ の場合、automated backup は standby で実行されます。Single-AZ では backup window 中に数秒間 I/O が止まることがあります。

Encryption と authentication
  • KMS による at rest 暗号化は instance の作成時にしか有効化できません。暗号化なしで作成済みの場合の手順：snapshot を取得 → snapshot をコピーして暗号化を選択 → 暗号化済み snapshot から restore → app を新しい instance に向ける。逆に、暗号化された DB の snapshot を暗号化なしでコピーすることはできません。
  • 暗号化された DB の read replica も暗号化されます。暗号化されていない primary から暗号化された replica は作成できません。
  • In transit：SSL/TLS を使い、RDS の CA bundle をダウンロードします。MySQL/PostgreSQL ではパラメータ require_secure_transport または rds.force_ssl で強制できます。
  • IAM database authentication（MySQL、PostgreSQL、MariaDB）：password の代わりに IAM が発行する token（有効期間15分）を使います。EC2/Lambda は role を使い、password を保持しません。avoid storing database passwords、use IAM to connect とあれば → IAM DB auth。rotate password automatically とあれば → Secrets Manager。
  • Transparent Data Encryption (TDE)：Oracle と SQL Server 独自の暗号化方式で、KMS encryption と併用できます。
RDS Proxy と Performance Insights
  • RDS Proxy：app と DB の間に置くマネージドなconnection pooling 層です。Lambda が数千の connection を開き、DB の connection が枯渇する（"too many connections"）問題を解決します。failover 時は proxy が app 側の connection を保持したまま新しい instance に切り替えるため、体感ダウンタイムを最大66%削減できます（AWS の公表値、AWSドキュメントで要確認）。IAM auth と Secrets Manager に対応。VPC 内からのみアクセスでき、public にはできません。
  • Performance Insights：wait event、SQL、ユーザー別に DB 負荷を可視化するダッシュボードで、どの SQL が負荷の原因か分かります。7日分のデータは無料です。identify the SQL statements causing high load とあれば → Performance Insights。Enhanced Monitoring は別物で、ホスト上のエージェントから OS メトリクス（プロセスごとの CPU、メモリ）を1秒間隔で取得します。
RDS の使いどころ
  • リレーショナルデータで SQL、join、transaction が必要な場合。既存の app が MySQL/PostgreSQL/Oracle/SQL Server 向けに書かれていて、OS を運用せずに lift and shift したい場合。
  • RDS を選ばないケース：OS へのアクセスが必要（EC2 に自前で構築するか RDS Custom）、リクエスト量が非常に多い非リレーショナルデータ（DynamoDB）、TB 級の分析基盤（Redshift）、書き込みをほぼ無限に水平スケールしたい（RDS の書き込みスケールは instance class の変更のみで、短いダウンタイムを伴う）。

確認クイズ

1. RDS MySQL Single-AZ を使うアプリケーションで、AWS が OS メンテナンスを行うたびに app が数分間停止します。least operational overhead で停止時間を減らす方法は？

Multi-AZ を有効化する。 RDS はまず standby にパッチを当て、failover してから旧 primary にパッチを当てるため、app は同じ endpoint への再接続で数十秒止まるだけです。Read Replica は役に立ちません。primary のメンテナンス中は書き込みが止まり、replica は自動でトラフィックを引き受けないためです。

2. RDS PostgreSQL を暗号化なしで作成しましたが、コンプライアンス上 at rest の暗号化が必要になりました。どうしますか？

snapshot を取得し、KMS 暗号化オプション付きで snapshot をコピーし、新しい instance として restore して app を切り替える。 稼働中の instance で encryption を有効化する方法はありません。暗号化なしの primary から暗号化された read replica を作ることもできません。

3. 数百の Lambda function が RDS MySQL を呼び出し、ピーク時に "Too many connections" エラーが発生します。何を選びますか？

RDS Proxy。 Proxy が connection をまとめて Lambda 間で再利用し、failover 時間も短縮します。max_connections や instance class を上げても上限が上がるだけで、Lambda がスケールすればまた超えてしまいます。問題は connection 数であって読み取り負荷ではないため、Read Replica も効果がありません。

4. 正しい記述を2つ選んでください：(A) Multi-AZ instance の standby は読み取りに使える、(B) Read Replica は async replication を使う、(C) Automated backup は最大35日保持、(D) snapshot からの restore は既存の instance を上書きする。

B と C。 A は Multi-AZ instance では誤りです（読み取り可能な standby を持つのは Multi-AZ DB cluster だけ）。D も誤りで、restore は常に新しい endpoint を持つ新しい instance を作成します。

Amazon Aurora：cluster volume、endpoint、Global Database、Serverless

概要
  • Aurora は AWS が独自に開発したリレーショナルエンジンで、MySQL と PostgreSQL に互換性があります（app は通常どおり接続でき、driver も変わりません）。AWS の公表では RDS 上の MySQL の最大5倍、PostgreSQL の最大3倍高速で、価格は同じサイズの RDS より約20%高くなります（AWSドキュメントで要確認）。
  • 根本的な違いはstorage と compute の分離です。データは共有のcluster volume に置かれ、3つの AZ に6コピー（各 AZ に2コピー）が自動で作られます。書き込みは6コピー中4つ、読み取りは3つの確認で成立するため、AZ を1つ丸ごと失っても読み書きできます。Volume は10 GB 単位で128 TiB まで自動拡張し（AWSドキュメントで要確認）、実際に使った容量分だけ課金されます。
  • 1つの cluster は writer 1台（primary）と、同じ volume を読む最大15台の Aurora Replica で構成されます。そのため replica lag は通常100 ms 未満です（RDS Read Replica のようにデータをコピーしない）。Replica は standby も兼ねており、replica への failover は約30秒です。選ばれる順番はpriority tier 0〜15 で決まります（数字が小さいほど優先、同じ tier なら大きい instance）。
  • S3 への継続的な backup、秒単位の PITR、retention 1〜35日で、性能への影響はありません。KMS 暗号化も作成時にしか選べません。

Replica auto scaling、Global Database、Serverless v2
  • Aurora Replica auto scaling：replica の平均 CPU や connection 数に基づく policy を設定すると、Aurora が replica を自動で増減します（上限15）。Reader endpoint には新しい replica が自動で含まれます。read traffic varies throughout the day とあれば → replica auto scaling。
  • Aurora Global Database：primary Region 1つ + secondary Region 最大5つ（AWSドキュメントで要確認）。storage 層でレプリケーションし、lag は通常1秒未満です。各 secondary には最大16台の読み取り replica を置けます。primary Region が停止した場合は secondary を promote（managed failover または detach）して RPO 約1秒、RTO 1分未満を実現します。disaster recovery across Regions や low-latency global reads に使います。write forwarding もあり、secondary Region の app が送った書き込みを Aurora が primary に転送します。
  • Aurora Serverless v2：compute は ACU（Aurora Capacity Unit、1 ACU は約2 GiB RAM）で計測し、0.5 ACU から設定した上限まで即座にスケールします。スケール時に接続は切れません。同じ cluster 内で通常の instance と serverless を混在でき、Global Database や Multi-AZ にも対応します。unpredictable、intermittent、spiky workload、dev/test 環境、pay only for capacity used のときに選びます。旧 v1 はスケールが遅く、ひっかけの選択肢としてよく出るので「v2」という名前を覚えておきましょう。

RDS ではなく Aurora を選ぶとき
  • 問題文が highest performance、highly available、minimal downtime、self-healing storage、automatic storage scaling を強調している場合。5台を超える read replica、非常に低い replica lag、最初から用意された reader endpoint、または RPO 1秒の Global Database が必要な場合。
  • RDS を選ぶとき：エンジンが MySQL/PostgreSQL 以外（Oracle、SQL Server）、小規模ワークロードで予算が少ない（RDS db.t3.micro の方が安い）、または問題文が単純な「managed relational」だけを求めている場合。
  • データが非リレーショナルの場合や、書き込みを無制限にスケールしたい場合は Aurora を選びません（DynamoDB）。

5. Aurora MySQL に writer 1台と replica 3台があります。レポート app はある replica の instance endpoint を指していますが、その replica が failover で writer になると、レポートが書き込みを遅くしてしまいます。最小限の変更で直すには？

レポート app を reader endpoint に向ける（または replica だけを含む custom endpoint）。Reader endpoint は常に writer を除外し、replica 間で自動的に負荷分散します。instance endpoint は特定のマシンに固定されるため、役割が変わると問題が起きます。

6. 東京とフランクフルトのユーザー向けに PostgreSQL DB が必要です。両方で高速に読み取れ、東京が停止したら数分以内にフランクフルトへ切り替え、RPO は1分未満にしたい。何を選びますか？

Aurora PostgreSQL Global Database（primary は東京、secondary はフランクフルト）。RDS cross-Region Read Replica でもフランクフルトで読めますが、lag が大きく promote も手動なので、厳しい RPO/RTO を満たせません。Multi-AZ は1つの Region 内だけです。

7. 開発者が20分前、Aurora MySQL の本番環境で WHERE なしの UPDATE を誤って実行しました。fastest な復旧方法は？

コマンド実行前の時点に cluster を Backtrack する。 数分で、その場で完了し、endpoint も変わりません。PITR でも復旧できますが、新しい cluster を作って app を切り替える必要があり遅くなります。Backtrack は事前に有効化（cluster の作成時または変更時）しておく必要があり、Aurora MySQL だけで使えます。

DynamoDB：capacity、index、DAX、Streams、TTL、Global Table

概要
  • DynamoDB：key-value と document の NoSQL です。完全な serverless（instance もパッチもなし）で、どんな規模でも1桁ミリ秒のレイテンシ、3つの AZ への自動レプリケーション、読み書きともほぼ無限にスケールします。常に at rest で暗号化されます。
  • Primary key：partition key のみ（hash、一意である必要あり）、または partition key + sort key（組み合わせが一意、同じ partition key に複数の item が sort key 順に並ぶ）。Partition key は item が置かれる物理 partition を決めるため、均等に分散するキーを選ぶ必要があります（user ID は良い、「status = active」は悪い）。
  • item の最大サイズは400 KB です。大きなオブジェクト（画像、ファイル）は S3 に置き、DynamoDB には S3 のキーとメタデータを保存します。join はなく、キー以外に固定スキーマはありません。
  • クエリ：Query（partition key を指定し sort key で絞り込む、安価）と Scan（テーブル全体を読む、高コスト、避ける）。GetItem/PutItem はキー指定です。
  • Consistency：読み取りはデフォルトで eventually consistent（1秒未満の遅れがありうる、RCU は半分）。Strongly consistent は最新データを返し、コストは2倍で、GSI では使えません。Transactions（TransactWriteItems、TransactGetItems）は最大100 item で ACID を提供し、capacity は2倍かかります。

DAX、Streams、TTL
  • DAX (DynamoDB Accelerator)：DynamoDB 専用のインメモリキャッシュです。API 互換なので app は endpoint を変えるだけで、キャッシュのロジックを書く必要はありません。読み取りを ms からマイクロ秒に短縮し、GetItem だけでなく Query/Scan もキャッシュします。最大10ノードの Multi-AZ cluster。read-heavy、microsecond latency、reduce read cost、minimal code changes のときに選びます。書き込みや strongly consistent read はキャッシュしません。複数のデータソースで共有するキャッシュや、sorted set のような構造が必要なら → ElastiCache（第4項）。
  • DynamoDB Streams：テーブルの変更（insert、update、delete）を順序どおりに記録するログで、24時間保持されます。view は KEYS_ONLY、NEW_IMAGE、OLD_IMAGE、NEW_AND_OLD_IMAGES から選びます。通常は Lambda trigger をつなぎ、新しいレコードの通知、OpenSearch へのコピー、集計、監査などを行います。Kinesis Data Streams for DynamoDB は代替手段で、最大1年保持、複数の consumer、Firehose 連携が可能ですが、順序は厳密には保証されず、レコードが重複することもあります。
  • TTL (Time to Live)：epoch 秒を格納する number 型の attribute を指定します。期限切れの item は数日以内に削除され（通常48時間以内、AWSドキュメントで要確認）、WCU を消費しません。まだ削除されていない期限切れ item は、フィルターしなければ読み取れてしまいます。TTL で削除されたレコードは Streams 上で userIdentity.principalId = dynamodb.amazonaws.com となるため、手動削除と区別できます。セッション、OTP、一時ログ、N日後に削除すべきデータなどに使い、容量を減らします。
Global Table、PITR、backup
  • Global Table：複数の Region で active-active にレプリケーションされるテーブルです。app は最寄りの Region で読み書きし、lag は通常1秒未満です。Streams の有効化が必須（NEW_AND_OLD_IMAGES）。2つの Region で同じ item への書き込みが競合した場合は last writer wins で解決します。multi-Region active-active、low latency for global users、Region failover for DynamoDB に使います。Aurora Global Database（書き込みは1つの Region のみ）とは異なります。
  • Point-in-time recovery：有効にすると35日間の継続 backup が取られ、任意の秒の時点に新しいテーブルとして restore できます。On-demand backup：無期限に保持でき、性能への影響はありません。どちらも AWS Backup と統合されており、cross-Region、cross-account のコピーが可能です。
  • Export to S3（RCU を消費しない）で Athena による分析ができます。Import from S3 で大量のデータを投入できます。
DynamoDB を選ぶとき

8. DynamoDB の Orders テーブルは partition key が OrderID です。カスタマーサポートが顧客のメールアドレスで注文を検索したいと考えています。テーブルには既に5,000万件の item があります。least operational overhead で実現するには？

CustomerEmail を partition key とする GSI を作成する。 GSI はデータのある既存テーブルにも追加できます。LSI はテーブル作成後には追加できず、partition key も同じでなければなりません。filter 付きの Scan はテーブル全体を読むため、RCU を消費し遅くなります。

9. モバイルゲームのスコアを DynamoDB に保存しており、95% がランキングの読み取りです。現在のレイテンシは5 ms で、minimal code changes で1 ms 未満にしたい。何を選びますか？

DAX。 DynamoDB API 互換なので SDK の endpoint を変えるだけで、マイクロ秒でキャッシュから読み取れます。ElastiCache Redis でもこのレイテンシは達成できますが、cache-aside のロジックを書く必要があり「minimal code changes」に反します。RCU を増やしてもレイテンシは下がりません。

10. セッションテーブルに TTL を設定しています。監査から、期限切れで削除されたセッションと、app が能動的に削除したセッションをどう区別するのか質問されました。

DynamoDB Streams を有効にする。TTL による削除レコードは userIdentity が dynamodb.amazonaws.com になる。 手動削除にはこのフィールドがありません（または app の principal になります）。Lambda をつないで監査ログに書き込むこともできます。

11. Global Table について正しい記述を2つ選んでください：(A) DynamoDB Streams の有効化が必要、(B) 書き込めるのは1つの Region だけ、(C) 競合は last writer wins で解決される、(D) レプリケーションは同期なので lag がない。

A と C。 B は誤りです。Global Table は active-active で、すべての Region で書き込めます。D も誤りで、レプリケーションは非同期で lag は通常1秒未満です。だからこそ競合時の last writer wins というルールが必要になります。

概要
  • ElastiCache はマネージドなインメモリキャッシュで、database の前に置いて読み取り負荷を減らし、レイテンシを1 ms 未満にします。エンジンは2つ：Redis（および Redis 互換のオープン版 Valkey）と Memcached。VPC 内に配置し、Security Group 経由でアクセスします。public にはできません。

Redshift と Redshift Spectrum

概要
  • Redshift はマネージドな data warehouse（OLAP）です。PostgreSQL ベースで、columnar（列指向）で保存し圧縮効率も高いため、数十億行をスキャンする集計クエリ（SUM、GROUP BY）を RDS より何倍も速く処理できます。ペタバイト規模に対応。レポートや BI（QuickSight、Tableau）に使い、OLTP（1行ずつの継続的な書き込み、短い transaction）には使いません。
  • cluster の構成：leader node 1台が SQL を受け取って実行計画を立て、結果を集約します。複数の compute node がデータを slice に分割して並列実行します（MPP、massively parallel processing）。Node type の RA3 は compute と storage を分離（データは managed S3 上）、DC2 は小規模データ向けのローカル SSD です。
  • データ投入：S3 からの COPY コマンド（並列で最速）、DynamoDB や EMR から、または Kinesis Data Firehose 経由。1行ずつの INSERT は避けます。
  • 1つの AZ に配置されます（RA3 では Multi-AZ が新たに利用可能、AWSドキュメントで要確認）。Redshift の HA：故障ノードの自動交換、S3 への自動 snapshot、DR のための別 Region への snapshot コピー。disaster recovery for Redshift とあれば → cross-Region snapshot copy。
  • Enhanced VPC Routing：COPY/UNLOAD のトラフィックをインターネットではなく VPC 内（endpoint 経由）に通すよう強制します。Concurrency Scaling：同時クエリが多いときに一時的な cluster を自動で追加します。
Redshift Spectrum と Redshift Serverless
  • Redshift Spectrum：S3 上のファイル（Parquet、ORC、CSV、JSON）に対して、cluster にロードせずに直接 SQL を実行し、Redshift 内のテーブルと join できます。稼働中の Redshift cluster が必要で、S3 のテーブルは external schema（Glue Data Catalog）で定義します。query exabytes in S3 from Redshift、join historical data in S3 with warehouse data、without loading のときに選びます。
  • Redshift Serverless：cluster の管理が不要で、RPU で計測し、自動でスケールし、クエリの実行秒数で課金されます。ad hoc、intermittent analytics、no cluster management のときに選びます。中身は Redshift のままです（columnar、SQL、Spectrum も使える）。
  • Data sharing：cluster やアカウント間でライブデータをコピーせずに共有します。Aurora から Redshift への Zero-ETL：自動でレプリケーションされ、パイプラインを書かずにほぼリアルタイムで分析できます。

理論 6 / 7

DMS と Schema Conversion Tool

概要
  • Database Migration Service (DMS)：ソースを稼働させたまま、ソース DB からターゲット DB へデータを移行します。replication instance（DMS が管理する EC2、サイズは自分で選択、Multi-AZ 可）上で、source endpoint、target endpoint、migration task を使って動作します。ソースはオンプレミス、EC2、RDS、S3。ターゲットは RDS、Aurora、DynamoDB、Redshift、S3、OpenSearch、Kinesis、DocumentDB など。
  • task は3種類です：Full load（1回だけコピー）、Full load + CDC（コピー後も変更を同期し続ける）、CDC only。CDC (change data capture) はソースの transaction log を読んで継続的にレプリケーションし、ダウンタイムをほぼゼロにします。両側が同期できてから app をターゲットに切り替えます。minimal downtime migration、continuous replication、keep source running とあれば → DMS と CDC。
  • Homogeneous（同じエンジン、Oracle → Oracle、MySQL → Aurora MySQL）：DMS で直接移行します。Heterogeneous（エンジンの変更、Oracle → Aurora PostgreSQL、SQL Server → MySQL）：まず SCT で schema を変換し、その後 DMS でデータを移行します。
  • Schema Conversion Tool (SCT)：PC にインストールするソフトウェアで、ソースの schema、stored procedure、view を分析してターゲットエンジンの構文に変換し、手作業で直す部分を示す評価レポートも出力します。SCT にはデータウェアハウス（Oracle、Teradata、Netezza）を Redshift に移す extractor もあります。現在は DMS コンソール内で SCT を実行することもできます（DMS Schema Conversion）。
  • 大容量データまたは低帯域：DMS と Snowball Edge を組み合わせます。SCT がデータを Snowball に抽出して AWS へ輸送し、DMS が S3 からターゲットにロード、輸送中に発生した変更は CDC で同期します。terabytes、limited bandwidth、migrate database とあれば → DMS + Snowball。

            item["expireAt"] = int(time.time()) + int(event["ttlSeconds"])
        table.put_item(Item=item)
        return {"written": item}
    resp = table.query(KeyConditionExpression=boto3.dynamodb.conditions.Key("userId").eq(user_id))
    return {"count": resp["Count"], "items": resp["Items"]}

    zip にして function を作成します（role の作成後、IAM の反映を数秒待ちます）：

  --role arn:aws:iam::<account-id>:role/saa-lambda-ddb-role `
  --handler lambda_function.lambda_handler --zip-file fileb://fn.zip `
  --environment "Variables={TABLE=saa-notes}" --timeout 10

    注意：返される item の数値は Decimal 型になります。Lambda が戻り値の JSON シリアライズでエラーを出したら、int(...) を str(...) に変えるか、json.dumps で default=str を使います。

確認ポイント

資料を見ずに自分で説明できるべき2つの問い

1. 問題文に応じて RDS、Aurora、DynamoDB、ElastiCache のどれを選ぶか？

回答の骨組み（隠してから自分で説明してみる）：

  • 最初の問い：データはリレーショナル（SQL、join、transaction）か、key-value か？ リレーショナル → RDS/Aurora。key-value、serverless、無制限のスケール、ms → DynamoDB。
  • リレーショナルの中では：エンジンが Oracle/SQL Server、またはシンプルで安価なマネージドで十分 → RDS。MySQL/PostgreSQL で最高の性能と HA、15 replica、Global Database、Serverless v2 が必要 → Aurora。
  • ElastiCache は DB の代わりではなく、DB の前に置くものです：sub-millisecond、reduce read load、session store、leaderboard とあれば選びます。HA/永続化/データ構造が必要なら Redis、シンプルでよければ Memcached。DynamoDB 専用のキャッシュは DAX です。
  • 各タイプの例を1つずつ挙げられること：会計 ERP → RDS、10 replica が必要な大規模 MySQL Web app → Aurora、ショッピングカート・session → DynamoDB、商品ページの読み取り負荷軽減 → ElastiCache。

2. Multi-AZ は HA のため、Read Replica は scale read のため？

回答の骨組み：

  • Multi-AZ：別 AZ の standby、synchronous レプリケーション、1〜2分の自動 failover、endpoint は変わらない、standby は読み取り不可（Multi-AZ DB cluster を除く）。目的：AZ 障害やメンテナンス時にデータを失わず、ダウンタイムを短くすること。
  • Read Replica：asynchronous なコピーで lag があり、専用の endpoint を持ち、app 側で読み取りクエリを振り分ける。cross-Region も可能で、最大15。自動 failover はなく、primary として使うには手動で promote する必要がある。
  • 両者は補完し合う関係で、本番では両方を有効にするのが一般的。Aurora は2つの役割を兼ね、replica が読み取りと standby の両方を担う。
  • 例を1つ挙げられること：レポートが app を遅くする → Read Replica、AZ 障害に耐えることが要件 → Multi-AZ。
