KMS と暗号化、ACM、CloudHSM

概要: KMS とは
  • AWS KMS（Key Management Service）は、AWS が管理する HSM 上で暗号鍵を作成、保管、利用するサービスです。鍵は平文のまま KMS の外に出ることはありません。データ（Encrypt 1回あたり最大 4 KB）を送ると、KMS が暗号文を返します。「encryption at rest」を持つほぼすべての AWS サービス（EBS、S3、RDS、DynamoDB、Lambda env、SQS、CloudTrail、Secrets Manager）は KMS の鍵で暗号化します。
  • KMS は regional なサービスです。東京で作った鍵は東京でしか使えません。暗号化済みの EBS/RDS スナップショットを別 Region にコピーする場合は、コピー先 Region の鍵を指定して再暗号化します。
  • 鍵を使うたびに CloudTrail に記録されます（誰が、いつ、どの鍵を）。監査担当者が自前の暗号化より KMS を好む理由です。
管理者で分ける3種類の鍵
種類誰が作り、誰に見えるかKey policy、rotation料金（要確認）設問で問われるとき
AWS owned keyAWS が作成し、複数アカウントで共用。自分には見えず、管理もできず、自分の CloudTrail にも出ません。操作できません無料SSE-S3、DynamoDB など多くのサービスの既定。設問が「encrypted at rest」だけを求め、制御を要求しないときに選びます。
AWS managed keyサービスが必要としたときに自分のアカウント内に自動作成。名前は aws/s3、aws/ebs、aws/rds。コンソールと CloudTrail で見えます。Key policy は AWS が記述し、編集不可。1年ごとに自動 rotate、無効化不可。鍵の保管料なし、リクエスト料のみ鍵の利用を監査したいが自分で管理する必要はないとき。cross-account では使えません。
Customer managed key (CMK)自分で作成し、alias を付け、key policy を書き、有効化と無効化、削除予約ができます。完全な制御。rotation は任意で、有効にすると1年（現在は 90〜2560 日に調整可能、要確認）。約 1 USD/鍵/月 + 10,000 リクエストあたり 0.03 USD設問に full control over keys、key policy、cross-account、disable key、audit key usage、rotation every X とあるとき。

補足: S3 では、SSE-S3 は AWS owned key（無料、見えない）、SSE-KMS は AWS managed の aws/s3 または CMK（CloudTrail あり、KMS 権限のないユーザーを拒否できる）、SSE-C はリクエストごとに自分の鍵を送る（AWS は保存しない）、client-side はアップロード前に自分で暗号化します。DSSE-KMS は高いコンプライアンス要件向けの二重暗号化です（名前だけ覚えておく）。

Symmetric と asymmetric
  • Symmetric (AES-256): 1つの鍵で暗号化と復号の両方を行います。既定で、高速、安価、すべての AWS サービスで使えます。鍵はダウンロードできないため、暗号化には KMS API を呼ぶ必要があります（または data key を使う。下の envelope を参照）。
  • Asymmetric (RSA, ECC): public/private のペア。Public key はダウンロードでき、AWS の外で暗号化や検証に使えます。private key は KMS の外に出ません。AWS の外部から自分宛てに暗号化して送る場合や、電子署名（sign/verify）が必要な場合に使います。automatic rotation はありません。
  • HMAC key: 認証コードの生成と検証（名前だけ覚えておく）。これも auto rotate しません。
イメージ: envelope encryption
  • KMS が直接暗号化できるのは最大 4 KB です。それより大きいデータは envelope encryption を使います。GenerateDataKey を呼んで平文の data key とその暗号文を受け取り、データは data key でローカル暗号化し、保存するのは data key の暗号文だけです。データ本体がネットワーク経由で KMS に送られることはありません。
  • 試験での帰結: SSE-KMS バケットにアップロードするユーザーには kms:GenerateDataKey、ダウンロードするユーザーには kms:Decrypt が必要です。どちらかが欠けると、S3 の policy が十分でも AccessDenied になります。Lab 3 でこのエラーをそのまま再現します。
  • Encryption context: 暗号化のたびに付ける key-value のペア（例: バケット名）で、復号時に一致している必要があり、CloudTrail に記録されます。ある場所の暗号文を別の場所で復号する行為を防ぎます。
Key policy、IAM policy、grant
  • Key policy は鍵ごとに付く resource-based policy で、必ず存在します。S3 と違い、key policy が許可していなければ、アカウント内の IAM policy も効きません。既定の key policy には "Principal": {"AWS": "arn:aws:iam::ACCOUNT:root"}, "Action": "kms:*" という statement があり、「このアカウントの IAM policy に判断を委ねる」という意味です。この statement を消すと、IAM policy はこの鍵に対して効かなくなります。
  • Cross-account: 鍵の所有アカウントの key policy で相手アカウントの principal を Allow し、同時に相手アカウントの IAM policy でも kms アクションを Allow する必要があります。S3 の cross-account と同じ「両側の積」のルールです。暗号化済み EBS/RDS スナップショットを別アカウントに共有するには CMK が必須です（AWS managed の aws/ebs は共有できません）。
  • Grant: 取り消し可能な一時的な権限で、ある principal に鍵の一部のアクションを許可します。AWS サービス（volume attach 時の EBS、RDS、Secrets Manager）は自分の代わりに grant を自動作成して鍵を使います。設問の temporary, programmatic permission to use a key → grant。
  • よく出る条件: kms:ViaService（S3 や EBS 経由でのみ鍵を使わせる）、kms:EncryptionContext、aws:PrincipalOrgID。
Rotation、multi-Region、import、削除
項目覚えるべき詳細
Automatic rotationKMS が key material を生成した symmetric CMK のみ対象。既定は1年ごと。rotation で新しい key material が生成されますが、key ID、ARN、alias は変わらず、古い material は古いデータの復号用に保持されるため、アプリは何も再暗号化する必要がありません。AWS managed key は1年で自動 rotate し、無効化できません。Asymmetric、HMAC、imported material、custom key store はauto rotate しません。
Manual rotation新しい鍵を作成し、alias を付け替える（UpdateAlias）。アプリは alias で呼ぶのでコード変更は不要です。古いデータの復号のために古い鍵は残す（削除しない）必要があります。asymmetric、imported、またはより頻繁に rotate したい場合に使います。
Multi-Region keyprimary key と他 Region の replica が同じ key ID と key materialを持つため、東京の暗号文を大阪で、Region をまたいで KMS を呼ばずに復号できます。クライアント側暗号化の DynamoDB global tables、DR、Region をまたぐバックアップに使います。各 replica は独立したリソースで、key policy も料金も別々です。「global key」ではありません。
Imported key material社内の HSM で鍵を生成して KMS に import します（BYOK）。有効期限を設定でき、待機期間なしでmaterial を即時削除できますが、material を失うとデータも失います。auto rotation はなく、自分で新しい material を import します。
鍵の削除即時には削除できず、7〜30日（既定 30）の waiting period 付きで schedule deletion します。待機中は Pending deletion 状態で使用不可、キャンセル可能です。期限が切れると永久に失われ、その鍵で暗号化したデータは復元できません。削除ではなく disable を選ぶべきです。
リクエスト制限アカウントごとに Region 単位で KMS リクエストの秒間 quota があります（数千 request/秒、具体的な数値は要確認）。小さなオブジェクトが多い S3 バケットで SSE-KMS を使うと ThrottlingException が出やすくなります。対策: S3 Bucket Key を有効化（S3 が CMK から bucket-level key を作り、KMS リクエストを最大 99% 削減）、または SDK の data key caching を使います。
EBS と RDS の暗号化: よく出る2つの落とし穴
  • 暗号化されていない EBS volume をその場で暗号化することはできません。手順: snapshot → Encrypt にチェックを入れて copy snapshot（CMK を選択）→ 暗号化済み snapshot から新しい volume を作成 → volume を付け替え。暗号化済み volume の snapshot は常に暗号化されます。Region 単位で EBS encryption by default を有効にすると、新しい volume はすべて自動で暗号化されます。
  • RDS も同じです。暗号化は作成時にしか選べません。未暗号化 DB → snapshot → 暗号化付きで copy snapshot → 新しい DB として restore。暗号化済み DB の read replica は常に暗号化されます。暗号化済み snapshot を cross-account で共有するには CMK を使い、鍵も共有する必要があります。
ACM (Certificate Manager)
  • TLS/SSL 証明書の発行と管理を行います。Public certificate は無料で、DNS 検証（CNAME を追加。Route 53 なら自動）またはメール検証を行います。ACM が発行した証明書は検証用 CNAME が残っていれば自動更新されます。外部から import した証明書は自動更新されず、再 import が必要です（ACM は期限前に EventBridge イベントを送り、Config には acm-certificate-expiration-check ルールがあります）。
  • ALB、NLB (TLS listener)、CloudFront、API Gateway、Elastic Beanstalk、App Runner で使います。EC2 に直接付けることはできず、public certificate は export できません（private key は ACM 内にあります）。EC2 上で TLS を使うなら証明書を購入するか ACM Private CA を使います（private 証明書なら export 可能）。
  • ACM は regional です。東京の ALB 用証明書は東京で作ります。ただし CloudFront は us-east-1（N. Virginia）の証明書が必須です。CloudFront が global サービスだからです。これは定番の問題です。
  • ACM Private CA: 社内サービス、IoT、mTLS 向けに証明書を発行する内部 CA を構築します。月額課金（約 400 USD/CA/月、要確認）のためラボでは使いません。
CloudHSM
  • 自分の VPC 内に置く専有（single-tenant）の物理 HSM で、FIPS 140-2 Level 3 認証済みです。ハードウェアは AWS が面倒を見ますが、ユーザー、鍵、バックアップは自分で管理し、AWS は鍵にアクセスできません。HA のためクラスターを複数 AZ に広げます。HSM ごとに時間課金（約 1.5 USD/時、要確認）のためラボは行いません。
  • 使いどころ: コンプライアンスが dedicated hardware、customer must control the key hardware を要求するとき、Web サーバーの SSL offload、Oracle TDE、PKCS#11、JCE、CNG ライブラリ。
  • custom key store を介して KMS と組み合わせられます。API は KMS のまま（AWS サービスは通常どおり使える）ですが、key material は自分の CloudHSM 内にあります。現在は鍵を AWS の外に完全に置く external key store (XKS) もあります（名前だけ覚えておく）。
  • KMS との比較: KMS は multi-tenant、managed、すべてのサービスと統合、安価。CloudHSM は single-tenant、自分で運用、custom key store 経由で統合。KMS の HSM も FIPS 140-2 Level 3 を取得済み（要確認）ですが、試験では「Level 3、single-tenant、自己管理」という表現が CloudHSM を指します。

確認クイズ

1. アプリが 200 MB のファイルを保存前に KMS で暗号化する必要があります。開発者がファイル全体を kms:Encrypt に渡したところエラーになりました。正しい方法は?

Envelope encryption: GenerateDataKey を呼び、平文の data key でファイルをローカル暗号化し、暗号化済みファイルと暗号化済み data key を一緒に保存する。 KMS はリクエストあたり最大 4 KB しか受け付けません。ファイルを 4 KB ずつに分割して KMS を何度も呼ぶのは設計として誤りで、リクエスト料もかかります。

2. IAM user が customer managed key の SSE-KMS バケットに対して s3:* の policy を持っています。アップロードはできますがダウンロードが AccessDenied になります。何が足りませんか?

その鍵に対する kms:Decrypt が不足（ユーザーの IAM policy に必要で、key policy が IAM に委任している必要があります）。アップロードには kms:GenerateDataKey、ダウンロードには kms:Decrypt が必要です。落とし穴: S3 の権限は十分なのに bucket policy を疑う人が多いです。

3. production の EC2 に 500 GB の未暗号化 EBS volume が付いており、minimal downtime で CMK により暗号化する必要があります。どうしますか?

snapshot を取り、CMK で encrypt するオプション付きで copy snapshot し、暗号化済み snapshot から新しい volume を作り、短時間 instance を停止して volume を付け替える。 既存 volume に「暗号化を有効にする」ボタンはありません。EBS encryption by default は今後作る volume にしか影響しません。

4. KMS automatic rotation について正しい記述を2つ選んでください。(A) asymmetric key に適用される、(B) rotation 後も key ID と ARN は変わらない、(C) 古いデータを再暗号化する必要がある、(D) 古い key material は古いデータの復号用に保持される。

B と D。 Asymmetric key に auto rotation はありません（A は誤り）。古いデータは古い material で復号できるので re-encrypt は不要です（C は誤り）。automatic rotation がアプリに対して「透過的」な理由です。

Secrets Manager と Parameter Store

概要
  • Secrets Manager: シークレット（DB パスワード、API key、OAuth token）の保管庫で、主な機能は自動 rotation です。すべてのシークレットは KMS で暗号化され、バージョン（AWSCURRENT、AWSPREVIOUS、AWSPENDING）を持ち、resource policy があるため cross-account で共有でき、別 Region への複製もできます。シークレットの削除には 7〜30日の recovery window があります（または --force-delete-without-recovery）。
  • Systems Manager Parameter Store: 設定値（文字列、リスト、機密データ向けの SecureString）を /app/prod/db/host のような階層 (hierarchy)で保管します。バージョンがあり、GetParametersByPath で枝ごとまとめて取得できます。Standard tier は無料です。rotation 機能は組み込まれていません。
  • どちらも CloudFormation の dynamic reference（{{resolve:secretsmanager:...}}、{{resolve:ssm-secure:...}}）、Lambda、ECS（環境変数への注入）と統合され、どちらも CloudTrail に記録されます。Parameter Store からは /aws/reference/secretsmanager/ten-secret というパスで Secrets Manager のシークレットも読めます。

エッジ保護: WAF、Shield、Firewall Manager、Network Firewall

概要
  • AWS WAF: layer 7 (HTTP/HTTPS) のファイアウォールです。rule（自作、または AWS や Marketplace の managed rule group）をまとめた Web ACL を作り、各 rule には Allow、Block、Count、CAPTCHA、Challenge のいずれかの action を設定します。Web ACL は CloudFront、ALB、API Gateway (REST)、AppSync、Cognito User Pool、App Runner、Verified Access に関連付けます。NLB や EC2 には直接関連付けできません（NLB と EC2 は HTTP を解釈しないため）。CloudFront 用の Web ACL は us-east-1（global）で作成します。
  • よく出る rule: rate-based rule（一定期間に N リクエストを超えた IP をブロック。ブルートフォースや軽度の layer 7 DDoS 対策）、IP set（allow list、block list）、geo match（国単位でブロック）、SQL injection と XSS の match、size constraint、regex、Bot Control managed rule（悪質な bot をブロック）、Account Takeover Prevention（名前だけ覚えておく）。WAF のログは CloudWatch Logs、S3、Kinesis Data Firehose に送れます。料金は Web ACL 数、rule 数、100万リクエスト単位です（要確認）。
  • Shield Standard: layer 3/4 の DDoS（SYN flood、UDP reflection）を自動で防御し、無料、全アカウントで既定有効、CloudFront、Route 53、Global Accelerator、ELB を保護します。何もする必要はありません。
  • Shield Advanced: 約 3,000 USD/月、1年契約（要確認）。追加されるもの: layer 7 の DDoS 検知と緩和、EC2 Elastic IP、ELB、CloudFront、Global Accelerator、Route 53 の保護、24時間365日対応の Shield Response Team（SRT、旧称 DRT）、cost protection（DDoS による費用増、例: Auto Scaling の膨張分を返金）、保護対象リソースの WAF が無料、DDoS のダッシュボードとレポート、Route 53 health check による health-based detection。
  • Firewall Manager: WAF、Shield Advanced、Security Group、Network Firewall、Route 53 Resolver DNS Firewall のポリシーを AWS Organizations 全体で一元管理します。policy を一度作れば、全アカウントと将来新しく作られるリソースにも自動適用されます。Organizations と Config が前提です。
  • Network Firewall: VPC レベルに置く managed ファイアウォールです（専用 subnet に firewall endpoint を作り、トラフィックをそこに route します）。stateless と stateful の rule、Suricata rule による IDS/IPS、domain フィルタ（外向き通信のドメイン allow list）、TLS inspection、プロトコルによるフィルタを備えます。VPC からインターネットへの通信、Transit Gateway 経由の VPC 間通信（集中型 inspection VPC）、オンプレミスからの通信に使います。WAF との違いは、WAF が HTTP だけを理解し CloudFront/ALB に付くのに対し、Network Firewall は VPC を通る layer 3〜7 のすべてのパケットを見る点です。
  • 全体像のための復習: Security Group（stateful、instance/ENI 単位、allow のみ）、NACL（stateless、subnet 単位、allow と deny、特定 IP をブロック）、Route 53 Resolver DNS Firewall（悪性ドメインへの DNS クエリをブロック。DNS のフィルタだけでよいなら Network Firewall より安価）。

SCP (Service Control Policy): 覚えるべき6つのこと
  1. SCP はメンバーアカウントの権限の上限であり、権限を付与しません。実際の権限 = SCP ∩ IAM policy。permissions boundary に似ていますが、アカウント単位です。
  2. SCP は management account には影響しません（Root に付けても同じ）。一方、メンバーアカウントではそのアカウントの root user を含むすべての principal に適用されます。
  3. ツリーを下に継承します。アカウントは Root、すべての親 OU、自分自身の SCP を受けます。許可される権限はすべての階層で Allow され、どの階層でも Deny されていない必要があります。
  4. 2つの戦略: deny list（すべての階層に既定の FullAWSAccess を残し、Deny の SCP を追加。管理しやすく AWS 推奨）と allow list（FullAWSAccess を外し、許可するサービスだけを Allow。厳格だが、すべての親階層で Allow を忘れずに付ける必要があり、誤ってロックしやすい）。
  5. SCP は service-linked role や一部の AWS の管理操作には適用されません。SCP には Principal がありません（アカウント全体に適用されるため）。
  6. 定番の例: Region の制限、CloudTrail/GuardDuty/Config の無効化の禁止、Organization からの離脱の禁止（organizations:LeaveOrganization）、タグの必須化、t3 以外の EC2 作成の禁止、KMS key の削除禁止、EBS 暗号化の必須化。

CloudTrail: 誰が何をしたか
  • すべての API call（Console、CLI、SDK、サービス間の呼び出し）を記録します: 誰が、いつ、どの IP から、どのパラメータで、結果は何か。Event history は既定で有効、無料で、90日間保持し、management event のみです。より長く保持して分析するには、S3 に書き込む trail を作り（無期限に保持、lifecycle を利用）、必要に応じて CloudWatch Logs にも送ります（metric filter と alarm を作るため。例: root がログインしたときや誰かが DeleteTrail を呼んだときの警告）。
  • Management event（control plane: EC2 作成、Security Group 変更、ログイン）: 既定で記録、read と write。Data event（data plane: S3 の GetObject/PutObject、Lambda の Invoke、DynamoDB の item）: 既定では記録されず、個別に有効化、量が多く追加料金。Insights event: write API やエラーの異常な割合を検知（例: 突然 RunInstances が1,000回）、追加料金。
  • Multi-Region trail: 1つの trail で全 Region を記録（コンソールでは既定）、新しい Region も自動追加。Organization trail: management account（または delegated admin）で作成し、全メンバーアカウントを1つのバケットに記録、メンバーアカウントは無効化できません。global サービス（IAM、STS、CloudFront）の event は us-east-1 に記録されます。
  • Log file integrity validation: CloudTrail は1時間ごとに SHA-256 ハッシュと RSA 署名を含む digest file を作り、validate-logs コマンドでログが改ざんや削除されていないことを証明できます。S3 Object Lock、MFA delete、専用の Log Archive アカウントのバケットと組み合わせて tamper-proof を実現します。ログは既定で SSE-S3 で暗号化され、SSE-KMS も選べます。
  • 配信は通常5〜15分ほど遅れます（要確認）。S3 上のログは Athena でクエリするか、CloudTrail Lake（保存と SQL クエリ、最大7年保持、名前だけ覚えておく）を使います。

21. 監査人から、2か月前にバケット内のオブジェクトを削除したのは誰かと聞かれました。アカウントには既定の Event history しかなく、trail はまだ作っていません。答えられますか?

答えられません。 Event history は90日間かつ management event しか保持しません。DeleteObject は data event であり、trail で data event を有効にしていなければ記録されません。教訓: 最初から S3 への multi-Region trail を作り、重要なバケットの data event を有効にしておくこと。

22. 運用チームは、EC2 上のアプリが RAM を90%超えて使ったときに警告を受けたいと考えています。least operational overhead が条件です。何を選びますか?

CloudWatch agent を入れて（SSM Run Command で配布可能）mem_used_percent metric を送り、SNS に通知する alarm を作る。 detailed monitoring にメモリは含まれません。PutMetricData を呼ぶスクリプトの自作も動きますが、agent より手間がかかります。

23. セキュリティ要件: NAT のない private subnet の EC2 に22番ポートを開けないこと。ただし管理者はシェルに入れる必要があり、すべてのセッションを記録すること。何を選びますか?

SSM Session Manager を使い、ssm、ssmmessages、ec2messages の VPC interface endpoint を作り、AmazonSSMManagedInstanceCore の role を付け、CloudWatch Logs/S3 へのセッションログを有効にする。 22番を開ける bastion は要件違反です。NAT がないので、エージェントが SSM に接続するには endpoint が必要です。

24. アプリのログを CloudWatch Logs からほぼリアルタイムで OpenSearch に送る方法を2つ選んでください: (A) Lambda への subscription filter、(B) S3 に export してから import、(C) Kinesis Data Firehose への subscription filter、(D) Logs Insights。

A と C。 Subscription filter がリアルタイムの仕組みです。Export to S3 はバッチ（最大12時間遅延）です。Logs Insights はクエリツールでデータを転送しません。

CloudFormation: template、stack、change set
  • Template（YAML または JSON）がリソースを記述し、stack はその template から作られたリソースの集合です。セクション: Parameters（作成時に入力）、Mappings（参照表。例: Region ごとの AMI）、Conditions、Resources（必須）、Outputs。よく使う関数: !Ref、!GetAtt、!Sub、!FindInMap、!ImportValue、!Join。サービス自体は無料で、作成したリソースの料金だけを払います。
  • Change set: 実行前に、stack の更新でどのリソースが追加、変更、置換 (replace) されるかをプレビューします。一部のプロパティを変えると CloudFormation は古いリソースを削除して新しく作ります（例: RDS の名前変更）。change set はそれを示してくれるので、データ消失を防げます。
  • 作成に失敗すると自動 rollback ですべて削除されます（ROLLBACK_COMPLETE 状態になり、stack を削除して作り直す必要あり）。更新に失敗すると以前の状態に rollback します。UPDATE_ROLLBACK_FAILED なら continue update rollback を使います。デバッグ時は rollback を無効にできます。
  • StackSets: 1か所から1つの template を複数アカウント、複数 Region にデプロイします。Organizations と統合でき（service-managed permissions、OU に追加された新アカウントへ自動デプロイ）、設問: deploy baseline to all accounts、same configuration in every Region。
  • Drift detection: CloudFormation の外で手動変更されたリソースを検知します（誰かがコンソールで Security Group を変えた）。自動修正はせず、報告だけです。
  • DeletionPolicy: Delete（既定）、Retain（stack 削除時にリソースを残す）、Snapshot（削除前に snapshot を取る。RDS、EBS、ElastiCache、Redshift、Neptune 向け）。UpdateReplacePolicy はリソースが replace されるときの同様の設定です。Termination protection は stack 全体の誤削除を防ぎます。Stack policy は一部リソースの更新を禁止します（例: prod の RDS を更新させない）。
  • Nested stack: 親 stack が S3 上の子 template を指す AWS::CloudFormation::Stack リソースを持ち、パターン（VPC、ALB）を再利用し、stack あたりのリソース数上限（500、要確認）を超えられます。Cross-stack reference: stack A が Outputs で Export を宣言し、stack B が !ImportValue で使います。export 名は Region 内で一意で、B が import している間は A を削除できません。ライフサイクルが同じなら nested、異なるなら cross-stack（network チームと app チーム）。
  • その他: custom resource（CloudFormation が未対応の処理を Lambda で行う）、CreationPolicy と組み合わせる cfn-init と cfn-signal（EC2 からインストール完了の通知を待って CREATE_COMPLETE とみなす）、DependsOn、Secrets Manager/Parameter Store への dynamic reference、CloudFormation Registry と Guard（名前だけ覚えておく）、既存リソースから template を作る IaC generator（名前だけ覚えておく）。
Elastic Beanstalk: PaaS と deployment policy
  • コード（Java、.NET、Node.js、Python、PHP、Ruby、Go、Docker）をアップロードすると、Beanstalk が裏側の CloudFormation で EC2、Auto Scaling、ELB、CloudWatch、（任意で）RDS を自動構築します。追加料金はなく、リソース代だけです。EC2 への完全なアクセス権も残ります。設定は .ebextensions/*.config ファイルで行います。2つの tier: web server（ELB + ASG）と worker（SQS + ASG でバックグラウンド処理）。Managed platform update で maintenance window にプラットフォームをパッチ適用します。
  • environment 内で作った RDS は environment と一緒に削除されます。本番では RDS を外部に作り、環境変数で参照すべきです。よく出る問題です。

25. CloudFormation stack に本番の RDS があります。チームは stack を削除したとき（または更新時に RDS が replace されたとき）にデータを失わないようにしたいと考えています。何を選びますか?

RDS リソースに DeletionPolicy: Snapshot（または Retain）と UpdateReplacePolicy: Snapshot を設定し、stack に termination protection を付ける。 termination protection だけでは、replace を伴う更新からは守れません。RDS の自動バックアップも instance の削除と一緒に消えます（automated backups を保持しない限り）。

26. Elastic Beanstalk 上のアプリで、新バージョンをダウンタイムなし、キャパシティ維持でデプロイし、失敗時は最速で rollback する必要があります。どの policy を選びますか?

Immutable。 新しい instance は一時 ASG に作られ、失敗したらそれを消すだけで、古い instance には手を付けていません。Rolling with additional batch もキャパシティを維持しますが、rollback は逆方向の rolling になるため遅くなります。All at once はダウンタイムがあります。

27. 財務部門が先月から各チームのコストを知りたいと考えています。リソースには年初から Team タグが付いていますが、Cost Explorer でタグによる絞り込みができません。なぜか、また何に注意すべきか?

Team タグを Billing console で cost allocation tag として activate していないため。 activate 後、最大24時間待つ必要があり、データは activate した時点以降しかなく、先月分には遡って適用されません（過去の数値が必要なら CUR と別の方法を組み合わせるか、欠落を受け入れる）。

確認ポイント

資料を見ずに自分で説明できるべき2つの問い

1. Secrets Manager と Parameter Store の違い

回答の骨組みのヒント（隠してから自分で話す）:

  • どちらも機密値を KMS で暗号化して保存し、CloudFormation、Lambda、ECS と統合されています。違いは rotation、料金、cross-account、階層です。
  • Secrets Manager: 自動 rotation（RDS、Aurora、Redshift、DocumentDB は managed、その他は Lambda）、0.40 USD/シークレット/月、resource policy による cross-account 共有、Region 複製、7〜30日の recovery window。
  • Parameter Store: standard tier は無料（4 KB、10,000 パラメータ）、advanced は有料（8 KB、有効期限の policy）、KMS 暗号化の SecureString、階層とパス単位の取得、rotation なし、従来は cross-account 不可。
  • 選択ルールを言えること: rotate credentials、RDS password、share with another account → Secrets Manager。configuration、lowest cost、hierarchy → Parameter Store。

2. WAF、Shield、GuardDuty、Inspector、Macie を目的で区別する

回答の骨組みのヒント:

  • 2つのグループに分けます: エッジでブロック（WAF、Shield）と内部で検知（GuardDuty、Inspector、Macie）。
  • WAF: rule（SQLi、XSS、rate、geo、bot）で HTTP をフィルタし、CloudFront/ALB/API Gateway に付ける。NLB は不可。Shield: DDoS 対策。Standard は無料で L3/L4、Advanced は有料で L7 + SRT + cost protection。
  • GuardDuty: CloudTrail、VPC Flow Logs、DNS logs から進行中の脅威を検知、エージェント不要。Inspector: EC2、ECR image、Lambda の CVE 脆弱性を探す。Macie: S3 内の機密データ (PII) を探す。
  • 補足して全体像を: Security Hub は3つの findings を集約し標準で採点、Detective は原因を調査、Config は設定の準拠をチェック、Trusted Advisor は support plan に応じてベストプラクティスをチェック。
  • 各サービスの例を1つずつ言えること: SQL injection → WAF、SYN flood → Shield、EC2 の暗号通貨マイニング → GuardDuty、AMI 内の Log4j CVE → Inspector、バケット内のクレジットカード番号 → Macie。
